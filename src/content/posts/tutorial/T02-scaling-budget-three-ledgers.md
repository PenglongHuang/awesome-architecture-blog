> 一句话点题：**模型规模不是抄头部模型的参数量。真正的判断是把训练账、推理摊销账与研发账合成一本总账——Chinchilla 只是训练终点的一次性最优，部署形态与研发试错才是规模决策的主变量。**

## 开场：同一个模型，两个"20:1"都够不着

[GLM-5 技术报告](https://arxiv.org/abs/2602.15763)披露了一组常被拿来当参照的数字：744B 总参数、40B 激活参数的 MoE，预训练 28.5T Token（口径：报告披露的预训练 Token 数，权重 MIT 开放）。

于是有人拿"训练 Token ÷ 参数量"去对照著名的 Chinchilla 比例（约 20:1），发现同一份 Token 数能算出两个相差近 20 倍的比值：

| 分母口径 | 计算 | Token : 参数 | 与约 20:1 的距离 |
|---|---|---:|---|
| 总参数 744B | 28.5T ÷ 744B | 约 38 : 1 | 约 2 倍 |
| 激活参数 40B | 28.5T ÷ 40B | 约 712 : 1 | 约 35 倍 |

先别急着判断哪个"超标"。第一个问题应该是：**分母是什么？**

- **总参数**回答"这个模型装了多少东西"——对应显存占用与权重体积；
- **激活参数**回答"每个 Token 实际动了多少参数"——对应每个 Token 的计算量。

MoE 模型每个 Token 只激活一小部分专家，所以两个口径天然差一个量级。用总参算出的 38:1 和用激活算出的 712:1，描述的是同一个事实的两个侧面，谁也不是笔误。

第二个问题更重要：**Chinchilla 的 20:1 到底在优化什么？** 它优化的是"只花一次训练算力时，训练终点的损失最低"。它不管你训完之后要服务多少请求，不管你的研发路上要死多少次实验，也不管你的模型是 Dense 还是 MoE。一个只看训练终点的最优解，落到要持续服务、持续试错的真实业务里，"远离 20:1"不但不奇怪，反而可能是正确决策的结果。

本章的任务，就是把这句话变成一套能落地的算法。

> **本章只解决一件事：给定目标能力、预算和部署形态，如何决定模型规模、训练 Token 数与推理预算？**

本章的推导路线，也是三本账的展开顺序：

```text
第 1 节   一个必须做选择的场景（隐藏成本登场）
    ↓
第 2 节   Chinchilla 在优化什么、它的三条适用边界
    ↓
第 3 节   训练账：6ND → 卡时 → 费用
    ↓
第 4 节   推理摊销账：请求量如何改写最优配比
    ↓
第 5 节   研发账：最终 Run 背后的乘数与账本
    ↓
第 6 节   部署形态倒推规模
    ↓
第 7 节   用小规模实验验证 Scaling 决策
    ↓
第 8 节   三本账合并 + Training Budget Calculator
```

## 一、同样的预算，为什么有团队训大模型，有团队选择小模型

### 1. 先做一个你会真实遇到的选择

假设你的团队要交付一个企业代码助手（以下为教学用合成场景，数字是编的，推导方法是真用的）：

- 目标能力：仓库级代码补全 + 技术问答；
- 负载：峰值并发 200 路，月均 1 亿次请求；
- 延迟：首 Token P95 < 1 秒；
- 服务周期：18 个月；
- 预算：一笔固定的训练预算，只够在三个候选方案里选一个。

| 方案 | 模型形态 | 训练 Token（示意） | 配比（Token : 参数） | 训练算力粗估 | 支持者的直觉理由 |
|---|---|---:|---:|---:|---|
| A | 700B 总参 / 40B 激活 MoE | 28T | 40 : 1（总参口径） | 约 6.7e24 FLOPs | 对齐头部开源模型的量级，一步到位 |
| B | 100B Dense | 2T | 20 : 1 | 约 1.2e24 FLOPs | 靠近 Chinchilla 配比，训练算力效率最优 |
| C | 30B Dense | 6.7T | 约 220 : 1 | 约 1.2e24 FLOPs | 小模型重度过度训练，推理便宜 |

注意 B 和 C 的训练算力粗估几乎相同（都用 6ND，Dense 无需区分口径）——同一笔训练预算，两种分法。这个巧合是本章后面最重要的一组对照。方案 A 则先放着，它要到最后才揭晓全部账目。

暂停一下，凭直觉选一个。选完再往下看。

### 2. 三个候选都只给你看了半本账

这三个方案的"直觉理由"都只算了训练这一笔账。还有两笔被略去了：

- **推理摊销账**：B 与 C 的训练账几乎相同，但每 Token 推理计算差 3 倍多（100B 对 30B）；月均 1 亿次请求 × 18 个月，这笔钱每个月都在发生，差距每个月都在累积。
- **研发账**：你看到的 28T / 2T / 6.7T 都是"最终训练 Run"的 Token 数。走到最终 Run 之前的数据实验、结构试验、失败重启、后训练，每一项都在烧同一批卡。

于是"哪个方案好"这个问题，无法在训练账内部回答。它至少要三本账一起翻：

| 账本 | 花费节奏 | 由什么决定 | 典型的遗漏方式 |
|---|---|---|---|
| 训练账 | 一次性 | 参数规模 × 训练 Token × 硬件效率 | 只报 FLOPs，不算卡时 |
| 推理摊销账 | 按月持续 | 请求量 × 每请求 Token × 单 Token 成本 | 用离线榜单代替单位成本 |
| 研发账 | 随实验发生 | 最终 Run × 试验乘数 | 把最终 Run 当成全部 |

```text
目标能力 + 部署形态 + 服务量
        ↓
┌─────────────────────────────────────┐
│ 训练账(一次性)                          │
│ 推理摊销账(按月)                        │   三本总账
│ 研发账(隐藏在最终 Run 背后)              │
└─────────────────────────────────────┘
        ↓
决策输出：总参数 / 激活参数、训练 Token、采样预算
        ↓
验证闭环：小规模外推 → 预测台账 → 复盘偏差
```

> **架构智慧：**规模决策的争论之所以难解，通常不是因为缺少数字，而是因为双方拿着不同的账本——一个在算训练终点，一个在算服务生命周期。先把三本账摊在同一张桌上，争论才有收敛的可能。

接下来逐本账拆开。

## 二、Scaling Law 与 Chinchilla 的适用边界

### 1. 先建立直觉：算力买的是"损失"的下降，而下降本身在递减

训练的目标通常是压低模型在下一个 Token 上的**损失（Loss）**——可以先理解成"模型对下文的预测错得多离谱"的度量。经验上，损失随算力、参数、数据的增长呈**回报递减**的平滑下降（常被拟合为幂律）：每一倍的投入，买到的损失下降都比上一倍少。

```text
损失
 │＼
 │  ＼
 │    ＼_
 │        ＼__
 │            ＼＿＿___
 │                    ＼＿＿＿＿＿＿＿＿ ← 趋平，但不会很快到零
 └────────────────────────────────────→ 训练算力
      10 倍算力买到的下降，比前一段少
```

这张草图解释了 Scaling 决策的全部张力：收益递减但持续，于是"再加一倍算力值不值"永远是个真问题；同时参数与数据都能换损失，于是"这一倍算力买参数还是买数据"也是个真问题。

### 2. 算力的记账单位：6ND 粗估

要比较"买什么"，先得会记账。训练算力大致按这个关系被消耗（工程上常用的粗估，称为 6ND 规则）：

```text
训练计算量 C ≈ 6 × N × D

N：每个 Token 参与计算的参数量（Dense 即总参数；MoE 用激活参数口径）
D：训练 Token 数
直觉拆解：前向约 2 + 反向约 4 ≈ 每个"参数 × Token"组合 6 次量级的运算
```

模型要变好，要么加参数（N 变大），要么加数据（D 变大）。算力固定时，两者此消彼长：参数翻倍，同预算下 Token 就得减半。

### 3. Chinchilla 回答的正是这个问题——但只回答了一次性训练的版本

[Chinchilla 论文](https://arxiv.org/abs/2203.15556)（Hoffmann 等人，2022）的做法可以概括成一组"等算力实验"（isoFLOP）：固定总训练算力，只改变 N 和 D 的分配比例，看哪种组合的训练终点损失最低。用教学示意的数字（非任何真实实验）：

| 实验 | 参数量 N（示意） | Token D = 预算 ÷ 6N（示意） | 训练终点损失（示意） |
|---|---:|---:|---:|
| 1 | 1B | 30T | 2.30 |
| 2 | 3B | 10T | 2.18 |
| 3 | 9B | 3.3T | 2.25 |

同一笔算力，中间的配比损失最低。Chinchilla 对一系列算力规模做这类实验后得出：对 Dense 模型，算力最优配比大约是每个参数配 20 个上下的 Token（常用概述口径约 20:1），而不是更早的拟合所倾向的"优先堆参数"。

这个结论极其有用，但它有三条经常被忽视的边界。

### 4. 边界一：它优化"训练终点"，不优化"部署生命周期"

Chinchilla 的目标函数里只有训练终点的损失，没有服务成本。训练算力只花一次，推理算力每个月都在花。一旦把推理摊销算进来，"同损失下参数更小"就值钱了——参数小一档，每一次请求、每一个 Token 都便宜一档。这正是开场 GLM-5 那 712:1 背后的第一股推力（本章第 4 节展开）。

### 5. 边界二：Dense 的分母，不能直接套给 MoE

Chinchilla 的实验对象是 Dense 模型：参数量只有一个口径。MoE 有两个口径，而研究表明最优配比本身会随架构变化。[细粒度 MoE 的 Scaling 律](https://arxiv.org/abs/2402.07871)（2024）给出的方向是：**最优 Token : 激活参数比会随规模上升而下降**——实验范围内 6.4B 激活约 44:1，64T 总参 / 1T 激活时降到约 8:1；同时更高的专家粒度在大算力下更优。

这说明"Token : 参数比"不是普适常数，而是"目标函数 × 架构 × 约束"联合求解的**结果**。GLM-5 按 38:1（总参）和 712:1（激活）双口径披露，正是 2026 年大型 MoE 的标准姿势——单口径报比值，等于没报。

### 6. 边界三：数据不是无限供给的

Chinchilla 隐含"数据想要多少有多少"。现实中高质量数据的供给是受限的。[Epoch AI 在 2024-06 的分析](https://epoch.ai/publications/will-we-run-out-of-data-limits-of-llm-scaling-based-on-human-generated-data)里估计公开人类文本存量约 300T Token，并按当时的 Scaling 趋势外推会在 2026–2032 年间被完全利用（口径：基于当时趋势的外推，不是确定日期）。当"再加数据"变贵，"在已有数据上多训轮次、把模型做小"的经济性就上升了。数据墙本身是下一章的主题，这里只需要记住：它是把最优配比推离 20:1 的第三股力。

### 7. 过度训练：从权宜之计变成常规操作

三股力合起来，诞生了一个专有名词：**过度训练（Overtraining）**——明知偏离训练算力最优配比，仍用远超 20:1 的 Token 数去训一个更小的模型，牺牲一点训练效率，换取更低的推理成本和更小的部署体积。

它在 2026 年已经不是边缘做法。端侧模型 [LFM2.5-350M](https://www.liquid.ai/blog/lfm2-5-350m-no-size-left-behind)（Liquid AI，2026-03）把预训练从 10T 扩到 28T Token，Token : 参数 ≈ 80,000:1（超过 Qwen3-0.6B 在 2025-04 创下的 60,000:1），模型体积 <500MB、32K 上下文；同系 230M 版本也训了 19T Token。对端侧形态来说，"远离 Chinchilla"不是失误，是约束求解的必然。

> **判断边界：**20:1 是"只算一次性训练算力 + Dense + 数据无限供给"这三个假设下的最优解。抄比例之前先问三件事：我的账算到部署了吗？分母是总参还是激活？我的数据预算够把配比推到那里吗？

## 三、训练账：一次训练到底要多少算力

### 1. 第一层：用 6ND 估出 FLOPs

训练账的第一步是把候选方案换算成计算量。用公开数字练一遍（估算为本文所做，非官方披露）：

| 模型 | 口径 | 6ND 估算 |
|---|---|---:|
| GLM-5 | 6 × 40B 激活 × 28.5T | 约 6.8e24 FLOPs |
| Inkling 2 Small H1 预训练 | 6 × 17B 激活 × 8.4T | 约 8.6e23 FLOPs |
| LFM2.5-350M | 6 × 0.35B × 28T | 约 5.9e22 FLOPs |

三个数字连数量级都不同——这就是"训练账"要的第一层答案。注意 MoE 一律用激活参数口径算计算量；总参数在这里不参与计算（它决定显存与加载，是 T05 训练系统章的话题）。

**6ND 意味着什么**：训练算力与参数、Token 都是线性关系。参数翻倍或 Token 翻倍，账单都翻倍；两者都翻倍，账单四倍。没有规模折扣。

### 2. 第二层：从 FLOPs 换算到卡时

FLOPs 是物理量，账单是工程量。中间要过两道换算：

```text
训练 FLOPs
    ÷ (GPU 数 × 单卡峰值算力 × MFU)
    ↓
训练时长
    × GPU 数
    ↓
卡时（GPU-hours） = 训练系统账单的基本单位
    × 你的卡时单价
    ↓
费用
```

**MFU（Model FLOPs Utilization，算力利用率）**可以先理解成：实际跑出来的训练算力 ÷ 硬件理论峰值算力。它衡量训练系统把硬件"喂饱"的程度——通信等待、数据供给、重计算、同步开销都会把它压低。MFU 通常显著低于 100%（具体值强依赖模型形态与并行方案，做预算时应留成区间假设，而不是拍一个数）。

**卡时（GPU-hours）**是"一块 GPU 跑一小时"。它是训练系统的通货：无论用什么型号的卡、什么精度，预算表最终都要落到卡时上才能比价。

用一组示意假设把换算链跑通（数字为教学示意，非任何真实集群）：

```text
已知：训练计算量 C = 1.2e24 FLOPs（方案 B / C 的粗估值）
假设：单卡有效吞吐 = 1e15 FLOP/s（= 单卡峰值 × MFU，教学假设）
      GPU 数 = 1,000，假设吞吐随卡数线性扩展
      集群有效吞吐 = 1,000 × 1e15 = 1e18 FLOP/s

训练时长 = 1.2e24 ÷ 1e18 = 1.2e6 秒 ≈ 333 小时 ≈ 13.9 天
    ↓
总卡时 = 1,000 × (1.2e6 ÷ 3,600) ≈ 333,333 卡时
（使用未取整的时长计算；GPU 数已计入集群吞吐，不能再除一次）
    ↓
费用 ≈ 333,333 × 你的单卡时价格
```

这道例子的重点不是数字本身，而是敏感性：有效吞吐假设减半，天数与卡时都翻倍；MFU 从 45% 掉到 30%，账单就涨 50%。**训练账里最大的不确定性往往不是 6ND，而是你对自己 MFU 的诚实程度。**

### 3. 第三层：估算值与真实账单之间隔着一串乘数

从 6ND 到真实账单，还会经过这些开销（每一项都可能让账单显著高于纸面估算）：

| 开销 | 它吃掉什么 |
|---|---|
| 利用率损耗 | 通信、同步、数据加载让 MFU 低于峰值 |
| 重计算与精度策略 | 用重算换显存、低精度试错，都会改变有效吞吐 |
| 故障与重启 | 长训练必有中断，恢复点之前的进度是沉没卡时 |
| 实验开销 | 消融、超参扫描、中途放弃的 Run，全算在研发账里 |
| 数据管线 | 处理、清洗、回放训练数据的算力常被整块漏算 |

所以训练账的诚实写法是：**FLOPs 是可以复算的，卡时是要靠系统假设的，费用是要留区间的。**

### 4. 可复算示例：Inkling 2 Small 的 H1 账本

[Inkling 2 Small](https://thinkingmachines.ai/news/inkling-2-small)（Thinking Machines，2026-11-05 发布，594B 总参 / 17B 激活 MoE）是目前公开披露最完整的训练账本之一。只看 H1 预训练阶段（口径均为官方披露）：

| 输入项 | 数值 | 口径 |
|---|---|---|
| 激活参数 | 17B | 官方披露，MoE 激活口径 |
| H1 训练 Token | 8.4T | 官方披露，H1 预训练阶段 |
| 硬件 | GB300 NVL72 机架 | 官方披露 |
| H1 时长 | 68 小时 | 官方披露 |
| 精度 | 原生 NVFP4 训练 | 官方披露（配方细节官方称待后续披露） |

用 6ND 粗估 H1 计算量约 8.6e23 FLOPs（本文估算）。这份披露的价值在于四个量（Token × 参数 × 硬件 × 时长）同时公开，外部第一次能把它们互相勾稽——而不是只拿到一个孤立的"我们训了 X T Token"。

对比 GLM-5：披露了 28.5T Token 和双参数口径，但没有披露卡时与硬件账——外部能估到 FLOPs 层（约 6.8e24），停在下探卡时之前。这不是批评：披露是选择，不是义务。但它直接决定"抄比例的人"能复算到哪一层。

> **架构智慧：**训练账的每个数字都有三种身份——官方披露、第三方估算、自己的复算。写进预算表时必须标明是哪一种；同一张表里混用三种口径，是预算评审里最常见的翻车点。

## 四、推理摊销账：训练最优不等于部署最优

### 1. 训练花一次，推理天天花

推理的每个生成 Token 大约需要 2N 量级的计算（粗口径，忽略 Prefill 与缓存差异），训练是每 Token 约 6N、但只发生一次。做一个只看数量级的粗估（示意推导）：

```text
训练总算力 ≈ 6 × N × D          （一次）
推理累计算力 ≈ 2 × N × Q        （Q = 服务生命周期内累计生成的 Token 数）

两者相等的临界点：Q ≈ 3D
即：累计服务 Token 超过训练 Token 的约 3 倍后，
推理侧的累计算力开销超过训练侧
```

D = 10T 的模型，临界点是累计服务约 30T Token——一个日均 10B 生成 Token 的服务约 8 年跨过；日均 100B 生成 Token 的服务（大规模 Agent 负载就在这个量级方向）约 10 个月跨过。**请求量越大、服务周期越长，"训练最优"就越要让位于"部署最优"。**

### 2. 每笔请求的账：被低估的三个变量

| 变量 | 为什么常被低估 |
|---|---|
| 请求量与累计 Token | 训练账是"一笔"，推理账是"速率 × 时间"，随业务增长复利式膨胀 |
| 采样次数 | 推理模型一次回答要生成完整思考链；多次采样、投票再翻倍 |
| 多轮 Agent 交互 | 一个任务几十轮工具调用，每请求 Token 数比聊天大几个量级 |

第三条有真实刻度：Inkling 2 Small 披露的 RL 训练中，单条 Rollout 的 Token 数 p50 = 43K、p99 = 1.5M，时长 p50 8 分钟、p99 4 小时（口径：RL Rollout 统计）。这是训练侧的采样负载，但同一批模型上线服务 Agent 任务时，用户侧请求的 Token 形态与之同构——**部署形态决定"每请求"有多重**。

推理经济性也直接体现在价格上（口径：官方 API 公开标价，每百万 Token，输入 / 输出）：

| 模型 | 输入 | 输出 |
|---|---:|---:|
| GLM-5 | $1.0 | $3.2 |
| Kimi K3 | $3 | $15 |

同为 2026 年的大型 MoE，每 Token 价差 3–5 倍。差距的一部分就能追溯到激活参数与部署账的差别——推理账不是训练的"尾巴"，而是独立的一等变量。

### 3. 回到开场的 B 与 C：同一笔训练预算，两本推理账

本章第 1 节的场景里，方案 B（100B @ 2T，20:1）和方案 C（30B @ 6.7T，约 220:1）的训练算力粗估相同（各约 1.2e24 FLOPs）。按 Chinchilla 的标准，C 是"错的"——它严重过度训练。但把推理账摆进来（示意推导，负载取场景值：月均 1 亿次请求 × 每请求 5K Token = 5e11 Token / 月）：

| 账项（示意粗估） | 方案 B（100B） | 方案 C（30B） |
|---|---:|---:|
| 训练算力（6ND，一次） | 约 1.2e24 FLOPs | 约 1.2e24 FLOPs |
| 每 Token 推理计算（约 2N） | 2e11 | 6e10 |
| 月推理算力（5e11 Token） | 约 1e23 FLOPs | 约 3e22 FLOPs |
| 18 个月推理累计算力 | **约 1.8e24 FLOPs** | 约 5.4e23 FLOPs |

三件事同时成立：

- **B 的 18 个月推理累计算力（约 1.8e24）超过了它自己的整个训练 Run（约 1.2e24）**——"训练是大头"的直觉在高请求量下失效；
- C 的推理账只有 B 的三分之一，且这个差距**每个月都在产生**；
- 代价是 C 的训练配比偏离算力最优——它用"训练阶段的低效"换"部署阶段的高效"。

哪个划算？答案取决于请求量与服务周期——这正是下一小节 T² 把采样也算进来之后，给出的系统性解法方向。

### 4. T² Scaling：把测试时采样算进预算再解一次

**Test-Time Scaling**指推理时多采样、多思考来换正确率。问题在于：采样也是算力。如果预算同时覆盖训练与推理采样，最优的 (N, D, 采样次数 k) 组合会怎么变？

[T²（Train-to-Test）Scaling](https://arxiv.org/abs/2604.01411)（Roberts 等，2026-04 提交的预印本）研究了这个问题：在固定端到端算力预算下，把模型规模、训练 Token 与推理采样次数（以 pass@k 建模）联合优化，在 8 个下游任务上得到一致的结论——**一旦计入推理成本，最优预训练配比大幅移入过度训练区间**，远超常规 Scaling 实验覆盖的范围；作者还按 T² 预测的区间实际预训练了重度过度训练的模型，验证其更强，且结论在后训练之后仍然成立。

它在此处的教学生命力在于方法而非数字：**先写清楚预算的边界（含不含推理），再解最优配比**。预算边界一变，答案就变——这解释了为什么不同团队拿着相同的论文却做出相反的规模决策。

### 5. 架构也进账本：推理感知 Scaling

更早的一步是把架构本身纳入与 Chinchilla 同型的联合优化。[Scaling Inference-Efficient Language Models](https://arxiv.org/abs/2501.18107)（ICML 2025）训练了 63 个模型（80M–1B 参数 / 1.6B–30B Token），发现**同参数量的模型推理延迟可以差 3.5 倍**，修改后的 Scaling 律在参数、Token 之外把架构（宽浅结构占优）作为第三根轴，产出的 Morph-1B 在精度持平下把推理延迟改善了 1.8 倍（口径：论文报告的实验结果）。

一句话：推理账不只是"多大模型 × 多少 Token"，架构与采样策略都在改写这本账的汇率。

> **判断边界：**离线基准的最优是"单次采样精度最优"，业务的最优是"单位成本的任务完成率最优"。两个目标在低请求量时几乎重合，在请求量放大后逐步分道——评审规模方案时，必须先声明在优化哪一个。

## 五、研发账：最终训练 Run 不是全部成本

### 1. 你看到的那个 Run，只是冰山露出的部分

走到"744B 参数 × 28.5T Token"这一步之前，同一批算力已经花在：

| 研发开销 | 典型内容 |
|---|---|
| 数据实验 | 配比扫描、清洗管线验证、质量评估 |
| 结构与超参试验 | 架构候选对比、学习率与批大小搜索 |
| 消融实验 | 每个组件"有没有用"的受控验证 |
| 失败与废弃的 Run | Loss 发散、中断、被放弃的分支 |
| 后训练 | SFT、偏好、RL 的 Rollout 与训练（本身就是算力大户） |
| 评测 | 基准、人工评估、回归测试 |

### 2. Epoch AI 的估算：最终 Run 只占研发算力的少数

[Epoch AI 的分析](https://epochai.substack.com/p/final-training-runs-account-for-a)（2026-03）估算了 OpenAI、Z.ai、MiniMax 三家的研发算力结构：**最终训练 Run 只占研发算力总支出的少数**——OpenAI 约 9.6%（对应约 $5B 的年研发算力支出对约 $0.5B 的最终 Run），另一家约 22.6%；最终 Run 的算力自 2016 年以来约以每年 2.4 倍增长（95% CI 2.0–3.1）。

用这个口径换算：**"训练一个模型的成本"如果只算最终 Run，会系统性低估约一个数量级**（1 ÷ 9.6% ≈ 10 倍；1 ÷ 22.6% ≈ 4.4 倍）。

两个纪律必须跟上：

- 9.6% / 22.6% 是**算力支出估算**（compute spending estimate）口径，不是实际 FLOPs 占比——支出混合了不同年份的采购价格与方式；
- 它是三家实验室的估算，不是行业常数，不能推广成"所有公司都乘十"。

乘数在预算表里的正确用法是区间与方向，不是精确系数：

| 用法 | 例子（示意） | 评价 |
|---|---|---|
| 错误用法 | "最终 Run 要 1 万卡时，所以研发预算 = 1 万 × 10 = 10 万卡时，精确到个位" | 伪精确；乘数本身是支出估算的换算 |
| 正确用法 | "研发预留 = 最终 Run 的 4–10 倍区间；我们的实验纪律更好，取 4–6 倍，并按预测台账逐季回填校准" | 把乘数当成会被经验修正的先验 |

还有一个常被漏掉的细节：乘数不是常数。团队成熟、数据管线复用好、失败 Run 少，乘数往下走；换架构、换 Tokenizer、开新能力线，乘数往上走。它是团队工程纪律的函数。

### 3. 案例拆解：Inkling 2 Small 的完整账本长什么样

研发账"全貌"稀缺，正因为稀缺，Inkling 2 Small 的分阶段披露值得整表读一遍（口径均为官方披露，2026-11-05 页面）：

| 阶段 | 内容 | 关键数字 |
|---|---|---|
| 模型 | 594B 总参 / 17B 激活 MoE | — |
| H1 预训练 | 8.4T Token | GB300 NVL72 机架，68 小时，原生 NVFP4 |
| H2 | 3.8T 未见过的更高质量新数据 | 512K 上下文 |
| H3 | 约 320B Token 推理 + Agent 轨迹 | 1M 上下文 |
| H4 | 约 34B Token 最高质量轨迹 | 主要采样自 Kimi K3 及自家早期模型，经正确性与对齐过滤 |
| RL | 单次联合 RL Run | 1,075 步、超 17M Rollout、9 天；sampler : trainer = 5 : 3；前缀缓存命中 93%+ |

这张表至少改写三个直觉：

- **后训练有大账**：RL Run 跑了 9 天，且采样与训练的算力配比（sampler : trainer = 5 : 3）意味着推理侧开销比训练侧还大——研发账里"训练之外"的部分可能相当可观；
- **轨迹数据本身要花钱生成**：H3 + H4 合计约 354B Token 的轨迹不是下载来的，是算力换来的；
- **工程决策直接改写账本**：前缀缓存命中 93%+ 这一项，决定了那 17M 次 Rollout 的实际成本——同一个算法决策，配上不同的缓存策略，账单不同。

一个必要的限定：官方页面同时表示权重需待外部安全测试后发布（截至 2026-11-05）。**账本透明与权重可得是两件事**，这份案例支撑的是"研发账长什么样"，不承诺"权重现在就能下载部署"。

### 4. 披露分层：你抄的配比，别人到底披露了多少

把 2026 年三个高关注度模型放在一起，能看到清晰的披露光谱：

| 模型 | 权重 | 参数口径 | 训练 Token | 卡时 / 硬件 | 外部能复算到哪层 |
|---|---|---|---|---|---|
| Kimi K3 | 开放权重 | 2.8T 总参、896 专家选 16（官方） | 未披露 | 未披露 | 不可复算 |
| GLM-5 | MIT 开放 | 744B / 40B 披露 | 28.5T 披露 | 卡时未披露 | 可估 FLOPs，估不了卡时 |
| Inkling 2 Small | Apache 2.0（权重待安全测试后发布） | 594B / 17B 披露 | 分阶段披露 | 硬件 + 时长披露 | 三本账可勾稽 |

Kimi K3 官方博客声称"较 Kimi K2 总体 Scaling 效率约提升 2.5 倍"（[官方博客](https://www.kimi.ai/blog/kimi-k3)，2026-07-16；厂商声称口径）——在训练 Token 与卡时未披露的情况下，这个倍数外部无法独立复算。**开放权重不等于开放账本**：权重让你能部署，账本才让你能学习它的预算决策。

### 5. 时间维度：比例会随时间贬值

[Epoch AI Trends](https://epoch.ai/trends)（2026-02-05 更新）的数据给研发账加了时间轴：前沿语言模型训练算力自 2020 年起约每年 5 倍增长（90% CI 4–6 倍，翻倍周期约 5.2 个月），前沿训练成本约每年 3.5 倍（翻倍约 7 个月）。

这意味着：去年抄的配比与成本结构，今年的账已经变了。任何"参照某模型"的预算决策都必须写上核查日期，并预期它在一年内失效。

> **架构智慧：**能抄的是别人的结果，不能抄的是别人的约束——你看不到他们的失败 Run、数据实验和采样账。研发账的存在本身，就是"不要照抄比例"的经济学证明。

## 六、部署形态倒推模型选择

### 1. 五种部署形态，五本不同的推理账

| 部署形态 | 硬约束 | 对规模决策的直接含义 |
|---|---|---|
| 云端高并发 API | 吞吐与单 Token 成本 | 摊销账主导；更小激活 + 更多 Token（过度训练）往往占优 |
| 低延迟在线服务 | 首 Token 延迟 | 参数与架构被延迟预算倒推（推理感知 Scaling 的主场） |
| 端侧 / 设备 | 体积、内存、离线运行 | 模型体积上限直接锁死参数规模；配比可达数万 : 1 |
| 本地私有化 | 客户硬件与许可证 | 总参数 = 显存口径；量化友好性成为一等变量 |
| Agent 长程多轮 | 每请求 Token 量爆炸 | 上下文与采样成本主导；每请求成本比参数量更关键 |

端侧是"形态倒推规模"最纯粹的例子：LFM2.5-350M 的 80,000:1 配比不是从 Scaling 曲线上优雅推出的，而是从"<500MB、离线可跑"这条硬约束反推回来的——体积上限锁死参数，剩余预算全部换成 Token。

### 2. 一个最小的倒推算例：体积上限如何锁死参数

权重体积 ≈ 参数量 × 每参数字节数（粗口径，不含嵌入共享、缓存与运行时开销）：

| 精度 | 每参数约 | 1B 参数的权重体积 | 500MB 上限容得下的参数 |
|---|---:|---:|---:|
| FP16 | 2 字节 | ≈ 2GB | ≈ 250M |
| 4-bit | 0.5 字节 | ≈ 0.5GB | ≈ 1B |

这就解释了 LFM2.5-350M 的选择空间：要压进 <500MB，参数只能落在数百 M 量级；而几百 M 参数想要够用的能力，Token 只能往数万倍配比上堆（28T ÷ 350M ≈ 80,000:1）。**部署形态先给出不等式，Scaling 决策在里面找最优点。**

### 3. 倒推链：从业务目标到训练配比

```text
业务目标：请求量、延迟、可接受单价、服务周期
    ↓
每请求平均 Token（输入 + 输出 × 采样次数）
    ↓
生命周期累计推理 Token → 推理摊销账
    ↓
单 Token 成本上限 → 参数规模上限 × 量化方案 × 架构取向
    ↓
参数规模确定后 → 训练 Token 配比（过度训练到什么程度）
    ↓
回填三本账：训练账 / 推理摊销账 / 研发账
    ↓
候选方案之间比总账，而不是比参数量
```

注意这条链的方向：**不是"选一个多大的模型然后看能不能部署"，而是"部署约束先说话，规模是解出来的"**。这也是引言八层坐标系里第①层（能力目标与任务形态）先于第⑦层（系统与资源）的原因——方向反了，每一层都会替你做出你没批准的决定。

> **判断边界：**权重开放、训练透明、可自部署是三个独立命题。Inkling 账本全开但权重待发布；K3 权重开放但账本未开。决定"参照谁"之前，先确认自己要借的是哪一层：借部署（要权重）、借方法（要账本）、还是借结论（要克制）。

## 七、实验设计：怎么验证你的 Scaling 决策

### 1. 小规模外推的标准做法

没人能用目标规模的实验来选目标规模——成本上不允许。标准做法是外推：

```text
用小算力跑一组 isoFLOP 实验（固定预算，扫描 N:D 分配）
    ↓
拟合"算力 → 最优参数 / 最优 Token"的幂律关系
    ↓
外推到目标算力，得到候选 (N, D)
    ↓
按预测实际训练，回填预测台账
```

外推的可靠性与距离强相关：拟合区间内是推算，拟合区间外是赌注。两者的分界必须写进决策记录。

### 2. 正面教材与它的边界：Q Labs 的数据受限 Scaling

[Q Labs / NYU / Princeton 的数据受限 Scaling 研究](https://arxiv.org/abs/2610.37842)（2026-10-27）展示了规范的外推纪律。它把处方分级（口径：论文实验设置）：

| 层级 | 内容 | 状态 |
|---|---|---|
| 已验证 | FineWeb 100M Token 上，迁移学习率 / 权重衰减 + 引入 ensemble 作第三扩展轴，较既有处方验证损失降 0.15+ nats（困惑度约 -14%） | 论文实验结果 |
| 部分验证 | 处方在 12 倍更大算力上仍有效 | 论文实验结果 |
| 纯外推 | 固定 5T Token + 1e29 FLOPs 时，算力最优参数量约为 Chinchilla 处方的 7000 倍（集成总参约 1.75Q） | 基于 ≤400M 参数实验的拟合外推，论文自身已标注 |

读研究结论时保持这三个层级的语感，是从"论文"到"预算"的必要翻译。T² 论文的作者同样如此：不只拟合曲线，还按预测区间实际预训练了过度训练模型来验证——**预测要配上用真金白银的验证**，这是 Scaling 决策区别于学术拟合的关键一步。

### 3. 控制变量与置信区间

- **控制变量**：比较 (N, D) 组合时固定总预算；比较架构时固定 (N, D)；同时动两个变量得到的"提升"，无法归因。
- **重复运行**：小实验的随机方差会污染幂律拟合，关键拐点附近需要多种子确认。
- **置信区间**：外推值必须带区间（如 Epoch 对增长率的 90% CI 写法），单点预测是伪精确。

### 4. 什么时候必须重跑外推

Scaling 曲线不是一次拟合、终身有效。三类变化会让旧处方失效：

| 变化 | 为什么动摇外推 |
|---|---|
| 换架构或专家粒度 | 本章第 2 节的边界二：Dense 上拟合的最优配比不自动迁移到 MoE；粒度变了，曲线本身变形 |
| 换数据分布 | 配比是"这份语料"上的最优；数据配方大改，曲线重画（下一章展开） |
| 换精度或硬件 | 精度与互联改变了"每 FLOP 的有效性"，等效算力与账单同时变 |

原则：外推处方要写有效期——架构、数据、精度任一换代，先小规模复验拐点，再继续外推。

### 5. 工程落点：预测台账

这是引言第⑧层（晋级证据）在预算决策上的最小实现。每个规模决策记录四列：

| 决策 | 预测 | 实际 | 偏差原因 |
|---|---|---|---|
| 中间损失 @ 50% 进度 | 2.41 | 2.44 | 数据配比在第 3 周调整过一次 |
| 端到端卡时 | 120K 小时 | 158K 小时 | 两次集群故障重启，MFU 低于假设 |

（行为示意。）台账的价值不在预测准——外推本来就会错——而在**让每一次偏差变成下一次预算的先验**。没有台账的团队，每年都在用同样的误差重训同样的惊讶。

> **判断边界：**外推分级（已验证 / 部分验证 / 纯外推）不是学术洁癖，是风险披露。预算表里每一个来自论文的数字，都该标注它属于哪一级。

## 八、决策总结：把三本账合成一本

### 1. 合并视图

```text
预算 B（算力或美元）
    ├─ 训练账：6 × 激活参数 × 训练 Token → FLOPs → 卡时 → 一次性投入
    ├─ 推理摊销账：请求量 × 每请求 Token × 单价 × 服务月数 → 周期性投入
    └─ 研发账：最终 Run × 试验乘数（约 4–10 倍，支出估算口径锚定）→ 隐藏投入
        ↓
约束过滤：部署形态 / 延迟 / 数据可得性 / 团队实验纪律
        ↓
决策输出：总参数与激活参数、训练 Token、采样预算、量化与硬件方案
        ↓
验证闭环：isoFLOP 外推 → 预测台账 → 复盘并更新乘数
```

### 2. 规模与预算决策表

把本章的推导压缩成一张速查表（倾向为方向性指引，最终以三本账复算为准）：

| 部署形态 | 请求量 | 预算姿态 | 规模倾向 |
|---|---|---|---|
| 云端高并发 API | 大 | 训练预算相对充足 | 更小激活 + 更多 Token（摊销账主导） |
| 云端低流量服务 | 小 | 一次性 | 可靠近 Chinchilla 配比（摊销压力小） |
| 低延迟在线 | 中–大 | 延迟硬约束 | 参数与架构由延迟预算倒推 |
| 端侧 / 设备 | — | 体积硬上限 | 极小模型 + 极端过度训练 |
| 本地私有化 | 中 | 客户硬件受限 | 中小规模、量化友好的结构 |
| Agent 长程 | 每请求 Token 极大 | — | 上下文与采样成本主导，参数反而其次 |

### 3. 回到开场：三个方案的总账裁决

现在可以回答第 1 节的三选一了。把三本账的粗估放在一起（示意推导，延续场景负载：月 5e11 Token，18 个月）：

| 方案 | 训练账（一次） | 每 Token 推理计算（约 2N） | 18 个月推理累计算力 | 研发账风险 | 适配的部署故事 |
|---|---:|---:|---:|---|---|
| A：700B 总参 / 40B 激活 MoE | 约 6.7e24 | 8e10 | 约 7.2e23 | 高：MoE 路由与训练系统的试验负担通常更重（定性判断） | 请求量大、要最强能力、训练预算充足 |
| B：100B Dense @ 20:1 | 约 1.2e24 | 2e11 | **约 1.8e24** | 中：配比贴近教科书参照 | 低请求量、一次性训练预算紧 |
| C：30B Dense @ 220:1 | 约 1.2e24 | 6e10 | 约 5.4e23 | 中低：配比偏离最优，需要实验验证能力补得回来 | 高请求量、延迟敏感、能力要求可由过度训练加采样补齐 |

三个结论值得写进决策记录：

- **B 的推理账（约 1.8e24）超过它的训练账（约 1.2e24），也是三个方案里推理最贵的**——训练最优的配比，在这个负载下是部署最差的选择之一；
- **A 与 C 的每 Token 成本都低于 B**：A 用"总参买容量、激活买便宜推理"的 MoE 结构，C 用极端过度训练。本章引用的 2026 案例正好展示了这两种"远离 20:1"的形态——大型 MoE（GLM-5、Kimi K3、Inkling 2 Small）与端侧重度过度训练（LFM2.5 系列）——而在本章引用的高请求量案例里，贴近 20:1 的中档 Dense 没有出现；
- **裁决不是"C 赢"**：C 的每 Token 成本与 A 同档、训练账只有 A 的约五分之一，但它的能力上限风险（仓库级代码任务）与首 Token 延迟优势需要本章第 7 节的实验去验证；A 的能力天花板最高，但训练账和研发乘数也最重。**三本账给出的是"每个方案的账单"，不是"唯一正确答案"——答案还要过能力目标与实验验证两道门。**

## 九、六种最常见的错误判断

### 错误 1：把 20:1 当成跨模型通用配方

Chinchilla 的 20:1 是 Dense + 一次性训练 + 数据无限供给三重假设下的结论。MoE 要换分母（总参 / 激活差一个量级），部署要换目标函数，数据受限要换约束。GLM-5 的 38:1 与 712:1 同时"远离 20:1"却并不矛盾——比例是求解结果，不是输入参数。

### 错误 2：只算训练账，不算推理摊销账

训练是一次性支出，推理是速率 × 时间。累计服务 Token 超过训练 Token 约 3 倍（粗口径）后，推理算力就超过训练。高请求量下省下的训练钱，几个月就会被推理账单吃回去。

### 错误 3：拿最终 Run 的成本当整个研发成本

Epoch 对三家的估算显示最终 Run 只占研发算力支出的少数（9.6%–22.6%，支出估算口径），只算它等于把预算系统性低估约一个数量级。数据实验、失败 Run、后训练 Rollout 都在你的卡上。

### 错误 4：抄参数量和配比，不抄约束

K3 未披露 Token 与卡时，连"抄"的对象都不完整；GLM-5 披露 Token 但无卡时；Inkling 全账本但你没有它的数据管线与团队。比例是"目标函数 × 架构 × 约束"的解，约束不同，同一个解就是错的。

### 错误 5：把离线榜单最优当业务最优

单次采样的基准分数不含延迟、单价与采样预算。T² 与推理感知 Scaling 的全部出发点就是：预算边界一变（计入推理），最优配比就大幅移动。评审时先声明在优化哪个目标。

### 错误 6：把权重开放当训练透明、当可自部署

三个独立命题。权重开放让你能部署（还得看体积、量化与许可证）；账本透明让你能学习决策；能否自部署取决于硬件与工程。Inkling 账本全开而权重待发布，K3 权重开放而账本未开——两者都提醒你别把三件事打包成一句"开源"。

## 本章小结

- **Scaling 比例是结果，不是配方。**Chinchilla 的约 20:1 只在"Dense + 一次性训练 + 数据无限"的假设下成立；MoE 双口径、推理摊销与数据受限都会把最优配比推离它。
- **MoE 必须双口径记账。**总参数对应显存与容量，激活参数对应计算量；单口径报比值等于没报。
- **训练账走 6ND 粗估，再换算卡时。**披露分层决定你能复算到哪一层：Token 与参数可估 FLOPs，加上硬件与时长才能勾稽卡时。
- **推理摊销账常常大于训练账。**累计服务 Token 约达训练 Token 的 3 倍（粗口径）后，推理累计算力超过训练；请求量与采样次数是放大器。
- **研发账约等于最终 Run × 乘数。**Epoch 对三家的估算给出 4–10 倍量级（支出估算口径），方向明确，比例不可硬抄。
- **部署形态倒推规模，而不是反过来。**端侧的 80,000:1 与云端 API 的小激活偏好，都是约束解出来的。
- **外推要分级，预测要台账。**已验证 / 部分验证 / 纯外推必须分开标注；每次决策回填预测、实际与偏差原因。
- **三本账合成一本才叫决策。**产出物是一张口径清晰、别人能复算挑错的 Training Budget Calculator。

> **下一章的问题：**预算确定后，下一步不是直接选模型结构，而是判断：有限的数据预算应该投向哪些数据，才能换来目标能力？

## 基础术语速查

| 术语 | 初学者可以先怎样理解 |
|---|---|
| Chinchilla 最优 | 2022 年论文给出的结论：只算一次性训练算力时，Dense 模型的算力最优 Token : 参数比约 20:1；它是训练终点的最优，不是部署最优 |
| isoFLOP 实验 | 固定训练算力、只改变参数与 Token 的分配比例，比较哪组终点损失最低，用来找最优配比 |
| 过度训练（Overtraining） | 明知偏离训练算力最优，仍用远超配比的 Token 训练更小的模型，牺牲训练效率换更便宜的推理与更小的体积 |
| 推理感知 Scaling | 把推理成本（延迟、架构、采样）与训练成本放进同一个优化目标来决定模型规模 |
| Test-Time Scaling / T² | 推理时多采样、多思考换正确率；T² 指训练预算与测试时采样预算的联合优化 |
| 6ND 粗估 | 训练总算力 ≈ 6 × 每 Token 参与计算的参数 × 训练 Token 数的工程粗估规则 |
| MFU | 实际训练算力 ÷ 硬件理论峰值，衡量训练系统把硬件喂饱的程度 |
| 卡时（GPU-hours） | 一块 GPU 运行一小时；算力需求换算成资源与账单的基本单位 |
| 摊销账 | 把一次性投入（训练）与周期性投入（推理）放进同一服务周期比较的记账方式 |
| 研发算力占比 | 最终训练 Run 在全部研发算力支出中的比例；注意是支出估算口径，不是 FLOPs 占比 |
| 总参数 / 激活参数 | MoE 的两个参数口径：总参数对应容量与显存，激活参数对应每个 Token 的实际计算量 |
| 账本披露分层 | 权重、参数口径、训练 Token、卡时逐层披露的程度差异；开放权重不等于开放账本 |
