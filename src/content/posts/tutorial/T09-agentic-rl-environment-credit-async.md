> **长程 Agent 训练必须把环境重置、轨迹归因和策略新鲜度一起纳入系统设计。**

读完可以为工具交互任务写一份环境规格，并定位环境、奖励归因或异步调度的瓶颈。

[专题地图](/tutorial/t01-introduction-map/) · 可独立阅读；文末有本章决策练习。

## 开场：同一台 RL 机器，为什么跑不动一个真实仓库

先把两个现场并排放。

**现场一（T08 的主场）**：数学 RLVR。模型收到一道题，生成一条几千 Token 的推理与答案，验证器比对标准答案，几秒钟内给出 0/1 奖励。一次采样=一次生成；任务之间互相独立；环境不存在——或者说，环境就是"题目+验证器"这层薄纸。

**现场二（本章的主场）**：修复一个真实仓库里的 GitHub issue。模型要克隆仓库、读代码、定位嫌疑文件、改代码、跑测试、读报错、再改——几十步工具调用，每一步都在改变环境状态（文件系统、测试结果、终端里的进程）；奖励只在最后才揭晓：测试通过与否。一条轨迹走完需要多久？[Inkling 2 Small 的 RL 账本](https://thinkingmachines.ai/news/inkling-2-small)给了一个真实刻度：单条 Rollout 的 Token 数 p50 = 43K、p99 = 1.5M，时长 p50 约 8 分钟、p99 约 4 小时（口径：官方披露的 RL Rollout 统计）。**它意味着什么**：同样叫"采一条样本"，RLVR 的样本是"一次生成"，Agentic 的样本是"一段带副作用、耗时几分钟到几小时的历史"。

很多团队的第一个动作，是把 T08 的 RLVR 训练计划原样拿来，换上一批更难的任务清单。然后训练循环在三个地方依次断裂：

- **环境断裂**：几十个并发 Rollout 同时改文件、跑测试，环境互相污染、随机崩溃，一半轨迹死于环境故障而不是策略错误；
- **归因断裂**：奖励只在结局出现，60 步轨迹里错误可能发生在第 5 步，也可能在第 55 步，"同题一组规整可比轨迹"的前提也不再自然成立；
- **吞吐断裂**：一条轨迹 8 分钟起步、长尾 4 小时，同步训练让 GPU 大部分时间在等最慢的那条轨迹收尾。

三个断裂各属于不同的坐标系层，也因此各有各的解法：

```text
环境断裂 → 第②⑥⑦层：环境资产 + 隔离组件 + 拓扑（第 1、5、7 节）
归因断裂 → 第④层：信用分配选型（第 3 节）
吞吐断裂 → 第⑦层：异步拓扑与调度（第 4 节）
```

> **本章只解决一件事：如何构建可训练的 Agent 环境，并把长程交互转化为稳定、可扩展的学习信号？**

本章的推导路线：

```text
第 1 节   环境是一等训练资产（四件套、隔离、可复现）
    ↓
第 2 节   从任务到轨迹（Observation/Action/Compaction/可回放）
    ↓
第 3 节   奖励与信用分配（主案例：GLM-5.2 转 critic-based PPO）
    ↓
第 4 节   异步训练拓扑（On-policy/Policy Lag/前缀缓存）
    ↓
第 5 节   环境吞吐与训练经济性（每条有效轨迹的成本）
    ↓
第 6 节   Agentic RL 的评测（成功率之外与环境隔离）
    ↓
第 7 节   端到端架构推导（一个软件工程 Agent 的数据流）
    ↓
第 8 节   工程产物：Agent Environment Specification
```

先用一张表把 T08 与本章的决策现场分开：

| 判断层 | RLVR（T08） | Agentic RL（T09） |
|---|---|---|
| 最小训练材料 | Prompt + 同题多条 Rollout + Reward | 多轮交互轨迹 + 环境反馈 + Reward |
| 奖励时点 | 生成结束即验证 | 通常只在任务终态（也可能有过程信号） |
| 环境的角色 | 几乎不存在（题目+验证器） | 一等训练资产：状态、工具、重置、隔离 |
| 轨迹形态 | 一次生成、长度同量级 | 几十步工具调用、长度差一个数量级以上 |
| 系统重心 | 组完整性、防投机 | 环境吞吐、Policy Lag、每条轨迹成本 |

> **架构智慧：**把 Agentic RL 理解成"换一批更难的任务清单"，等于把一场话剧演出当成了换剧本——真正新增的工程对象是舞台本身：环境、轨迹、异步编排。任务清单只是环境这个资产最表层的部分。

## 一、环境是一等训练资产

### 1. 环境的四件套定义

2026 年的工程讨论里，"RL 环境"已经收敛成一个相当具体的定义：**任务 + 测试 + 容器 + 奖励规则**（定性观察，来自 2026-09 前后的行业博文叙事）。拆开看：

- **任务**：初始状态与目标描述（一个 issue、一张网页操作指令、一个数据查询请求）；
- **测试**：判定终态是否达成的方式（单元测试、端到端断言、页面状态检查）；
- **容器**：任务运行所在的隔离空间（Docker 容器、虚拟机、microVM）；
- **奖励规则**：把测试结果、过程约束（步数上限、违规操作）映射成分数。

对照[GLM-5 技术报告](https://arxiv.org/abs/2602.15763)（2026-02）披露的 agentic 环境三件套，能看到这个定义不是抽象推演：**真实 issue-PR 对**（任务+测试都来自真实仓库历史）、**Docker 化终端**（容器）、**web 知识图谱**（另一类任务源）。同一份报告给出的成绩是 SWE-bench-Verified 77.8、Terminal-Bench 2.0 得分 56.2（口径：报告披露值，发布时为开源模型最高）——注意这里的基准版本是 TB 2.0，第 6 节会专门讲为什么版本号必须跟着分数走。

### 2. 环境规格的七个面

把"环境"当成一个可以写规格的工程对象，它至少有七个必须回答的面：

```text
┌──────────────────────────────────────────────────┐
│ Agent 环境                                         │
│                                                    │
│  ① 任务定义      任务从哪来、难度如何分层          │
│  ② 初始状态      每次重置后环境长什么样            │
│  ③ 工具接口      模型能调用什么、参数与返回格式    │
│  ④ 权限边界      哪些操作被禁止、越界如何处置      │
│  ⑤ 重置机制      轨迹结束后如何恢复到干净状态      │
│  ⑥ 终止条件      何时判定成功/失败/超时            │
│  ⑦ 奖励与验证    终态怎么测、过程约束怎么罚        │
└──────────────────────────────────────────────────┘
```

第 ④⑤ 两个面最容易被任务清单思维漏掉。权限边界不写清，模型可能学会用 `rm -rf` 让测试"无法运行"从而绕开失败判定；重置机制不严格，上一条轨迹改过的文件会漏进下一条轨迹，学习信号从此混入环境噪声。把七个面压成一张评审表：

| 面 | 关键问题 | 不写的典型后果 |
|---|---|---|
| ① 任务定义 | 任务从哪来、难度怎么分层 | 任务全堆在模型刚好做不出的难度带上，奖励恒 0，训练空转 |
| ② 初始状态 | 重置后环境长什么样 | 初始状态随机漂移，"同题可比"从源头失效 |
| ③ 工具接口 | 有哪些工具、参数与返回格式 | 模型学到调用习惯本身，换一套工具名能力归零 |
| ④ 权限边界 | 哪些操作被禁止、越界怎么罚 | 模型发现"让测试跑不起来"比"修好代码"更容易得分 |
| ⑤ 重置机制 | 轨迹结束后如何恢复干净 | 上一条的改动漏进下一条，环境噪声混入学习信号 |
| ⑥ 终止条件 | 何时判成功/失败/超时 | 超时策略缺位，长轨迹无限占住 Worker |
| ⑦ 奖励与验证 | 终态怎么测、过程怎么罚 | 奖励规则改版后旧轨迹混用新规则，实验不可比 |

### 3. 重置的三种实现与代价

第 ⑤ 个面值得单独展开，因为它是"环境账"里最稳定的一笔开销。重置有三种主流实现：

| 重置实现 | 做法 | 优势 | 代价 |
|---|---|---|---|
| 重建 | 每条轨迹从镜像全新启动 | 最干净，无残留风险 | 启动开销=每条轨迹的固定税 |
| 快照恢复 | 轨迹开始前打快照，结束即回滚 | 恢复快，秒级 | 存储成本；快照覆盖不到的副作用（外部网络调用）仍会残留 |
| 模板克隆 | 以 microVM 模板秒级克隆新实例 | 干净且快，one-sandbox-per-rollout 的载体 | 需要模板版本管理，模板老化是新的漂移源 |

注意快照恢复的一个盲区：工具调用如果在环境之外留下了痕迹（外部 API 的副作用、远端仓库的提交），快照回滚不掉——这类"环境外副作用"要么在任务协议里禁止，要么在验收时显式检查。状态残留检查应该成为环境上线前的一道固定门禁：跑一条已知会乱改环境的轨迹，重置后逐项比对初始状态。

### 4. 真实、模拟、合成：三种环境来源的取舍

| 环境来源 | 典型例子 | 优势 | 代价 |
|---|---|---|---|
| 真实环境 | 真实 issue-PR 对、真实网站 | 分布最接近上线场景 | 状态不可控、重置难、可能有版权与隐私问题 |
| 模拟环境 | 本地克隆的服务、回放的网页快照 | 可重置、可复现、便宜 | 与真实世界有分布差，模型可能学到"模拟器专用技巧" |
| 合成环境 | 程序生成的任务家族（注入 bug 再要求修复） | 任务量近乎无限、难度可控 | 任务分布窄，容易过拟合到生成模板 |

GLM-5 的"真实 issue-PR 对"选择真实路线，代价是要处理真实仓库的多样性与噪声；合成路线的典型风险则相反——注入式 bug 的修法可能收敛成模板匹配。三条路线不是单选，同一套训练里混合使用是常态；真正要写进决策记录的是各自占比与验收方式——尤其要为每种来源单独设一组"留出任务"：模拟器技巧与模板过拟合只有在对各自来源的留出集上才暴露得出来，混在一个总分里它们都被平均掉了。

### 5. 隔离层级：从共享容器到 one-sandbox-per-rollout

几十路 Rollout 并发执行时，隔离层级直接决定"状态污染"的概率：

| 隔离方案 | 启动开销 | 隔离强度 | 典型问题 |
|---|---|---|---|
| 共享容器/共享文件系统 | 最低 | 弱 | 一条轨迹修改影响另一条，学习信号被污染 |
| 每任务一个容器 | 秒级 | 中 | 同任务内多次 Rollout 仍互相干扰 |
| 每条 Rollout 一个沙箱（one-sandbox-per-rollout） | 取决于实现 | 强 | 沙箱启动成本必须压到可忽略 |
| VM / microVM | 传统 VM 分钟级；microVM 秒级 | 最强 | 资源与管理复杂度上升 |

2026-09 的工程讨论把"每条 Rollout 独占一个沙箱"收敛成了明确口号（博文叙事，2026-09-11，标题即 one-sandbox-per-rollout），配套的硬件方向是 microVM 沙箱——用秒级启动的轻量虚拟机摊薄"一轨迹一沙箱"的开销（Prime Sandboxes，2026-09-23）。**它意味着什么**：隔离不再是"安全规范"里的加分项，而是学习信号纯度的前提——共享环境里的一条脏轨迹，代价不是一条样本，而是污染整组组内比较。

同一时期还出现了 RL 环境的"市集化"：Hugging Face 在 2026-09-28 发文把 RL 环境引入 Hub（"Welcome RL Environments to the hub"，博文标题+日期引用），环境开始变成可发布、可复用、可外购的资产，而不是每家实验室的自建孤岛。有 2026-09 的行业观察甚至把实验室在 RL 环境上的投入称为"超过几乎其他一切项"——这是一个值得记录的定性观察，但不是可复算的数字，引用时按观察看待（F12 纪律）。

### 6. 版本化、可复现与任务泄漏

环境必须像数据一样被版本化管理，三个理由都指向训练证据：

- **可复现**：同一策略+同一环境版本，两次 Rollout 结果应该统计一致（允许环境自带的随机性，但不允许未记录的版本漂移）；第 6 节会展开"高成功率但不可复现"为什么是训练的毒药；
- **任务泄漏**：训练环境的任务池与评测基准必须做隔离检查，否则评测分数测量的是记忆而不是能力——这与 T03 的数据污染是同一类问题，只是载体从语料变成了任务；
- **回归可比**：环境改版（换基础镜像、加测试）之后，跨版本的成功率不可直接比较，必须重跑基线。

> **判断边界：**环境的第一性指标是三角：真实性（离上线分布有多近）、稳定性（重置与隔离是否可信）、成本（每条轨迹摊多少）。三者常常互斥——最真实的环境最难重置也最贵。评审环境方案时，先问这三个角各让了多少，而不是问"够不够真实"一个角。

## 二、从任务到轨迹：Observation、Action 与 Compaction

### 1. 五个名词，一段历史

Agentic RL 的训练材料不再是"Prompt + Response"，而是**轨迹（Trajectory）**——一段有副作用的历史。先把五个名词用一张解剖图讲清（本章自足定义，不要求回看引言）：

```text
轨迹（Trajectory）= 一段交替的历史
─────────────────────────────────────────────────────
Observation（观察）   模型此刻看到什么：issue 描述、
                      文件内容、上一条命令的输出
      ↓
Action（动作）        模型决定做什么：一段生成
      ↓
Tool Call（工具调用） 动作里真正改变世界的部分：
                      读文件、改代码、跑测试
      ↓
Environment State（环境状态）
                      工具执行后环境变成什么样：
                      文件树、进程、测试结果
      ↓ （回到 Observation，循环几十次，直到终止条件）
─────────────────────────────────────────────────────
```

与 T08 最大的差别在第四行：**工具调用会改变环境状态，而环境状态决定下一段观察**。RLVR 里同题多条 Rollout 天然"平行宇宙"；Agentic 轨迹里没有平行宇宙，只有一条随每步动作不断分叉的现实。

### 2. Compaction：长程轨迹的上下文管理

几十步交互下来，历史很快超过模型可用的上下文。**Compaction（轨迹压缩）**可以先理解为：把已经走过的历史压缩成摘要，腾出上下文给后续步骤——哪些细节保留、哪些折叠，是一套独立的工程决策。

```text
原始轨迹：[obs1 act1 obs2 act2 … obs40 act40 obs41 …]
                              ↓ 上下文逼近上限
Compaction：把前 40 步压缩为摘要 S
                              ↓
继续执行：[S, obs41, act41, …]
```

Compaction 换来的是"能走得更远"，代价是**信息有损**：摘要没保住的细节（某个中间报错、某次失败的尝试）从模型视野里消失了。什么该保留、什么可折叠，是一套独立的剪辑策略：

| 倾向保留 | 倾向折叠 |
|---|---|
| 错误与修复的成对记录（哪次尝试失败、为什么） | 重复的文件读取、相同命令的多次输出 |
| 关键决策点（为什么选这个文件、这个方案） | 超长的测试日志（压成结论句） |
| 当前任务目标与已完成进度 | 已验证过的中间推导 |

更关键的是它给训练材料带来的形态变化——一条超长轨迹经 Compaction 之后，会被切成**数量不等、长度不一的子轨迹**：顺利的任务可能只切一刀，曲折的任务切出五段，每段从摘要重启。这个看似技术性的细节，是第 3 节主案例里方法切换的直接推手，先把结论挂在墙上：

> **架构智慧：**训练材料的形态决定方法的前提。当"一条轨迹"变成"若干段不规则子轨迹"，所有假设"样本规整可比"的算法都在悄悄失效——复杂度不会消失，只会转移到你还没看的那一层。

### 3. 可回放、可审计的轨迹

轨迹不只是训练数据，也是事后取证的材料。一个可用的轨迹 Schema 至少包含：

| 字段 | 记什么 | 支撑什么 |
|---|---|---|
| step_id / turn_id | 步骤序号与轮次 | 定位失败发生在第几步 |
| observation | 模型当步看到的输入（含截断策略） | 复现模型视角 |
| action | 模型生成的完整动作 | 审计决策质量 |
| tool_call_raw | 工具名、参数、原始返回 | 区分"模型调用错"与"工具返回怪" |
| env_snapshot_handle | 环境快照句柄（可恢复当时状态） | 事后回放与取证 |
| reward_event | 奖励值 + 触发它的规则版本号 | 奖励规则改版后的可比性 |
| policy_version | 采样时的策略版本 | Policy Lag 统计（第 4 节） |
| compaction_marks | 哪几步之间发生了压缩 | 解释子轨迹边界 |

两个场景强依赖这套 Schema：

- **失败归因**：训练中发现 Reward 异常，要能回放这条轨迹，区分"策略真的做错了"还是"环境在第 37 步崩了"——回放一条坏轨迹十分钟就能定责，没有快照就只能猜；
- **投机取证**：怀疑模型绕过测试（比如改了测试文件本身）时，回放是唯一证据来源——这与 T08 的反投机检查同一逻辑，载体换成了轨迹。T10 会把"轨迹级审计"接进发布证据链，这里先立住记录义务。

### 4. 失败恢复：轨迹中断之后怎么办

p99 长达 4 小时的轨迹必然遇到中断：Worker 掉线、环境崩溃、集群发布。恢复策略要在设计期选定，而不是事故现场即兴：

| 恢复策略 | 做法 | 代价 |
|---|---|---|
| 弃轨迹重采 | 中断即丢弃，任务重新入队 | 长任务重采最贵；p99 轨迹可能反复死于同一类中断 |
| 断点续采 | 从快照恢复环境状态，续接上下文 | 快照开销 + 续接处的上下文拼接误差（一种被动的 Compaction） |
| 降级收账 | 保留已完成前缀，按部分进度结算或作废 | 结算规则要预先写死，否则变成隐式的过程奖励 |

三个选项分别把中断成本转移给采样账、快照账与奖励设计——同一句"环境要能容错"，落到账本上是三笔完全不同的钱。选哪个取决于任务时长分布：p50 短的任务弃轨迹重采最省事；p99 极长的任务不配断点续采，等于把最贵的样本交给运气。

## 三、奖励与信用分配：主案例 GLM-5.2 为什么转 critic-based PPO

### 1. 奖励的四种形态

| 奖励形态 | 给分时机 | 优势 | 风险 |
|---|---|---|---|
| 最终结果奖励 | 任务终态（测试通过=1） | 最可靠、最难钻空子 | 几十步共享一个信号，归因最粗 |
| 过程奖励 | 关键里程碑（如"定位到正确文件"） | 缓解稀疏性 | 里程碑定义引入主观性，可被迎合 |
| 步骤级奖励 | 每步/每轮 | 归因最细 | 打分器本身就是新的 Reward Model 偏差源（T07） |
| 约束惩罚 | 违规即罚 | 守住权限与安全边界 | 罚则设计与误伤率要单独验收 |

实践里通常是"结果奖励兜底 + 约束惩罚划界"，过程/步骤奖励按需引入。引入过程奖励时带上 T07 的教训：每一个"给过程打分的东西"都是一个评分器，都会带来评分器偏差与被迎合的风险——"定位到正确文件给 0.2 分"这条规则本身，就可能教模型学会先乱猜一堆文件把里程碑刷满。过程奖励的每一条规则都要配一个反投机测试用例，这是 T08 验证器纪律在轨迹上的延续。

真正的难点也不全在给分，而在**信用分配（Credit Assignment）**：分数已知之后，功劳和责任怎么摊到几十步、几万个 Token 上？

### 2. 两条归因路线：组内基线 vs Critic

第 4 层（信号粒度与信用分配）的两条主流路线，前提和代价都不同：

| 路线 | 机制 | 成立前提 | 系统代价 |
|---|---|---|---|
| 组式基线（GRPO 系） | 同一任务采一组轨迹，组内相对比较形成 Advantage | 组内轨迹规整可比、有方差 | 成组采样与组完整性维护；无需独立 Critic |
| Critic / Value 路线（PPO 系） | 训练一个价值模型估计"从当前状态继续下去预期多好"，得到 Token 级 Advantage | Critic 学得准、不引入系统性偏差 | 额外的模型、显存、GPU 与同步；价值学习的稳定性 |

组式路线用"多采几条"换掉了 Critic——这正是它 2024 年以来流行的原因（去 Critic 化）；Critic 路线用"多养一个模型"换来了**单条轨迹也能学习**与更细的归因粒度。两条路线没有绝对优劣，各自的前提绑在轨迹形态上。

[GLM-5 技术报告](https://arxiv.org/abs/2602.15763)明确其 RL 建立在 GRPO 之上、Agentic 阶段采用组式策略优化：同一任务生成多条轨迹，用组内相对结果形成训练信号。到此为止，这是 2024--2026 年的主流形状。

先用一个教学示意把组内比较的工作方式走一遍（数字为示意，非任何真实实验）：同一任务采 4 条轨迹，测试通过分别记 1、通过记 1、失败记 0、失败记 0——组均值 0.5，于是"通过"的两条获得正 Advantage（比基线好），"失败"的两条获得负 Advantage。整套机制的前提写在里面：**四条轨迹面对的是同一个初始状态、长度同量级、没有中途被压缩重切**。任何一条前提破了，"比基线好"就不再是"策略更好"的同义词。

### 3. 主案例：GLM-5.2 的完整因果链

到了 GLM-5.2（2026-06），[官方说明](https://z.ai/blog/glm-5.2)描述了面向超长程 Agent 任务的训练变化。把因果链完整摆出来（表述按证据库核对整理，因果方向为官方叙述）：

```text
任务形态变化：更长程、更复杂的 Agent 工程任务
        ↓
超长轨迹经 Compaction 切成多个可训练子轨迹
（数量不等、长度不一——第 2 节的形态变化）
        ↓
"同一 Prompt 采一组规整、可比较轨迹"的前提
不再自然成立
        ↓
转向 critic-based PPO
        ↓
从单条 Rollout 学习，由 Critic 估计 Token 级 Advantage
        ↓
主动偏离业界组内相对路线的主流（官方自知）
```

用一个教学示意把"前提怎么破"走一遍（示意，非官方数据）：同一个长程任务采 4 条轨迹——

```text
轨迹 A（顺利）：43K Token，Compaction 切成 1 段，测试通过 → 1
轨迹 B（曲折）：900K Token，切成 4 段，测试通过 → 1
轨迹 C（曲折）：1.2M Token，切成 6 段，最终失败 → 0
轨迹 D（顺利）：51K Token，1 段，失败 → 0
```

组均值仍是 0.5，但现在的"单位"已经混乱：A 的 1 段和 C 的 6 段不再是可比较的样本——C 的中间子轨迹既贡献过正确步骤、也包含致命错误，把它们统一记 0（继承终态）等于惩罚了其中做对的部分；按子轨迹分别记分又没有各自的终态可依。**组内相对比较需要"规整可比的样本单位"，Compaction 恰好消灭了它。**这就是因果链中间那一格的全部含义。

放回八层坐标系逐层翻译：

| 判断层 | GLM-5 的组式路线 | GLM-5.2 的长程任务约束 |
|---|---|---|
| ① 能力目标 | Agentic、Reasoning、Coding | 更长程、更复杂的 Agentic 工程任务 |
| ② 训练材料 | 同一任务下成组生成多条轨迹 | Compaction 后数量、长度不规则的子轨迹 |
| ③ 学习信号 | 环境终态 + 组内相对 | 环境终态 + Critic 价值估计 |
| ④ 信用分配 | 组归一化的相对 Advantage | Critic 估计 Token 级 Advantage |
| ⑤ 优化方法 | GRPO 基的组式策略优化 | Critic-based PPO、单轨迹学习 |
| ⑥ 辅助组件 | 不需要独立 Critic | 增加 Critic（显存与 GPU 新账单） |
| ⑦ 系统影响 | 成组采样、组完整性维护 | Actor/Critic/Rollout 三类资源的调度与同步 |
| ⑧ 晋级证据 | 目标基准提升、无投机 | 同上，还要覆盖 Critic 偏差风险 |

### 4. 三条必须跟上的纪律

**第一，严禁读成"PPO 取代 GRPO"。**GLM-5 仍以 GRPO 基的组式优化为主，GLM-5.2 只是在长程任务这一段转向 critic-based PPO；业界默认仍然是 GRPO 系（含 GSPO 等变体），GLM-5.2 是官方明言的"自觉偏离主流"。正确的句子是"某模型在特定任务形态下采用了 X"，不是"业界已转向 X"。

**第二，Critic 不是免费的。**[slime 的使用文档](https://github.com/THUDM/slime)直观展示了这笔账：GRPO 工作流不需要 Critic；PPO 工作流则要分别规划 Actor、Critic、Rollout 三类 GPU 资源。方法层的"加一个模型"，到了系统层就是新的显存账单、新的同步路径，以及三个新的失败模式：

| Critic 路线的失败模式 | 表现 | 监控要点 |
|---|---|---|
| 价值估计偏差 | Critic 系统性高估/低估某些状态，Advantage 失真 | Value loss 与实际回报的偏差分布 |
| 价值学习不稳 | Value 损失 spikes，Advantage 噪声放大 | Value loss 曲线与梯度范数联动观察（T08 指标组） |
| 资源挤压 | Critic 挤占 Actor/Rollout 的显存与卡 | 三类资源的配比复盘 |

对照第 5 节 Inkling 账本的 sampler : trainer = 5 : 3 再想一层：Critic 属于 trainer 侧，组式路线省下的 Critic 算力，正好可以换更多采样——这也是"去 Critic"潮流在系统层面的真实动机之一。

**第三，复用推理，不复制答案。**如果你的任务是短答案、同题能便宜地采出多条可比轨迹、Reward 有足够组内方差——GRPO 系仍然是更轻的选择。GLM-5.2 值得抄的不是"选 PPO"这个结论，而是"任务形态→轨迹形态→方法前提→系统拓扑"这条推理链（引言错误 4 的正面教材）。

> **判断边界：**信用分配的选型不问"谁更强"，先问两个事实问题：我的轨迹经不经 Compaction、规不规则？我养得起 Critic 的资源与稳定性成本吗？两个答案凑齐，选型常常自己浮出来。

## 四、异步训练拓扑：On-policy、Policy Lag 与新鲜度

### 1. 两个自足定义：On-policy 与 Policy Lag

**On-policy（在策略）**：训练数据由当前版本的策略实际产生，而不是从别处收集。完全 on-policy 意味着每更新一次参数，之前采的所有经验作废重来——对"一条轨迹 8 分钟"的 Agent 任务，这等于训练器永远在等数据。所以工程现实都是**近似 on-policy**：允许数据稍微"过期"，换取采样与训练的重叠并行。

**Policy Lag（策略滞后）**：Rollout Worker 用版本 v_t 的策略在采样，Trainer 已经更新到 v_t+k——这 k 个版本的差距就是 lag。lag 越大，经验分布离当前策略越远，每条经验的"有效性折扣"越大；lag 为零则回到同步等待。异步训练的全部张力就在这一个量上。它有三种常用度量，各盯一个视角：按版本差（v_t 落后多少个更新）、按时间（这条轨迹开始采样时权重已多旧）、按占比（训练批里旧经验的混合比例）。监控至少报其一的分布（p50/p99）而不是均值——lag 的伤害集中在尾部，均值会把最坏情况藏起来。

### 2. 三种拓扑的取舍

| 拓扑 | 工作方式 | 优势 | 代价 |
|---|---|---|---|
| 同步 | 全部 Rollout 完成→训练一步→发新权重 | lag=0，理论最干净 | 训练器等最慢轨迹，GPU 大量空转 |
| 部分异步 | 分批滚动：新权重定期发出，旧经验混合使用 | 折中，工程可控 | 需要管理混合版本数据 |
| 完全异步 | 生成与训练持续重叠，各自全速 | 吞吐最大，长短任务都吃得下 | lag 不可控地波动，需要经验过滤与丢弃策略 |

```text
完全异步拓扑（生成与训练解耦）
─────────────────────────────────────────────────
环境工厂 ──▶ Rollout Worker 群（用权重 v_t 采样）
     ↑            │  轨迹+奖励（带版本号 v_t）
     │            ▼
     │      经验队列 / Buffer（lag 监控、过期丢弃）
     │            │
     │            ▼
     │      Trainer（正在更新 v_t+k）
     │            │ 新权重（定期/连续下发）
     └────────────┘ v_t 落后 v_t+k 越多，lag 越大
─────────────────────────────────────────────────
```

### 3. 2026 年的生态收敛：cross-engine 是中心问题

这一年异步 RL 从"各家自研脚本"收敛成了公开讨论的系统问题。[Hugging Face 2026-03 的综述 "Keep the Tokens Flowing"](https://huggingface.co/blog/async-rl-training-landscape)梳理了 16 个开源异步训练项目，并把 async 定义为"生成与训练有效重叠并行"；同年上半年的多框架复盘与"16 个开源框架教训"（2026-03）指向同一个瓶颈：**agentic RL 的核心系统问题是训练引擎与推理引擎之间的 cross-engine 数据流**——Policy Lag 与 Rollout 吞吐都卡在这条边界上。

生态的回应是分工与合流：

| 组件 | 职责 | 2026 年的例子（按各自官方文档口径） |
|---|---|---|
| 训练引擎 | 梯度更新、权重管理 | veRL（有官方 Agentic RL 训练文档路线）、torchtitan 的 TitanRL（预训练与后训练统一引擎） |
| 推理引擎 | 高吞吐 Rollout 生成 | vLLM |
| 训练栈/胶水层 | 把两者接成异步循环 | slime（THUDM，支持全异步 rollout、生成与训练解耦）；vime（vLLM 2026-06-09 发布，打通 slime 训练栈与 vLLM rollout） |

[vime 的发布](https://vllm.ai/blog/2026-06-09-announcing-vime)是一个标志性事件：slime 与 vLLM 生态合流，说明行业不再默认"一个框架包打天下"，而是接受"训练引擎 + 推理引擎 + 数据流胶水"的三件套结构。**它意味着什么**：选型 Agentic RL 系统时，真正要评估的是 cross-engine 边界上的三件事——权重怎么下发、经验怎么回流、lag 怎么监控，而不是单看训练侧的 FLOPs。

### 4. 权重同步与前缀缓存：吞吐的隐藏杠杆

异步循环里有三个不起眼但决定成败的机制。

**权重同步**要回答下发频率与一致性，三种常见策略：

| 下发策略 | 做法 | 适合 |
|---|---|---|
| 定期批量下发 | 每 N 步训练发一次全量/增量权重 | 中小规模，简单可控；lag 上限=N 步 |
| 连续下发 | 训练器持续推送最新参数 | 大集群，追求低 lag；带宽与一致性管理更重 |
| Worker 按需拉取 | Worker 完成当前批量后拉最新版 | Worker 自治、长短任务混合；lag 由任务时长决定 |

**经验过滤与丢弃**是 lag 的另一半：经验队列里每条轨迹带策略版本号，超过阈值（按版本差距或时间衡量）的经验直接丢弃或降权，防止"上一个世代的经验"污染当前更新。丢弃率本身是一个要盯的健康指标——它飙升说明采样速度与训练速度失配，通常意味着环境侧或队列侧出了瓶颈。

**前缀缓存**利用的是 Agent 任务的天然结构：同一任务的多次尝试、同一条轨迹内的多轮请求，前缀高度重叠，命中缓存就不必重算。[Inkling 2 Small 的 RL Run](https://thinkingmachines.ai/news/inkling-2-small)披露前缀缓存命中 93%+（口径：官方披露）——**它意味着什么**：17M 次 Rollout 的实际推理开销被这个数字直接改写；同一个算法，配上不同的缓存与调度，账单完全不同（T02 第 5 节的同款结论，在 RL 侧重演）。

> **架构智慧：**异步训练的净收益 = 经验量 × 每条经验的有效性。吞吐把第一项抬上去，lag 把第二项压下来——只报 GPU 利用率的异步方案评审，等于只报了分子不报分母。

## 五、环境吞吐与训练经济性：每条有效轨迹的成本

### 1. 把账记到"每条有效轨迹"上

T02 用三本账算训练预算；Agentic RL 要在这三本账之外单列一项**环境账**，并把单位从"生成 Token"换成"每条有效轨迹"：

```text
环境账（按训练周期）
    环境启动：每条 Rollout 一个沙箱的创建开销
  + 任务执行：工具调用、测试运行的计算
  + 重置与清理：轨迹结束恢复干净状态
  + 验证：终态判定（跑测试本身可能很贵）
  + 回放与审计：轨迹存储、快照、取证
        ÷ 有效轨迹数（剔除环境故障、超时、组不完整的废样本）
        ↓
    每条有效轨迹成本 ←── 环境经济性的基本单位
```

分母里的"有效"两个字最贵。环境崩溃率 10%，意味着每 9 条有效轨迹背后有 1 条废轨迹的启动+执行成本要被摊进去；组式方法更苛刻——组里坏一条，整组可能作废（T08 的组完整性问题在环境侧加倍放大）。用一个教学示意把摊派算完（数字全部为假设，只为走通公式）：

```text
假设：目标采 1,000 条有效轨迹，组大小 4（组式路线）
单条环境崩溃率 10%
    → 不成组时：启动约 1,111 条即可（1,000 ÷ 0.9）
    → 成组时：组内任一轨迹故障即整组作废，
      单组存活率 = 0.9⁴ ≈ 0.66
      需启动约 1,500 条（250 组 ÷ 0.66 × 4）才凑齐 1,000 条有效
每条轨迹环境成本（示意）：沙箱启动 5s + 执行 480s + 验证 60s
    → 成组路线的有效轨迹环境成本 ≈ 标称成本的 1.5 倍
若组改为 8：单组存活率跌到 0.43，放大倍数继续上探
```

这道示意题的结论方向是普适的：**组越大、环境越脆，"有效"二字的环境税越重**；而 Critic 路线不需要成组，反而对环境崩溃率更宽容（坏一条丢一条）——信用分配选型与环境稳定性在系统层又耦合了一次。

### 2. 长短任务混合：p50 与 p99 的分叉

Inkling 账本里的一对数字值得单独看：Rollout Token p50 = 43K、p99 = 1.5M（口径同前）。**它意味着什么**：一半轨迹 8 分钟内结束，但最慢的百分之一要跑 4 个小时——相差 30 倍。同步拓扑下，每一步训练都要等 p99 收尾；异步拓扑解开了这个死结，但把问题转移给了调度：长任务占住 Worker 时，短任务要能插队；不同时长的轨迹要能凑成不齐的批次；超时策略（硬杀还是放行）本身是一个会影响学习信号的决策——被硬杀的失败轨迹，究竟是策略差还是环境慢？

这就是 one-sandbox-per-rollout（第 1 节）与 microVM 真正的用武之地：隔离要强，启动要快，两者同时成立，"每条轨迹一个干净环境"才付得起钱。

超时策略是调度的收尾一环，三种选择的代价不同：

| 超时策略 | 做法 | 代价 |
|---|---|---|
| 硬杀记 0 | 超时即终止，按失败结算 | 把"环境慢"误记为"策略差"，惩罚了慢而正确的轨迹 |
| 硬杀丢弃 | 超时即终止，不计入训练 | 数据少了但干净；长任务的信号系统性缺席 |
| 分级超时 | 按任务难度分层设时限 | 最合理，也最依赖难度分层的质量（回到任务协议） |

### 3. Inkling RL 账本整表读一遍

把这份目前公开披露最完整的 RL 账本放在一起（口径均为官方披露，2026-11-05 页面；模型为 594B 总参 / 17B 激活 MoE）：

| 账项 | 数值 | 它意味着什么 |
|---|---|---|
| RL Run 形态 | 单次联合 RL Run | 一次连续运行，不是多次拼接 |
| 训练步数 | 1,075 步 | 步数不多——每一步背后是海量采样 |
| Rollout 总量 | 超 17M 条 | 平均每步约 1.6 万条轨迹；采样才是主负载 |
| 时长 | 9 天 | 与预训练 H1 的 68 小时同一量级坐标系（对照 T02） |
| sampler : trainer 算力配比 | 5 : 3 | 采样侧算力大于训练侧——RL 的账本结构反转了预训练 |
| 前缀缓存命中 | 93%+ | 决定 17M 条 Rollout 实际成本的头号杠杆 |
| Rollout Token | p50 43K / p99 1.5M | 长短任务混合，调度与超时策略成为一等决策 |

**sampler : trainer = 5 : 3 是本章最重要的单个数字**：它用官方口径证实了开场那句判断——Agentic RL 不是"带环境的微调"，而是一台以采样为主负载的机器。预算评审只算训练 GPU 的方案，从第一天起就漏掉了大头。

### 4. 环境从自建资产变成可外购资产

环境账太重，市场开始拆分这个成本：Hugging Face 在 2026-09-28 把 RL 环境引入 Hub（环境市集）；ProRL Agent 在 2026-03-19 提出 Rollout-as-a-Service（把采样循环整体外包）；2026-10-05 已有覆盖 coding-agent RL 环境的商业供应商名录（三条均为博文标题+日期引用，属于行业叙事而非定论）。自建还是外购的判断与 T02 的三本账同构：外购买的是启动速度与维护免除，自建买的是分布控制与数据主权——评测环境通常必须自建并隔离，训练环境则可以混合。

> **架构智慧：**RL 预算里"环境工程"必须单列，不能折进 GPU 账里凑整。一个只写"128 卡 × N 天"的 Agentic RL 提案，等于一份没写食材成本的餐厅开业计划。

## 六、Agentic RL 的评测：成功率之外

### 1. 六个评测维度

| 维度 | 测什么 | 为什么成功率不够 |
|---|---|---|
| 任务成功率 | 终态达标比例 | 基础指标，但掩盖路径质量 |
| 步骤效率 | 完成任务用了多少步/Token | 同样成功的两条轨迹，成本差一个数量级 |
| 工具调用正确性 | 调用序列是否合理（参数、顺序、冗余） | 成功但绕路的策略会把成本转嫁给推理账单 |
| 恢复能力 | 出错后能否自我纠正 | 真实环境必有扰动，一次失败即崩盘的模型不可用 |
| 安全违规 | 权限越界操作频率 | 成功+越权=更危险的模型（T10 的入口） |
| 多次运行稳定性 | 同设置重复运行的成功率方差 | Agent 任务随机性大，单次结果不可信 |

两个维度的做法值得展开。**恢复能力**不能只测"一帆风顺"的路径：在轨迹中段注入扰动（把一个已修复的文件回滚、让某个工具临时超时），看模型能否发现并纠正——注入扰动本身就是受控的环境操作，这也是训练环境与测试环境要用不同随机种子的原因之一。**多次运行稳定性**要报分布而不是均值：同一 Checkpoint、同一环境版本跑 N 次，报成功率的区间；区间很宽的"平均 60 分"和区间很窄的"平均 58 分"，工程价值完全不同。

### 2. 训练环境与测试环境必须隔离

第 1 节提过任务泄漏，这里给出它在上评测时的完整形态：训练任务池与评测基准之间要做去重检查（同源仓库、同模板任务都算嫌疑），评测环境版本与训练环境版本要分开管理。**高成功率但不可复现的环境尤其危险**：同一策略两次运行结果不同，奖励噪声直接混入学习信号——你无法区分"模型变好了"与"环境这次运气好"，消融与回归全部失效。可复现不是科研洁癖，是训练信号的信噪比前提。

### 3. Terminal-Bench 的版本纪律

Agentic 能力评测没有稳定的中立标尺，Terminal-Bench 是最常被引用的一个，于是版本纪律成了引用纪律：

| 基准版本 | 模型 | 分数 | 口径 |
|---|---|---|---|
| Terminal-Bench 2.0 | GLM-5 | 56.2 | 技术报告披露，发布时开源最高 |
| Terminal-Bench 3.0 | GLM-5.2 → GLM-5.3 | 4.6 → 28.3 | 官方模型卡报告值，同一基准版本内对比 |
| Terminal-Bench 4.0 | Kimi K3.1 Pro | 65.7%（含 86 个 CLI 任务） | Artificial Analysis 汇总口径 |

三行数字属于三个不同版本，**跨版本不可比**：TB 4.0 的 65.7 与 TB 2.0 的 56.2 之间不能画箭头说"超过"。看到任何 Agent 基准分数，第一问永远是"哪个版本、谁测的、含多少任务"。

### 4. Agent Arena 与榜单叙事的限定

静态基准之外，动态榜单成为 2026 年的新战场。[Agent Arena](https://arena.ai/leaderboard/agent) 按真实 Agent 会话的任务成功率、用户满意度与可控性动态排名（2026-11-08 仍在更新）。用它叙事时有两条限定必须跟上：

- **开源第一 ≠ 全场第一**：2026-07 的榜单由 Claude Fable 5（High）领跑；开源模型的第一名（如 2026-11-05 开放权重后登顶开源榜的 Kimi K3.1 Pro）是子榜叙事；
- **代表性争议**：Arena 自家论文披露，83 个开源模型合计仅占 29.7% 的榜单数据——开源模型在榜单数据里的代表性本身存疑，"开源社区已追平"这类结论从这份榜单推不出来。

Kimi K3.1 Pro 顺带提供了一个开放权重口径的注脚：2.8T 参数、权重约 5.6TB（2026-11-05 在 HuggingFace 开放），消费级硬件难以本地部署——又一次印证 T02 的纪律：**权重开放 ≠ 可自部署**，登顶开源榜与"人人可跑"是两个命题。

### 5. 流水线视角：跨阶段回退

最后一块评测拼图来自 GLM-5 报告自己：其后训练采用顺序 RL（Reasoning → Agentic → General 三阶段的顺序执行，是 GLM 对自家配方的称呼，不是业界标准术语），官方明确承认顺序训练会造成前段能力回退，流水线末尾用 on-policy 跨阶段蒸馏修复。**它意味着什么**：Agentic 阶段的收益必须放在整条流水线里验收——只看本阶段基准涨了多少不够，还要查前段（Reasoning）能力有没有被侵蚀、修复手段（蒸馏）有没有付出新代价。这也是 T11 编排章的入口，本章先把验收口径立住。

评测在时间轴上跑三遍，各答一个不同的问题：

| 时机 | 跑什么 | 回答什么 |
|---|---|---|
| 训练中（持续） | 小规模探针任务 + 训练健康指标（T08 指标组） | 学习信号还健康吗？环境崩溃率正常吗？ |
| 阶段末 | 完整评测矩阵 + 跨阶段回退检查 | 这个 Checkpoint 比上一个好吗？ |
| 发布前 | 留出任务 + 抗污染检查 + 安全违规审计（接 T10） | 证据链齐了吗？能签发吗？ |

> **判断边界：**Agentic RL 的晋级证据至少四件套：目标基准提升（带版本口径）、跨阶段无不可接受回退、多次运行稳定、无环境投机迹象（改测试、读隐藏答案）。缺任何一件，分数都不构成发布依据。

## 七、端到端推导：一个软件工程 Agent 的训练架构

### 1. 数据流全景

把前面各节拼成一个软件工程 Agent（修 issue 型任务）的完整训练架构：

```text
任务库（真实 issue-PR 对，难度分层，与评测池隔离）
    ↓
环境工厂 ──── 每条 Rollout 一个沙箱（microVM/容器）
    ↓
Rollout Worker 群（推理引擎，权重 v_t）
    │  ①读仓库 ②改代码 ③跑测试 ④读报错 …（几十步循环）
    ↓
轨迹 + 终态奖励（测试通过=1/失败=0，附约束惩罚）
    ↓
验证器/过滤器 ── 剔除环境故障轨迹、投机轨迹（回放取证）
    ↓
经验队列（带策略版本号；lag 监控，过期丢弃）
    ↓
Trainer（Actor [+ Critic，按第 3 节选型]）
    ↓ 新权重定期/连续下发
    └────────▶ 回到 Rollout Worker 群
旁路：Monitor（成功率/熵/Reward 曲线/环境健康度）
      存档：轨迹库（可回放、可审计）
```

虚线之外还有两个容易漏的部件：**Monitor** 要同时盯学习健康（T08 的指标组）与环境健康（崩溃率、重置失败率、lag 分布）；**轨迹库** 是投机取证与失败归因的证据链。把图里每个框的职责与部署考量压成一张表：

| 组件 | 职责 | 部署/选型考量 |
|---|---|---|
| 任务库 | 供给任务、难度分层、隔离检查 | 与评测池物理分开；任务版本化 |
| 环境工厂 | 每条 Rollout 造一个干净沙箱 | 启动延迟预算（microVM/容器/快照） |
| Rollout Worker 群 | 用推理引擎跑轨迹 | 推理引擎吞吐、前缀缓存、权重版本管理 |
| 验证器/过滤器 | 判定终态、剔除环境故障与投机轨迹 | 验证规则版本化；过滤标准要防误杀 |
| 经验队列 | 缓存轨迹、监控 lag、过期丢弃 | 容量与丢弃率是一对矛盾 |
| Trainer | 更新 Actor（含 Critic 时双模型） | 三类 GPU 配比（Inkling 口径 5:3 的 trainer 侧） |
| Monitor | 学习指标 + 环境健康双通道 | 环境指标缺失=盲飞 |
| 轨迹库 | 存快照句柄与完整轨迹 | 存储成本 vs 取证能力的取舍 |

**故障走哪条路**同样要预先设计：环境崩溃的轨迹进"废样本桶"（计入环境账，不进训练数据）；疑似投机的轨迹进"取证桶"（冻结待人工回放）；超时轨迹按第 5 节的超时策略定生死。三类出口混在一条"失败"管道里，是训练信号被污染的最常见入口。

### 2. 同步还是异步：选型依据

| 条件 | 倾向同步 | 倾向异步 |
|---|---|---|
| 任务时长分布 | 短且同质（分钟内、长度集中） | 长短混合（p50/p99 差一个数量级以上） |
| 对 lag 的敏感度 | 任务简单、经验泛化快 | 任务长、经验本身耗时久，等待占比更高 |
| 环境故障率 | 低且可控 | 高（异步可绕过故障轨迹继续吞吐） |
| 工程能力 | 小团队、快速验证 | 有 cross-engine 数据流与版本管理能力 |

选型不是二选一到底：很多团队从同步起步验证信号，再迁到部分异步，最后在长短任务混合压力下走向完全异步。真正不可取的是"隐式异步"——系统事实上解耦了，却没有 lag 监控与过期丢弃策略，让旧经验无声地混进训练。

[GLM-5 技术报告](https://arxiv.org/abs/2602.15763)披露其采用异步 RL 训练框架；第三方评述同时注意到这份报告"在基础设施上花了异常多篇幅"（定性观察）——这从侧面印证了本章的主线：agentic 训练的失败更多来自系统瓶颈而非算法瓶颈。报告的篇幅分配本身就是证据。

> **架构智慧：**算法层的每一个选择都会在系统层长出新组件和新账单：组式路线长出成组采样与组完整性维护，Critic 路线长出价值模型与三类 GPU 调度，异步拓扑长出权重下发与 lag 监控。评审任何"我们换算法 X"的提案时，要求附一张组件图，标出每个框的显存与 GPU——引言错误 3 的 RL 版。

## 八、工程产物：Agent Environment Specification

环境规格是本章交付的可复用产物。骨架如下（评审时逐行过，空一行就是一枚待引爆的雷）：

| 模块 | 要填什么 | 常见翻车点 |
|---|---|---|
| 任务协议 | 任务来源、难度分层、与评测池的隔离检查 | 任务泄漏：评测基准混入训练池 |
| 环境镜像与启动 | 基础镜像、依赖锁定、启动时长预算 | 镜像漂移导致"同版本"不同环境 |
| 权限边界 | 允许/禁止的操作清单、越界处置与罚则 | 靠"模型自觉"而非沙箱强制 |
| 状态管理与重置 | 重置步骤、快照机制、状态残留检查 | 上一条轨迹的修改漏进下一条 |
| 工具定义 | 工具清单、参数与返回 Schema、超时 | 工具输出超长撑爆上下文，无截断策略 |
| 奖励与验证器 | 终态判定方式、约束罚则、版本号 | 奖励规则改动后旧轨迹混用新规则 |
| 轨迹 Schema | 观察/动作/工具输出/快照句柄/版本号 | 只存文本不存快照，事后无法回放 |
| 回放与审计 | 回放接口、取证流程、留存期限 | 出了投机争议却拿不出证据 |
| 并发与隔离 | 沙箱策略（one-sandbox-per-rollout？）、microVM 选型、超时策略 | 共享环境省了钱、脏了学习信号 |
| 监控 | 环境崩溃率、重置失败率、lag 分布、成功率方差 | 只监控训练曲线，不监控环境健康 |
| 版本策略 | 环境版本号、跨版本重跑基线的规则 | 环境改版后直接比较跨版本成功率 |

这份规格与引言的 Training ADR 第 2、6 段（训练材料、系统影响）直接对接：任务协议填进材料段，其余各模块填进系统影响段。环境规格不过关的 Agentic RL 提案，应该像显存超限的预训练方案一样被直接打回。

使用它的三个时刻：

```text
立项时   任务协议 + 权限边界先行——决定这个任务能不能安全地采
评审时   重置/隔离/监控三行必审——决定学习信号可不可信
复盘时   版本策略 + 回放取证两行回填——决定下一次能不能比这一次更好
```

## 九、六种最常见的错误判断

### 错误 1：把 Agentic RL 当成"换一批更难的任务"

任务清单只是环境四件套（任务+测试+容器+奖励规则）的一角。没有重置、隔离、版本化的任务清单，跑起来的第一周就会死于状态污染与环境崩溃。**纠正动作**：提案必须附 Agent Environment Specification，缺角先补角。

### 错误 2：只算训练 GPU，不算环境账与采样账

sampler : trainer = 5:3 的官方口径说明采样侧算力大于训练侧；环境启动/重置/验证/回放还要单列。只写"N 卡 × M 天"的预算，漏掉的是大头。**纠正动作**：预算换算到"每条有效轨迹成本"，环境账单列。

### 错误 3：把 GLM-5.2 的选择抄成通用配方

看到 critic-based PPO 就跟进，却没有经 Compaction 的不规则子轨迹，也不需要 Token 级归因——复制的是结论，不是推理。业界默认仍是 GRPO 系，GLM-5.2 是官方自知的偏离。**纠正动作**：重走"任务形态→轨迹形态→方法前提→系统拓扑"因果链，确认约束同构再复用。

### 错误 4：只报吞吐不报 lag

异步把 GPU 利用率抬上去的同时，把每条经验的有效性压下来；没有 lag 监控与过期丢弃策略的异步，是在用旧经验稀释学习信号。**纠正动作**：异步方案必须同时报经验量与 lag 分布，最好附同步对照。

### 错误 5：拿单个基准分数下结论

Terminal-Bench 跨版本不可比（TB 2.0/3.0/4.0 是三把不同的尺子）；Agent Arena 有开源代表性争议（83 个开源模型仅占 29.7% 榜单数据）。**纠正动作**：每个分数带版本、评测方、任务数三要素；子榜叙事必须注明是子榜。

### 错误 6：高成功率但不可复现的环境照训不误

环境不可复现意味着奖励噪声混入学习信号：组内比较失去可比性，失败无法归因（环境 bug 还是策略错误），消融全部失效。**纠正动作**：环境上线前先跑可复现性验收——同策略同版本重复运行，结果分布必须统计一致。

## 本章小结

- 环境是训练资产：任务、测试、运行空间和奖励规则都需要版本、隔离与可复现检查。
- 长轨迹增加了信用分配和采样长尾问题，算法选择要根据实际轨迹形态检验前提。
- 异步提高吞吐，也引入 Policy Lag。用每条有效轨迹的成本衡量收益，并区分策略失败与环境故障。

> **下一章的问题：**当模型能在复杂环境中自主行动,安全风险和评测复杂度都会上升。下一章讨论如何把安全要求变成可验证的规格,并建立发布证据链。

## 基础术语速查

| 术语 | 初学者可以先怎样理解 |
|---|---|
| Agentic RL | 让模型在工具与环境里完成长程任务的强化学习；新增的工程对象是环境、轨迹与异步编排 |
| 环境（Environment） | 任务+测试+容器+奖励规则的四件套；训练用的一等资产，不是背景板 |
| 轨迹（Trajectory） | 一次完整尝试的历史：观察、动作、工具调用与环境状态交替几十轮 |
| Observation / Action | 模型此刻看到什么／模型决定做什么；两者交替构成轨迹 |
| 工具调用（Tool Call） | 动作里真正改变环境状态的部分：读文件、改代码、跑测试 |
| Compaction（轨迹压缩） | 把走过的历史压成摘要腾出上下文；代价是信息有损，并把轨迹切成不规则子轨迹 |
| On-policy（在策略） | 训练数据由当前策略产生；工程现实是允许少量过期的"近似 on-policy" |
| Policy Lag（策略滞后） | 采样用的策略版本落后于训练中版本的差距；异步吞吐与经验有效性的交换代价 |
| Rollout Worker | 负责生成轨迹的推理进程群；与 Trainer 解耦是异步训练的基本结构 |
| 信用分配（Credit Assignment） | 最终结果的好怎样摊到几十步、几万个 Token 上（八层坐标系第④层） |
| Token 级 Advantage | 好/坏评分落到每个 Token 的细粒度归因；通常由 Critic 估计 |
| 前缀缓存（Prefix Cache） | 复用相同前缀的计算；Agent 轨迹前缀高度重叠，命中率决定 Rollout 账单 |
