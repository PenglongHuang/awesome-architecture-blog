## 开场：同一份模型方案，三种翻车

先拿一个真实体量当锚：[Inkling 2 Small](https://thinkingmachines.ai/news/inkling-2-small)（Thinking Machines，2026-11-05 官方训练账本页）是 594B 总参数 / 17B 激活参数的 MoE（口径：官方披露）。把一个最朴素的问题摆上桌——这套权重用 BF16 存（每个参数 2 字节）约 1.19TB，而单块 GPU 的显存以百 GB 计。**还没开始训练，光是"把模型放进去"就已经超出了任何单卡。**

于是团队开工，然后以三种方式翻车（以下三个现场为教学归纳的典型模式，不是特指某家）：

- **翻车一：装不进（显存账没算）。** 照着论文抄了 GPU 数量，第一步就 OOM（显存溢出）。显存里住的不止权重：梯度、优化器状态、激活值都要在训练的每一步同时在场——后面会算给你看，对一个 594B 总参的模型，这三样加起来是权重的数倍。
- **翻车二：跑不快（通信账没算）。** 终于把模型切开、训起来了，但 MFU（算力利用率，第 2 章定义过）只有百分之十几——GPU 大部分时间在等别的 GPU。并行度翻倍不等于时间减半：每加一个并行维度，就多出一类通信，而通信坐在哪条网络上，决定了它付不付得起。
- **翻车三：恢复不了（状态没存全）。** 训到第三周，一个节点故障。从 checkpoint 恢复，loss 却从 1.9 直接跳到 2.4，再也回不去——那份 checkpoint 只保存了模型权重，而"训练进行到哪了"远不止权重。

值得先看一眼：上一章（T04）的每一个架构决定，都会在本章长出对应的系统问题——这是"骨架定了，系统来还债"的完整清单：

| T04 的决定 | 在本章变成什么 |
|---|---|
| 万亿级总参数 | 四本显存账爆炸，状态分片成为必需 |
| 稀疏 MoE | EP 维度、专家路由 All-to-All、负载均衡 |
| 长上下文 | 激活值爆炸，重计算与 CP 上桌 |
| 注意力与层结构选择 | 单层大小决定 TP 的必要程度 |

三种翻车对应三笔账：显存账、通信账、时间线上的可靠性账。本章的推导顺序由此确定，也就是标题里那句方法论——**账本先行（先算显存装不装得下），组合随后（并行维度怎么乘起来），时间线裁决（精度、优化器与 Goodput 决定端到端到底多快）**。

> **本章只解决一件事：给定模型、硬件和训练目标，如何设计训练并行、数值精度、优化器和容错机制？**

还有一个题眼要说清：为什么说"训练系统不是运维"？运维回答"怎么让既有系统持续正常运行"；训练系统设计是架构决策——切几维并行、用什么精度、多久存一次 checkpoint，每一个选择都改写资源账单与失败模式，方向错了，监控看得再紧也救不回来。引言的判断边界在这里原样适用：一种技术只有改变数据形态、计算图、系统拓扑、资源账单或失败模式，才是本章要讨论的架构问题。

## 一、一步训练的机械：五份状态，一步流水

训练系统的问题千头万绪，源头只有一个：**一步训练到底发生了什么**。把一步拆开，后面所有的显存、并行、精度、容错讨论才有落点。

### 1. 一步流水

```text
取一个 Batch 的 Token 序列
   ↓ ① Forward(前向):逐层计算,得到每个位置对下一个 Token 的预测
   ↓ ② Loss(损失):比较预测与真实的下一个 Token,得到一个标量"错得多离谱"
   ↓ ③ Backward(反向):沿计算图反推,算出每个参数的梯度(往哪调能减小损失)
   ↓ ④ Optimizer Step(优化器步):按梯度与优化器规则更新每个参数
   ↓ 丢弃本批激活值,进入下一个 Batch
```

这一步流水在单卡上已经完整；分布式训练没有发明新步骤，只是让这四步发生在很多卡上，并为"状态放在哪"付出全部代价。

### 2. 五份同时在场的状态

| 状态 | 是什么 | 谁在读 / 写 | 大小由什么决定 |
|---|---|---|---|
| 参数 | 模型全部可学习数字（MoE 含全部专家） | 前向读，优化器写 | 总参数 × 精度字节数 |
| 梯度 | 每个参数"该往哪调、调多急" | 反向写，优化器读 | 与参数同形 × 精度 |
| 优化器状态 | 优化器的内部记忆（动量等，第 5 节展开） | 优化器读写 | 参数量 × 状态字节数 |
| 激活值 | 前向各层中间结果，反向要用 | 前向写，反向读 | 批大小 × 序列长度 × 层数 |
| 临时 Buffer | 通信缓冲、算子临时空间 | 框架管理 | 并行方案与算子实现 |

一个直觉归类：前两份是"模型本身"，第三份是"优化器的记忆"，后两份是"这一步的工作台"。**训练显存 = 五份之和**，任何"装不下"都是其中一份爆了；本章后面的所有手段，本质都是在回答这五份东西分别放在哪。

### 3. 三个交换手段

状态放不下时，工程上只有三种交换可做：

| 手段 | 交换方式 | 代价 |
|---|---|---|
| 重计算（激活检查点） | 前向只存每层边界，反向时重算中间结果 | 多一次（部分）前向计算，换激活显存大幅下降 |
| 梯度累积 | 把大 batch 切成多个 micro-batch，累积梯度后一次更新 | 数学上等效大 batch，但一步时间拉长 |
| 卸载（Offload） | 把暂不用的状态搬到主机内存 | 用 PCIe / NVLink 带宽换显存，时间换空间 |

（定性教学归纳；三者常组合使用，代价都记在第 6 节的利用率口径里。）

### 4. 一道算术，定住本章的起点

用第 2 节会推导的"约 16 字节 / 参数"静态口径（BF16 混合精度 + AdamW），先做一道最粗的算术（教学估算，假设单卡显存 80GB）：

```text
单卡能直训的参数量 ≈ 80GB ÷ 16 字节/参数 ≈ 5B 参数
                                          (还没算激活与 Buffer)

对照:一个 7B 模型的静态状态 ≈ 7B × 16 字节 = 112GB > 80GB
     → 连 7B 都要状态分片或卸载才能"装下"
对照:594B 总参 MoE 的静态状态 ≈ 9.5TB
     → 需要 72 卡起步的完整并行组合(第 2、3 节展开)
```

这道算术就是本章的起点：**在 2026 年的模型体量下，"单卡直训"只覆盖教学规模；一切真实训练从"状态放不下"开始**。分布式训练不是可选项，是模型形态直接长出来的必然。

> **架构智慧：**训练系统的所有问题，都是"五份状态怎么放"的问题。装不下是状态的容量问题，跑不快是状态的搬运问题，恢复不了是状态的快照问题。先把状态列全，再谈方案——跳过这一步去抄并行配置，等于没看牌就下注。

## 二、四本显存账：先回答"装不装得下"

### 1. 第 2 章留下的半句话，现在兑现

第 2 章算训练 FLOPs 时说过：计算量走激活参数口径，总参数不参与计算——"它决定显存与加载，是 T05 训练系统章的话题"。现在兑现：**显存账的全部四个本子，都按总参数算**。对 594B 总参 / 17B 激活的 MoE，两个口径差约 35 倍——算力账用 17B，显存账用 594B，这就是 MoE 训练系统的第一重张力：计算上它像个 17B 的模型，显存上它是个 594B 的模型。

### 2. 四本账逐本算（以 594B 总参为例）

| 账本 | 粗估口径 | 教学估算（594B 总参） |
|---|---|---:|
| 账本一：参数 | BF16，2 字节 × 总参 | ≈ 1.19 TB |
| 账本二：梯度 | BF16，2 字节 × 总参 | ≈ 1.19 TB |
| 账本三：主权重 + 优化器状态 | FP32 主权重 4 字节 + AdamW 两份动量 8 字节 | ≈ 2.38 TB + 4.75 TB |
| **静态合计（前三本）** | **约 16 字节 × 总参**（BF16 混合精度 + AdamW 口径） | **≈ 9.5 TB** |
| 账本四：激活与 Buffer | 随批大小 × 序列长度 × 层数增长（重计算策略直接改写这一本） | 另算，可观 |

口径纪律：这是本文教学估算，非任何官方披露；假设是"BF16 混合精度 + AdamW"，不含激活、通信 Buffer 与框架开销。换优化器、换精度、换重计算策略，前三本与第四本都会变——但"先列口径再报数"的顺序不能变。

**9.5 TB 意味着什么**：即使把静态状态完美均摊到 72 块 GPU（一个 NVL72 机架的卡数）上，每卡也要约 130GB——这还只是静态部分，激活值与通信 Buffer 要在此之上另算。所以没有任何单一手段能解决问题——必须组合，这正是下一节的主题。

### 3. 精度怎么改写这本账

"约 16 字节 / 参数"不是常数，它是精度方案的函数。把三种典型方案的静态账排在一起（单位：字节 / 参数，不含激活与 Buffer；教学口径）：

| 精度方案 | 参数 | 梯度 | FP32 主权重 | 优化器状态 | 静态合计 |
|---|---:|---:|---:|---:|---:|
| 全 FP32 | 4 | 4 | —（本体即主权重） | 8 | 16 |
| BF16 混合 + AdamW | 2 | 2 | 4 | 8 | 16 |
| 权重 / 梯度 FP8 + FP32 状态 | 1 | 1 | 4 | 8 | 14 |

读出两个反直觉的结论：其一，**在表中假设下，BF16 混合与全 FP32 的静态状态均为 16 字节 / 参数**——BF16 参数与梯度节省的空间，被额外的 FP32 主权重抵消；混合精度仍可改善计算吞吐与激活占用，不能只凭计算精度推断静态显存收益；其二，**把权重梯度降到 FP8，静态账只省 2 字节**——FP8 的大头收益在计算吞吐与激活（第 4 节），不在静态账。这两条是"抄精度档位"最容易抄错的地方。

### 4. 为什么需要 FP32 主权重

混合精度训练里存在两份参数：BF16 副本负责前向 / 反向的高速计算，FP32 主权重负责累积更新。直觉解释：BF16 尾数只有 8 位，"大数加小数"时小更新会被直接舍入丢掉——单步更新量相对参数本身常常非常小，累积若干步后在 BF16 里可能一步都没变。FP32 主权重把每步的小更新忠实累加，再同步出一份新的 BF16 副本去计算。**算得快和记得准，是两份不同的状态**——这也是为什么第 6 节的 Checkpoint 五件套里，优化器状态与主权重不能靠权重副本代替。

### 5. 状态分片：ZeRO 与 FSDP 的思路

前三本静态账的解法是一条清晰的思路：**既然状态在所有卡上都要有一份副本是浪费，那就把它们切片摊到所有卡上，用到谁再临时聚合谁**。这就是 ZeRO（方法起源：微软 2020 年论文，按参数 / 梯度 / 优化器状态逐级分片）与 PyTorch FSDP（Fully Sharded Data Parallel，把这套思路带进 PyTorch 生态）的核心——用通信换显存。第 3 节会把它放回并行家族里一起组合。

### 6. 换你来做：一份 7B Dense 的显存账

拿一个最小的真实体量练手（7B Dense，教学估算，不含激活与框架开销）：

| 账本 | 口径 | 估算 |
|---|---|---:|
| 参数 | BF16，2 字节 × 7B | 14 GB |
| 梯度 | BF16，2 字节 × 7B | 14 GB |
| FP32 主权重 | 4 字节 × 7B | 28 GB |
| 优化器状态（AdamW 两动量） | 8 字节 × 7B | 56 GB |
| **静态合计** | 约 16 字节 / 参数 | **约 112 GB** |

结论立刻可读：假设单卡 80GB，这份静态账就放不下——**"7B 模型单卡训练"在混合精度 + AdamW 的口径下本来就不成立**，要么状态分片 / 卸载，要么多卡。注意这笔账完全没提激活：序列越长、批越大，第四本账越厚，而它才是重计算与 CP 要对付的对象。顺带看见规模的不对称：7B 的静态账 112GB，594B 总参 MoE 是 9.5TB——差 85 倍，但两者都不能单卡直训，**差别只在于"需要多复杂的组合"**。

> **判断边界：**显存估算必须写清口径：精度假设、优化器假设、是否含激活与框架开销。"模型 600B"这句话回答不了任何工程问题——600B × 2 字节与 600B × 16 字节差 8 倍；把激活算漏，差得更多。评审任何训练方案，第一件事是查它的显存账口径齐不齐。

## 三、并行策略：从计算图推导拓扑

并行不是五个可以随便勾选的选项，而是五个各自回答"切什么、传什么"的维度。先逐个认识，再看它们怎么乘起来。

### 1. 五个并行维度

| 维度 | 切什么 | 通信什么 | 什么时候用 |
|---|---|---|---|
| 数据并行 DP | 每卡一份完整模型副本，各吃不同数据 | 每个优化器步同步一次梯度（AllReduce） | 模型装得下单卡时最简单的扩展 |
| 状态分片 ZeRO / FSDP | DP 之上把参数 / 梯度 / 优化器状态切片摊开 | 前向 / 反向按需聚合参数分片 | 静态状态装不下单卡时 |
| 张量并行 TP | 把单层权重矩阵切开，多卡合力算一层 | 每层前向 / 反向都要通信，高频小消息 | 单层太大，且卡间有机内高带宽互联 |
| 流水线并行 PP | 把层切成连续阶段，各卡负责一段 | 阶段边界传激活，点对点 | 跨机扩展，容忍较低带宽 |
| 序列 / 上下文并行 CP | 把一条序列切开，多卡协作 | 注意力计算需要跨卡协调 | 长序列激活爆炸时 |
| 专家并行 EP | 把 MoE 的专家分到不同卡 | 每个 Token 被路由到专家所在卡（All-to-All） | MoE 的必备维度 |

### 2. 组合公式与一张拓扑图

```text
组合公式:GPU 总数 = DP × TP × PP × CP × EP
(torchtitan 把这套组合称作 5D 并行,口径:PyTorch 官方博客)

示意:一个 MoE 训练拓扑,72 卡 = DP2 × TP2 × PP2 × EP9(数字为教学示意)

   流水线阶段 0(下层)                流水线阶段 1(上层)
   ┌──────────────────────┐        ┌──────────────────────┐
   │ DP 组 0: TP=2 切层内矩阵 │        │ DP 组 0: TP=2          │
   │          EP=9 分专家    │ ─────→ │          EP=9 分专家    │
   │ DP 组 1: 同上           │ 传激活  │ DP 组 1: 同上           │
   └──────────────────────┘        └──────────────────────┘
        │      ↑                          │      ↑
        │      └─ 专家路由 All-to-All(持续高频,留在机内 NVLink 域)
        └─ 梯度同步 AllReduce(每优化器步一次)

   跨机(如果有多个机架):PP 激活点对点 + DP 梯度同步 + 跨机专家路由,
   全走跨机网络——带宽比机内低一个量级,能留在机内的流量绝不外送
```

这张图的读法：**每个维度引入一种通信，每种通信有自己的频率、消息大小与可容忍时延；拓扑设计的本质是给通信分类定价**——高频小消息（TP、EP 的 All-to-All）放进机内 NVLink 域，低频大同步（DP 梯度、PP 激活）可以走跨机网络。

### 3. 通信分类定价表

| 通信模式 | 谁在用 | 频率与消息 | 可容忍时延 | 应该落在哪条网络 |
|---|---|---|---|---|
| AllReduce（梯度同步） | DP | 每优化器步一次，大消息 | 中 | 机内最好，跨机可忍 |
| AllGather（分片聚合） | ZeRO / FSDP、TP | 前向 / 反向层间，高频 | 低 | 机内高带宽域 |
| All-to-All（专家路由） | EP | 每个 Token 每层，持续流量 | 极低 | 机内 NVLink 域，尽量不出机架 |
| 点对点（激活传递） | PP | 每微批一次 | 中高 | 可跨机 |

这张表的用法是反向的：**先看每种通信"能忍多大的延迟、出得起哪条网络"，再决定对应并行维度的边界划在哪**。All-to-All 出了机架，吞吐立刻被跨机带宽锁死——这就是 2026 年拓扑以机架为单位组织的根本原因。

### 4. 从模型形态倒推并行组合

并行组合不是从"别人的配置"抄来的，是从自己的模型形态推出来的。推导链（决策推导，顺序不可乱）：

```text
第 1 问  静态状态单卡装得下吗?(第 2 节的四本账)
         └ 装得下 → 先用 DP 吃掉简单扩展,再往下问
         └ 装不下 → 开状态分片(ZeRO/FSDP),继续问
第 2 问  单层权重切开后单卡算得动吗?
         └ 单层太大 → TP(注意:TP 通信高频,只放机内)
第 3 问  层数多到单卡放不下 / 装下了也太多?
         └ 层放不下 → PP(点对点传激活,可以跨机)
第 4 问  序列长到激活爆炸吗?
         └ 长 → 重计算 + CP
第 5 问  是 MoE 吗?
         └ 是 → EP 先行:专家分组决定机架内布局,
              再让 DP/TP/PP 在剩余维度上配合
收尾     DP 吃掉剩余扩展;核对五维乘积 = 实际 GPU 数;
         按"通信分类定价表"复查每种流量落在哪条网络
```

### 5. MoE 训练的通信瓶颈与 Dense 根本不同

Dense 模型的重头通信是每步一次的梯度同步；MoE 在这之上加了一层持续流量：**每个 Token 在每一层都要被路由器发给选中的专家所在的卡**，这产生 All-to-All 通信——所有卡同时向所有卡发数据。它带来两个 Dense 没有的问题：

- **流量持续且巨大**：它随 Token 吞吐线性增长，不能靠"等一步同步一次"的节奏摊薄；
- **负载不均**：专家被激活不均匀时，热专家所在的卡成为瓶颈，其他卡空转。工程上用路由均衡类损失、专家容量上限等机制约束（定性；具体机制随模型而异）。

2026 年现役旗舰的激活比可以感受这个量级：Kimi K3 为 2.8T 总参 / 104B 激活、896 个专家每 Token 选 16 个（激活比约 3.7%，口径：arXiv:2607.24653 技术报告）；GLM-5 为 744B / 40B（约 5.4%，口径：arXiv:2602.15763）。专家数越多、激活比越低，路由流量与均衡难度越大。

工程界的应对方向有一条清晰的主线：**以 EP 为中心、以机架为单位组织通信**。[NVIDIA 官方工程博客](https://developer.nvidia.com/blog/scaling-large-moe-models-with-wide-expert-parallelism-on-nvl72-rack-scale-systems)展示了在 GB200 / NVL72 机架级系统上用宽专家并行（wide EP）加 DP 部署超大 MoE——把专家路由的 All-to-All 留在机内高带宽互联域内完成。研究侧，[Mixture-of-Parallelisms](https://arxiv.org/html/2607.01844v1)（2026-07，arXiv 预印本）系统化组合多种并行来压 MoE 训练显存；[torchtitan](https://pytorch.org/blog/torchtitan-update-new-sota-models-performance-at-scale-titanrl) 提供 5D 并行栈（下文框架一节展开）。

一个必须写下的限定：**不存在适用于所有模型的"标准并行组合"**。TP 适合机内、PP 适合跨机、EP 由专家数决定分组、CP 由序列长度决定要不要开——组合是"模型形态 × 硬件拓扑"解出来的，不是抄来的。2024 年教科书里"TP / PP / DP 3D 并行"的说法，在万亿参数 MoE 面前已经不够用了——2026 年的公开工程实践共同指向：以 EP 为中心、以机架级系统（NVL72）为部署单位。

### 6. 案例拆解：Inkling H1——机架即部署单位

[Inkling 2 Small](https://thinkingmachines.ai/news/inkling-2-small) 的 H1 预训练（口径均为官方披露）给了这套叙述一个可以勾稽的实物：

| 输入量 | 数值 | 口径 |
|---|---|---|
| 模型 | 594B 总参 / 17B 激活 MoE | 官方披露 |
| H1 训练 Token | 8.4T | 官方披露，H1 预训练阶段 |
| 硬件 | GB300 NVL72 机架 | 官方披露 |
| H1 时长 | 68 小时 | 官方披露 |
| 精度 | 原生 NVFP4 | 官方披露（配方细节待后续披露） |

从拓扑角度读这份账本，三个读法：

- **部署单位是机架不是卡**。NVL72 把 72 卡的高带宽互联封进一个机架域，正好对应上一小节"专家路由 All-to-All 不出机架"的原则——这不是巧合，是"硬件形态为并行策略服务"（或反过来）的相互选择。
- **四量齐披露才能勾稽**。17B 激活 × 8.4T Token 给出 6ND 约 8.6e23 FLOPs（第 2 章的估算），除以 68 小时，得整机架有效吞吐约 3.5e18 FLOP/s（本文估算口径）。少披露任何一个量，这道对账就断了。
- **68 小时本身是个信息量**。8.4T Token 量级的预训练在一个机架、三天内完成——机架级系统的吞吐密度，正在改写"预训练必须数月"的默认预期（第 2 章预算表的卡时行可以直接受益）。

第 4 节会从精度角度再读一遍这份账本——同一份数据，两种决策视角。

> **架构智慧：**并行度的每一分收益都要拿通信去买。设计拓扑时不问"我能开几维并行"，先问"每种通信走哪条线、付不付得起"。GPU 数量是模型形态与硬件互联的解，不是论文里的超参数。

## 四、数值精度：省一半账单，先过三层约束

### 1. 格式速览

| 格式 | 每元素字节 | 2026 年的状态（口径注明） |
|---|---:|---|
| FP32 | 4 | 参考精度；主权重与优化器状态常用 |
| BF16 | 2 | 通用训练基线（FP32 的指数位、更短的尾数，范围大、精度粗） |
| FP16 | 2 | 需要损失缩放管理溢出，训练场景渐被 BF16 取代 |
| FP8 | 1 | 2026 年的前沿训练标准之一——但限定条件见下 |
| MXFP8 | 1 + 块共享指数 | Blackwell 原生 Tensor Core 支持，1×32 块粒度（Megatron-Core 生态推荐，[arXiv:2603.07685](https://arxiv.org/html/2603.07685v1)，2026-03） |
| FP4 / NVFP4 | 0.5 | 训练侧仍是研究前沿与早期实践；生产落地目前在推理 / 部署侧 |

### 2. FP8 的"省一半"是什么口径

[FP8 训练基础设施指南](https://introl.com/blog/fp8-training-infrastructure-next-generation-precision-guide)（Introl，2026-02）给出的口径是：相比 BF16 约省一半计算与内存；Meta 也已把 FP8 流程从 Hopper 迁移到 Blackwell。但这句"省一半"的成立要过三层约束，缺一层都会在账单或曲线上翻车：

| 约束层 | 它管什么 | 缺了会怎样 |
|---|---|---|
| 硬件支持 | 哪代 Tensor Core 原生跑哪种格式（Hopper 起 FP8；Blackwell 加 FP4，B200 上 FP4 吞吐为 FP8 的 2 倍） | 硬件不支持 → 用模拟精度，省的是显存不是计算 |
| 框架实现 | kernel、缩放（Scale）管理、通信精度 | 数值溢出 / 下溢、缩放因子失配 → 训练不稳 |
| 模型稳定性 | 哪些张量能降精度、哪些必须保高精度 | loss 曲线发散或评测悄悄掉分 |

所以正确表述是：**FP8 训练在 Hopper / Blackwell 级硬件与已验证管线上是 2026 年的成熟做法，但"FP8 = 省一半"不是普适等式**——把这句话写成无条件的行业共识，就违反了事实纪律。

### 3. 不同张量、不同精度

混合精度训练的真正做法是"按张量分工"。低精度格式能表示的数值窗口比 FP32 窄得多，直接塞进去会发生两件事：

```text
上溢(overflow):数值太大,超出可表示范围 → 变成 inf,一步带飞参数
下溢(underflow):数值太小,低于最小可表示值 → 变成 0,梯度悄悄丢失

缩放(Scale)的用途:给张量乘一个因子,把数值整体搬进可表示窗口,
                    计算后再搬回去 —— 窗口管住了,精度才可用
```

于是一份精度方案是一张"张量 × 格式"的分配表，而不是一个单一开关。典型分工（工程惯例的定性描述，具体随模型与框架而异）：

| 张量 | 常见做法 | 原因 |
|---|---|---|
| 权重（前向矩阵乘） | 可降到 BF16 / FP8 / 更低 | 权重对精度相对鲁棒，收益最大 |
| 梯度 | 低精度 + 缩放因子 | 动态范围大，最容易上溢 / 下溢 |
| 主权重与优化器状态 | 保 FP32 | 第 2 节第 4 小节：小更新要记准 |
| 归约与累加 | FP32 | 低精度累加误差会累积 |

这也解释了为什么精度方案必须整体验证：任何一格改错了，都可能在几万步之后才显形——那时已无法把它与数据、超参的改动区分开。

### 4. 案例与红线：NVFP4

FP4 训练的证据现状要分两侧写清楚：

- **训练侧**：[Inkling 2 Small](https://thinkingmachines.ai/news/inkling-2-small) 的 H1 预训练阶段（8.4T Token，GB300 NVL72，68 小时）官方披露使用**原生 NVFP4 训练**——这是目前公开账本里 FP4 级训练的标志性实践。两条纪律必须跟上：其一，官方明确表示 **NVFP4 配方细节待官方后续披露**，外部不知道哪些张量在什么缩放策略下降到了 4 比特；其二，FP4 训练整体仍属前沿实践，不是可以照抄的默认档位。
- **部署侧**：FP4 的成熟生产应用目前在推理 / 部署量化（如 GLM-5.2-NVFP4 量化版，口径：NVIDIA 侧 2026-10 发布）。

顺手做一次勾稽，体会"账本透明"的价值：H1 的四量（17B 激活 × 8.4T Token × GB300 NVL72 × 68 小时）同时披露，外部就能互相对账——6ND 粗估约 8.6e23 FLOPs（第 2 章的估算），除以 68 小时，整个机架的等效有效吞吐约 3.5e18 FLOP/s（本文估算口径）。**没有精度、硬件、时长的同时披露，这道勾稽就做不了**——这是披露分层在训练系统章的直接体现。

### 5. 精度变更的门禁

精度每一次降档都是一次受控实验，不是配置修改。最低门禁按顺序过四关：

1. **对照**：同一配置只改精度，训练 loss 曲线应当对齐（允许微小偏移，不允许系统性走高）；
2. **评测**：跑下游能力评测，确认无回退（不只看 loss——第 10 章的评测体系在这里第一次被预支）；
3. **长跑**：观察缩放因子、梯度范数是否稳定，短程验证发现不了慢性的数值漂移；
4. **回退条件**：把"什么信号出现就退回上一档"写进配置，而不是写进某个人的记忆。

任一关失守就退回上一档。这套门禁会直接进入本章工程产物的"数值精度"一栏。

> **判断边界：**精度表里的"省一半"是硬件口径（每元素字节数与峰值吞吐），不是你的账单口径。只有当硬件、框架、模型稳定性三层同时成立，省的一半才会出现在账单上；在那之前，它只是别人的账单。

## 五、优化器：AdamW 的账、Muon 的边界与超参纪律

### 1. AdamW：为什么优化器状态是显存大户

AdamW 为每个参数维护两份"记忆"，一步更新的直觉版（不是公式推导，只看每行在做什么）：

```text
g = 本批算出的梯度
m = 平滑版 g(一阶动量)        ← 记住"惯常往哪走":方向的多步平均
v = 平滑版 g²(二阶动量)       ← 记住"通常抖多大":噪声的尺度
p ← p - lr · m/√v  -  lr · wd · p
     ↑ 按"方向÷抖动尺度"走一步   ↑ 权重衰减单独施加(与梯度解耦)
```

工程上要记的账：**两份动量各 4 字节 FP32，共 8 字节 / 参数——是 BF16 参数本体（2 字节）的四倍**。第 2 节四本显存账里账本三那么厚，就是它撑起来的。

### 2. Muon：从个案走向研究 / 工程实践的主流路线

2026 年优化器叙事的主角是 Muon。把它的证据链按时间读一遍，正好是"一种技术怎样从个案变成路线"的标本：

| 时间 | 事件 | 口径 |
|---|---|---|
| 2025-07 | Kimi K2 用 MuonClip 首次稳定训练万亿参数 MoE：MuonClip 为解决预训练中注意力 logit 爆炸，配套 QK-Clip（每步对 q/k 权重做缩放） | [arXiv:2507.20534](https://arxiv.org/abs/2507.20534)，历史锚点 / 个案起源 |
| 2026-06 | PyTorch 官方博客《Using Muon Optimizer with DeepSpeed》，Muon 与 DeepSpeed 集成进入官方生态 | [PyTorch 官方博客](https://pytorch.org/blog/using-muon-optimizer-with-deepspeed) |
| 2026-10 | torchtitan 以 FlexShard 高效支持分布式 Muon 的分片训练 | [torchtitan 官方博客](https://pytorch.org/blog/torchtitan-update-new-sota-models-performance-at-scale-titanrl) |

Muon 的设计直觉：对 2D 权重矩阵的更新做一次正交化（用 Newton–Schulz 迭代近似），让每步更新在不同特征方向上的"能量"更均匀——大矩阵更新得更整齐，收敛更快。但它有三条清晰的适用边界：

- **只管 2D 权重**：embedding、输出头、归一化层等 1D 参数仍然用 AdamW——主流做法是"Muon（2D 权重）+ AdamW（1D 参数）"的混合策略，而不是整体替换；
- **微调场景 MuonClip 不占优**：Hugging Face 2025-12 的微调实验（[优化器对比博客](https://huggingface.co/blog/KingNish/optimizer-part1)）显示，微调里 Muon / Muon+AdamW 的收敛优于 MuonClip——QK-Clip 是**预训练**的稳定措施，不是微调增益；
- **叙事纪律**：Muon 在 2026 年的状态是"从个案走向研究 / 工程实践的主流路线"，不是"全面取代 AdamW"。抄优化器之前，先抄它的适用矩阵。

### 3. 超参纪律：每个超参守一道闸

| 超参 | 它守什么 | 失守的样子 |
|---|---|---|
| 学习率与日程（warmup + 衰减） | 每步走多大、何时减速 | 过大 → 发散与 spike；过小 → 浪费卡时 |
| Batch size（含逐步放大） | 梯度噪声尺度与吞吐的平衡 | 太小 → 噪声大不稳；太大 → 同算力下步数变少 |
| 梯度裁剪 | loss spike 的第一道闸 | 单个坏批次把参数带飞 |
| 权重衰减 | 参数不无界长大 | 数值缓慢恶化，后期训练不稳 |

学习率日程值得一张草图——它同时解释了 warmup 与衰减各自防的是什么：

```text
学习率
 │        ／＼ ← warmup:开局小步,等优化器统计(m/v)稳定
 │       ／    ＼
 │      ／       ＼＿＿
 │     ／             ＼＿＿＿＿＿ ← 衰减:后期小步精细收敛
 │    ／
 └──────────────────────────────→ 训练步数
```

（定性教学归纳；具体取值是外推实验的事，见第 2 章的预测台账纪律。）

> **架构智慧：**优化器不是"选最强的"，而是"按参数形状分工 + 按训练阶段选件"。Muon 管 2D、AdamW 管 1D、QK-Clip 只服务预训练稳定性——2026 年的主流路线本身就是一张分工表，而不是一个排行榜冠军。

## 六、训练可靠性：Checkpoint 状态机、Loss Spike 与 Goodput

### 1. 故障是日程，不是意外

训练规模越大、时间越长，硬件故障从"意外"变成"日程"：几千块 GPU 跑几周，节点失效、网络抖动、数据管线卡顿都会按概率发生。先把常见故障按"检测信号 → 处置"归档（教学归纳）：

| 故障 | 检测信号 | 处置 |
|---|---|---|
| 节点失效（GPU 掉卡、进程退出） | 心跳丢失、进程退出码 | 自动摘除节点，回退到最近好点恢复 |
| 网络异常 | 通信超时、集合通信卡死 | 有限重试；持续失败则整机回退恢复 |
| 数据加载瓶颈 | GPU 等数据时间占比升高 | 加大预取与缓存；查存储带宽与 worker 数 |
| 慢节点（straggler） | 某卡持续落后拖住同步 | 定位原因；必要时隔离重启，不带病长跑 |

训练系统设计的可靠性部分回答一个问题——**故障发生时，你丢多少进度、花多久恢复**。这不是运维细节：GLM-5 的技术报告（[arXiv:2602.15763](https://arxiv.org/html/2602.15763v1)，2026-02）被第三方评述指出"在基础设施上花了异常多篇幅"，其中 agentic 训练的失败更多指向系统瓶颈而非算法——可靠性工程是训练系统能不能交付模型的主变量之一。

### 2. Checkpoint 状态机：引言的承诺，这里兑现

引言的术语表只给了半句定义（"Checkpoint：训练快照与恢复所需的状态，完整状态机在 T05 定义"）。现在补全。**一个可用的 Checkpoint 是五件东西的整体，缺一件，恢复出来的就不是原来那个训练：**

| 组件 | 是什么 | 缺了会怎样 |
|---|---|---|
| ① 模型参数 | 全部可学习权重（MoE 含全部专家） | 模型退回旧版本 |
| ② 优化器状态 | AdamW / Muon 的动量等内部记忆 | 优化器"失忆"，恢复后 loss 跳变、训练震荡 |
| ③ 数据游标 | 数据读到哪个分片、哪条样本、第几轮 | 恢复后重复读旧数据或跳过未读数据 |
| ④ RNG 状态 | 随机数生成器的种子与内部状态 | dropout、数据打乱不可复现，实验无法对照 |
| ⑤ 调度状态 | 当前步数、学习率日程位置、梯度累积计数 | 学习率与日程错位，超参在错误的点上续跑 |

状态机一览：

```text
          保存(每 N 步触发;异步分层:显存 → 主机内存 → 对象存储)
RUNNING ─────────────────────────────────────→ CHECKPOINTED(第 k 步快照)
   │                                               │
   │ 故障:节点失效 / 网络异常 / 数值异常               │ 恢复:五件套整体加载
   ↓                                               ↓
FAILED ──────────→ RESTORING ────────────────────→ RUNNING(从第 k 步继续)
                       │ 校验失败(哈希对不上 / 组件缺失)
                       ↓
                  回退到上一个好点(所以至少保留两代)
```

两条工程纪律：

- **保存是有账单的**。以第 2 节的估算口径，594B 总参模型一份完整 checkpoint 约 9.5TB（五件套里的①②，加 FP32 主权重与优化器状态）。保存频率是"单次故障丢多少进度"与"存储成本、写入开销"的权衡。大规模训练用**异步分层保存**：先把快照从 GPU 显存搬到主机内存（快，不打断训练），再后台写入对象存储（慢，但持久）——同步等磁盘的每一分钟，都是全集群的卡时在空烧。
- **没演练过的恢复等于没有恢复**。恢复路径（校验、回退、五件套加载、从第 k 步续跑）要在平时演练，而不是在故障现场第一次执行。演练要验证的不是"能恢复"，而是"恢复出来的训练与中断前严格一致"——数据游标接得上、RNG 可复现、loss 从断点平滑续走。

### 3. Loss Spike 的分类与第一反应

| 类型 | 曲线长相 | 常见原因 | 第一反应 |
|---|---|---|---|
| 单步尖峰后自愈 | 一步跳高，几步回落 | 个别坏数据批次、瞬时数值抖动 | 记录批次号，观察数步；不急着重启 |
| 发散不回头 | 持续上升 | 学习率过高、精度溢出、数据分布突变 | 立即回滚 checkpoint，逐项排查 |
| 阶段边界跳变 | 换数据配方 / 换阶段时跳 | 配方切换、超参未按日程重置 | 预期内；小步长过渡并核对调度状态 |
| 恢复后跳变 | 从 checkpoint 恢复即跳 | 状态机缺件（游标 / RNG / 动量） | 停；查五件套，这不是超参问题 |

（教学归纳，定性。第四类正是开场"翻车三"的解剖。）

### 4. MFU、HFU、吞吐与 Goodput：四个不可互替的刻度

第 2 章的预算表里，MFU 是那个必须设成区间的假设；本章把它变成要盯的运行指标，并补齐另外三个刻度：

| 指标 | 口径 | 回答什么 | 陷阱 |
|---|---|---|---|
| MFU | 有用计算（6ND 口径）÷ 硬件峰值 | 跑的时候硬件喂饱了吗 | 重计算会压低它——但重计算可能恰恰是划算的 |
| HFU | 实际执行计算（含重算）÷ 峰值 | 硬件在转吗 | 同一训练 MFU ≤ HFU，口径不同不可横比 |
| 吞吐 | Token/s 或样本/s | 管线流速 | 不同并行与精度方案之间不可直接比 |
| Goodput | 名义吞吐 × 有效时间占比 | 扣掉故障、重启、恢复后到底前进多快 | 长训排期唯一诚实的 KPI |

四个刻度各守一段：MFU 管单步效率，HFU 揭示重计算的真实代价，吞吐管管线，**Goodput 管时间线**。把 Goodput 算一遍（教学示意数字）：

```text
假设:名义吞吐 1,000 Token/秒(集群口径);每周故障 3 次
     单次故障:检测 5 分钟 + 重启排队 30 分钟 + 恢复 25 分钟 = 1 小时
     另因保存间隔太稀,单次故障平均丢 2 小时进度 → 折合 6 小时/周

Goodput = 1,000 × (168 - 3 - 6) / 168 ≈ 946 Token/秒
        ≈ 名义吞吐的 94.6%

读法:每 1% 的 Goodput 损失,交付日期直接滑 1%
     ——把保存频率调密、恢复流程调快,常常比加卡便宜得多
```

一个 MFU 45% 但每周三次故障、每次丢六小时的集群，和一个 MFU 38% 但稳如磐石的集群，谁先交付模型？——只有 Goodput 能回答。

### 5. 把可靠性写回预算

第 2 章研发账的表格里有一行"故障与重启：长训练必有中断，恢复点之前的进度是沉没卡时"——本章给它补上工程内容。可靠性决策的三个落点都会改写账单：**保存频率**决定单次故障丢多少步（存储与写入开销是它的价格）；**恢复速度**决定每次故障烧多少卡时（检测、重启、加载的总时长）；**拓扑余量**决定慢节点与局部故障能不能被隔离而不是拖垮全局。落到纸面：第 2 章的预测台账应该加一行"Goodput 假设 vs 实际"——预算时的 Goodput 假设、训练结束后的实际值、偏差原因（保存太稀？恢复太慢？慢节点太多？）。下次排期，这一行就是先验。

> **判断边界：**长训练的进度 KPI 是 Goodput，不是 MFU。MFU 量"跑的时候多满"，Goodput 量"这个月到底前进了多少"。把故障、重启、回退全部扣掉之后的速率，才是排期、预算与交付承诺的依据。

## 七、案例拆解：DeepSeek V4 的分阶段混合芯片栈

本章前六节的方法论，在 2026 年最有信息量的应用案例之一是 DeepSeek V4——不是因为它"新"，而是因为它把"训练系统 = 模型 × 硬件栈的联合设计"摆到了台面上。先把事实逐条摆正（每条带口径）：

| 事实 | 口径 |
|---|---|
| V4 约 1.6T 参数（总参口径），预训练数据超 32T Token | HF 模型卡 |
| V4 预训练以 NVIDIA 硬件为主，部分流程适配华为 Ascend | [MIT Technology Review](https://www.technologyreview.com/2026/04/24/1136422/why-deepseeks-v4-matters)（2026-04）报道 |
| V4-Pro 由华为牵头的深圳联合体用至少 1000 片 Ascend 芯片完成全参数后训练 | SCMP 2026-06 报道，转述口径，引用前应复核原文 |
| 第三方论文 SLAI T-Rex 在 Ascend NPU SuperPOD 上对 DeepSeek-V4 做端到端全参后训练，达到 34.22% MFU | [arXiv:2607.20145](https://arxiv.org/abs/2607.20145) |
| "V5 将在华为硬件上预训练" | 单源报道，计划性信息，不写成既成事实 |

叙事红线先立好：这套硬件栈必须写成**分阶段混合硬件**——预训练以 NVIDIA 为主、部分流程适配 Ascend；V4-Pro 的全参后训练由华为方用 1000+ 片 Ascend 完成。写成"完全国产化训练"或"完全去英伟达"都是错的；反过来写成"与国产硬件无关"也是错的。还有一条不可引用数字的警示值得记下：网传 V4 的"2.788M H800 GPU 小时"来自第三方 GitHub 仓库，非官方披露——训练系统的数字尤其要问"谁披露的"。

这个案例对训练系统设计的教益有三条：

- **跨芯片栈意味着账本全部重算**。四本显存账按新硬件的显存容量重算；通信拓扑按新的互联结构重排（NVIDIA 的 NVLink 机架域换成了 Ascend SuperPOD 的互联域）；精度方案按新芯片支持的数值格式重验——没有任何一本账可以平移。
- **34.22% MFU 的口径要读准**：它是**后训练阶段**、在 Ascend NPU SuperPOD 上端到端全参后训练的 MFU（论文口径），不能与预训练 MFU 直接横比——阶段不同、工作负载不同（后训练的显存与计算形态见 T06--T09）。
- **分阶段混合本身就是训练系统决策**：先用已验证的 NVIDIA 栈跑预训练（保交付），同时在 Ascend 上完成后训练的适配与放大（攒能力）——这是"账本先行、时间线裁决"的一次真实运用。

### 评审视角：如果会上有人提议"我们也上双芯片栈"

按本章的框架，追问的顺序应该是：一问**切分阶段**——哪个训练阶段先适配（先小规模验证还是先全参）；二问**基线口径**——两套栈各自的 MFU / Goodput 与精度验证是否已有一手基线（没有基线的"已适配"不能进决策）；三问**同构性**——两套栈的 checkpoint 五件套与数据管线是否可互切，故障恢复路径是否各自演练过；四问**退出条件**——出现什么信号时退回单栈。四问答齐，这个提案才从叙事变成方案。

> **架构智慧：**硬件异构不是立场叙事，是工程账。每多引入一种芯片栈，显存、通信、精度、监控、容错五套方案都要各自验证一遍；V4 选择"分阶段混合"而不是一刀切切换，正是把异构当风险管理的做法。

| vLLM | 高吞吐推理引擎 | 站在 Rollout 采样一侧；与训练引擎之间的 cross-engine 数据流（Policy Lag、Rollout 吞吐）是 T09 的主课题 |

框架是工程载体，不是架构决策本身——**"选哪个框架"从来不替代"切几维并行、用什么精度、怎么容错"这三层决策**；框架只是把你已经做出的决策配置出来。选型时问三个问题就够：一问**并行覆盖**，你的五维组合它是否都成熟支持（尤其 EP 与 CP 这两个 MoE 时代才变关键的维度）；二问**精度档位**，你要用的格式（含缩放管理）它是否有经过验证的实现；三问**可靠性**，它的 checkpoint 是否是五件套、恢复路径能否演练。三问之外才是生态与团队熟悉度。RL 训练侧的框架细节（veRL / slime / vLLM 如何组成异步拓扑）让位给第 9 章，本章只留坐标。

### 2. 一份最小配置如何映射到拓扑

把本章的推导收进一份与框架无关的伪配置，看每个字段落到哪里：

```text
# Distributed Training Configuration(骨架示意,字段与具体框架无关)
model:          594B 总参 / 17B 激活 MoE        # 口径:官方披露体量(Inkling 2 Small)
hardware:       GB300 NVL72 机架 ×1(72 卡)      # 口径:与官方账本同款机架形态
memory_budget:                                     # ← 第 2 节:账本先行
  params_bf16:      ≈1.19 TB                    # 教学估算
  grads_bf16:       ≈1.19 TB
  master_fp32:      ≈2.38 TB
  optimizer_fp32:   ≈4.75 TB                    # AdamW 两动量,8 字节/参数
  activations:      另算(重计算 on,长序列另开 CP)
parallel:        TP=2  PP=2  CP=1  EP=9  DP=2   # ← 第 3 节:组合随后;乘积 = 72 卡
precision:       BF16 权重/梯度 + FP32 主权重与优化器(教学保守档)
                # 实际项目:FP8 需过三层约束与验证门禁(第 4 节)
optimizer:       AdamW —— 或 Muon(2D)+AdamW(1D) 混合(第 5 节)
checkpoint:      每 1000 步异步分层保存,保留 3 代 + 每日 1 代(第 6 节五件套)
monitor:         MFU / Goodput / loss / 梯度范数 / 显存水位
recovery:        故障检测 → 回退最近好点 → 五件套恢复;恢复演练每季一次
```

读法对照：显存预算回答"装不装得下"；并行五元组回答"怎么乘出 72 卡、每种通信落在哪条网络"；精度与优化器两行是受控实验的结论，不是默认值；checkpoint 与 recovery 两行是时间线上的保险。**每一行都是前文一节的落点——这就是训练系统设计"可推导"的意思。**

## 九、工程产物：Distributed Training Configuration

上面那份伪配置的正式版，就是本章交付的工程产物。表格骨架如下（每个字段都要求填口径）：

| 板块 | 要填什么 | 示例与口径要求 |
|---|---|---|
| 模型形态 | 总参数 / 激活参数 / 层数 / 专家数 / top-k | 594B / 17B …（官方披露或设计值，注明） |
| 硬件 | GPU 型号 / 单卡显存 / 机内互联 / 跨机网络 / 机架形态 | GB300 NVL72 …（硬件代际决定精度档位） |
| 显存预算 | 四本账逐项估算 + 假设 | 教学估算口径：精度假设、优化器假设、是否含激活 |
| 并行维度 | TP / PP / CP / EP / DP 各维取值与乘积 | 乘积 = GPU 总数；标注每种通信落哪条网络 |
| 通信拓扑 | 机内域与跨机域各承担什么流量 | 专家路由 All-to-All 必须落在高带宽域 |
| 数值精度 | 各张量格式 / 缩放策略 / 验证门禁与回退条件 | 降档必须附对照实验结论 |
| 优化器 | 类型 / 参数形状分工 / 学习率日程 / 裁剪 / 权重衰减 | Muon 限 2D；微调另有结论 |
| Checkpoint | 五件套清单 / 保存频率与分层方式 / 保留代数 / 演练周期 | 单份体积估算与存储账 |
| 监控指标 | MFU / HFU / Goodput / loss / 梯度范数 / 显存水位 | 每个指标写口径 |
| 故障恢复 | 检测 → 回退 → 恢复流程与职责 | 回退最近好点的判据 |

三条使用纪律：**每个数字标注身份**（官方披露 / 第三方估算 / 本文估算 / 假设场景，四选一，与第 2 章预算表同款纪律）；**输出必含失败模式**（哪种故障最可能发生、单次损失多少、恢复要多久）；**与 Training ADR 对接**——这份配置直接填进引言 ADR 骨架的第 5 段（决策：并行、精度和可靠性方案）与第 6 段（系统影响）。

> **判断边界：**Distributed Training Configuration 的价值不在"配置正确"——训练系统没有一次写对的配置——而在于每个字段带口径、每个决策可追溯：并行组合怎么解出来的、精度档位过没过门禁、恢复演练在什么时候。能被同事复算并挑错的配置，才配得上几千卡跑几周的投入。

## 十、六种最常见的错误判断

### 错误 1：抄论文里的 GPU 数量，不抄它的切分约束

GPU 数量是"模型形态 × 硬件 × 互联"解出来的积，不是超参数。同一份模型，在 NVLink 机架和普通以太网集群上解出的并行组合完全不同。**纠正动作**：看到任何 GPU 数，先问它的五维并行各是多少、每种通信走哪条网络。

### 错误 2：把 MoE 当 Dense 切

MoE 的持续 All-to-All 专家路由流量和负载均衡问题，Dense 的"每步一次梯度同步"模型完全覆盖不了；忽略 EP 的拓扑，通信一定成为瓶颈。**纠正动作**：MoE 拓扑设计从 EP 开始倒推（专家分组决定机架内布局），而不是从 DP 开始。

### 错误 3："上了 FP8 就省一半"

三层约束（硬件代际、框架与缩放实现、模型稳定性）缺一层，"省一半"就停在硬件口径，进不了账单；FP4 训练更是前沿实践——Inkling 的 NVFP4 配方细节官方尚未披露，照抄无从谈起。**纠正动作**：每次精度降档配一次对照实验与回退条件，写进配置。

### 错误 4：Checkpoint 只存模型权重

权重只是五件套之一。缺优化器动量、数据游标、RNG 或调度状态，恢复出来的就是一个"失忆、复读、不可复现"的训练，loss 跳变只是最早的症状。**纠正动作**：五件套清单进配置；恢复路径按季度演练。

### 错误 5：拿 MFU 当唯一 KPI，不看 Goodput

MFU 量的是"跑的时候多满"，故障、重启、回退吞掉的进度它完全看不见。长训练的排期、预算与交付承诺必须用 Goodput 口径。**纠正动作**：监控面板上 MFU 与 Goodput 并排；汇报训练进度时报"本月有效前进步数"。

### 错误 6：把框架当架构决策

"我们用 torchtitan / Megatron"回答不了切几维并行、什么精度、怎么容错——框架是载体，决策在配置里。反过来，把 Megatron-LM（仓库）与 Megatron-Core（组件库）混称、把 RL 框架与训练框架混称，都是信号：讨论还没落到决策层。**纠正动作**：评审时先看 Distributed Training Configuration，再看用什么框架实现。

## 本章小结

- 先列参数、梯度、主权重、优化器和激活的占用，再决定分片、并行、卸载与重计算。
- 并行与精度方案都在交换成本：省显存可能增加通信，提高峰值吞吐也可能增加数值风险。
- 同时看 MFU、吞吐与有效产出，并验证 Checkpoint 能恢复。配置表要记录资源假设和实测结果。

> **下一章的问题：**预训练得到的是基础能力。要让模型按照指定方式回答、推理和执行任务,需要选择合适的学习信号。先从示范学习开始。

## 基础术语速查

| 术语 | 初学者可以先怎样理解 |
|---|---|
| 显存四账 | 参数、梯度、优化器状态、激活（含临时 Buffer）——训练时同时住在显存里的四类东西 |
| 数据并行（DP） | 每卡一份完整模型，各吃不同数据，每步同步一次梯度 |
| 张量并行（TP） | 把单层权重矩阵切开、多卡合力算一层；通信高频小消息，适合机内 |
| 流水线并行（PP） | 把层切成连续阶段、各卡负责一段；阶段之间只传激活 |
| 上下文 / 序列并行（CP） | 把一条长序列切开多卡协作，对付长序列的激活爆炸 |
| 专家并行（EP） | 把 MoE 专家分到不同卡；Token 路由产生持续的 All-to-All 流量 |
| ZeRO / FSDP | 把参数、梯度、优化器状态切片摊到所有卡的思路与实现，用通信换显存 |
| 重计算（激活检查点） | 前向只存边界、反向重算中间结果，用计算换激活显存 |
| 梯度累积 | 小批多次累积再一次更新，等效大 batch 而不爆显存 |
| 混合精度与缩放（Scale） | 不同张量用不同精度，靠缩放因子防上溢 / 下溢 |
| MFU / HFU / Goodput | 有用计算÷峰值、实际执行计算÷峰值、扣除故障后的有效进度速率——三个不同的刻度 |
| Checkpoint 状态机 | 权重 + 优化器状态 + 数据游标 + RNG + 调度状态五件套，及其保存 / 校验 / 回退 / 恢复流程 |
