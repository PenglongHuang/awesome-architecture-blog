> 一句话点题：**模型架构不是追逐最新结构，而是在能力、训练成本、推理延迟、显存、上下文和部署约束之间做联合权衡——容量、窗口与模态三笔账互相改写，谁也不能单独拍板。**

---

> **🧠 基础模型训练决策专题 第 4 章 · 本章只练一件事**
>
> 上一章（T03）把数据配方定下来之后，模型「学什么」已经确定；接下来要回答的是模型「如何表示和处理这些信息」——这正是上一章章末留下的钩子，本章就站在这个决策现场。在引言的八层坐标系里，本章展开第①⑥⑦⑧层的交点：从能力目标与部署约束（①）出发，决定模型本体怎样计算（⑥）——Dense 还是 MoE、注意力走哪条路、上下文开多大、模态怎么进——再把它翻译成显存、通信与延迟的约束（⑦），最后用一份 Architecture ADR 留下可复盘的决策证据（⑧）。读完本章，你应该能把「我们用什么骨架」从一句口号，改写成一张三笔账齐全、别人能挑错的架构决策记录。

## 开场：同一个任务，三份对不上的报价单

上一章结束时留下的话是：「数据决定模型「学什么」，但模型的容量、注意力和模态结构决定它「如何表示和处理这些信息」。下一章进入模型骨架设计。」现在，我们已经在骨架设计的现场了。

假设你的团队要交付一个**中文企业智能体**：读合同与财报（输入常到几十万 Token）、看图表与系统截图（多模态输入）、企业内高并发在线服务，私有化部署是加分项。你收到三份骨架报价：

| 报价 | 骨架方案 | 卖点 | 数字口径 |
|---|---|---|---|
| A「旗舰同款」 | 2.8T 总参 / 104B 激活 MoE，896 个专家每 Token 选 16 个；标称 1M 上下文；原生多模态；开放权重 MXFP4 量化 | 「每 Token 只激活 3.7%，推理最便宜」 | Kimi K3 技术报告披露值（[arXiv:2607.24653](https://arxiv.org/abs/2607.24653)，2026-07） |
| B「省推理」 | 744B 总参 / 40B 激活 MoE；DSA+MLA 注意力；预训练 28.5T Token | 「稀疏注意力让长上下文计算大降」 | GLM-5 技术报告披露值（[arXiv:2602.15763](https://arxiv.org/abs/2602.15763)） |
| C「便宜可控」 | 30B Dense + 视觉连接器 + 128K 窗口 + 检索（RAG） | 「你们根本用不到 1M，总拥有成本最低」 | 教学合成场景，数字为示意 |

评审会现场大概是这样：A 的方案经理指着**激活比例**说推理便宜；B 的方案经理指着**注意力折扣**说长上下文划算；C 的方案经理指着**总价**说你们被参数量绑架了。

吵不下去的原因只有一个：**三方报的根本不是同一本账。** A 在报容量账里的一个比例，B 在报窗口账里的一项折扣，C 在报三本账的合计。容量、上下文、模态这三笔账互相改写——激活参数决定每 Token 计算量，总参数决定装载显存，注意力结构决定长上下文的经济性，模态路线决定窗口预算和数据配方（上一章的产出在这里被改写）。任何一本单独拍板，都会在另外两本上翻车。

```text
评审会现场的三本账错位：
    A 报容量账里的一个比例（激活 3.7%）
    B 报窗口账里的一项折扣（1M 注意力约省 2.9 倍，同系 GLM-5.2 第三方拆解口径）
    C 报三本账的合计（总拥有成本）
        ↓
    三个数字都对，但不在同一本账上——无法直接比较
        ↓
    本章的任务：给任何一份骨架方案统一度量衡，
    再判断它在你这组约束下是否成立
```

还有一个更隐蔽的问题：A 的卖点本身就是个口径游戏。3.7% 是**比例**，104B 是**绝对值**——每个 Token 动用的参数仍是 B 方案（40B 激活）的 2.6 倍。T02 引用过的官方 API 标价正好给出刻度（口径：每百万 Token，输入 / 输出）：GLM-5 为 $1.0 / $3.2，Kimi K3 为 $3 / $15——激活参数更多的模型，每 Token 价格确实更贵。**比较推理成本要看激活参数的绝对值，激活比例只说明「这个模型相对自己的总容量有多省」。**

> **本章只解决一件事：给定任务与部署约束，如何选择 Dense / MoE、注意力结构、上下文长度和多模态路线？**

本章的推导路线，也是三笔账的展开顺序：

```text
第 1 节   统一度量衡：三笔账怎么读（参数口径复习）
    ↓
第 2 节   容量账：Dense 与 MoE 是两种成本结构，不是大小之分
    ↓
第 3 节   窗口账：压缩、稀疏、线性是三条路，不是一级级台阶
    ↓
第 4 节   模态账：原生与连接器，以及「它真的在看图吗」
    ↓
第 5 节   三笔账互相改写：架构是一张依赖图，不是技术清单
    ↓
第 6 节   Architecture ADR：把骨架决策写成可复盘的文档
```

## 一、统一度量衡：容量、窗口、模态三笔账怎么读

### 1. 先把 T02 的参数口径带过来

T02 已经立过规矩：MoE 模型的参数必须双口径记账。本章把它变成架构决策的第一块度量衡：

| 口径 | 回答什么 | 对应哪本账 |
|---|---|---|
| 总参数 | 模型装了多少东西 | 装载显存、权重体积、部署门槛 |
| 激活参数 | 每个 Token 实际动了多少参数 | 每 Token 计算量、推理成本方向 |
| 注意力结构 | 每个 Token 回看历史的方式 | 长上下文的计算与 KV Cache 显存 |
| 模态结构 | 非文本输入怎么变成 Token | 数据配方、窗口预算、训练阶段 |

架构决策就是在这四行之间同时求解，而不是在某一行里找最大值。

### 2. 三笔账各自的「记帐单位」

```text
容量账：总参数 → 显存与权重体积
         激活参数 → 每 Token 计算（≈推理单价的方向）
    ↓
窗口账：注意力结构 → 长上下文的计算曲线与 KV Cache 体积
         标称上下文 → 有效上下文（要打折）→ 并发（抢同一块显存）
    ↓
模态账：原生 / 连接器 → 数据配方（T03 的产出被改写）
         视觉 Token 预算 → 挤占窗口账
    ↓
三笔账都过一遍，才叫「看过这份架构方案」
```

### 3. 用三笔账重读开场的报价单

| 账本 | 报价 A（K3 同款） | 报价 B（GLM-5 同款） | 报价 C（30B Dense，教学示意） |
|---|---|---|---|
| 容量：装载 | 2.8T 总参，最重；开放权重体积按第三方报道约 5.6TB | 744B 总参，较重 | 30B 总参 = 30B 激活，最轻 |
| 容量：每 Token 计算 | 104B 激活，三份中最贵 | 40B 激活 | 30B 激活，最便宜 |
| 窗口 | 标称 1M；KDA/AttnRes 混合线性路线 | DSA+MLA；同系 GLM-5.2 加 IndexShare 后 1M 经济性改善 | 128K；长文档靠检索切片 |
| 模态 | 原生多模态（官方报告口径） | 报告以文本能力为主，多模态路线需另行确认（以对应官方文档为准） | 连接器路线，「是否真的用图」要自己验 |
| 部署门槛 | TB 级权重，消费级硬件难以本地部署（第三方报道口径） | 中等 | 最低，量化后可单机跑（示意） |

注意这张表**没有选出赢家**——它只把每份报价的前提摆到了同一张桌面上。A 的「激活便宜」被 104B 绝对值和 5.6TB 权重对冲；B 的「注意力省」要等到下一节才知道省的是哪一段；C 的「便宜」要拿「128K + 检索能不能撑住合同问答」来换。裁决属于第 5 节的依赖图和第 6 节的 ADR，不属于任何单一指标。

### 4. 开工前的概念排雷：骨架讨论的三种常见错位

引言（T01）把「架构」拆成三种：模型架构（本章）、训练方法（T06–T09）、训练系统（T05）。骨架评审会上最常见的三个错位，恰好都发生在这个分界线上：

| 错位说法 | 它混淆了什么 | 正确的问法 |
|---|---|---|
| 「换成 MoE，训练会不会更好收敛？」 | 模型架构 × 训练方法：MoE 改变每 Token 动用哪些参数，不直接改变「按什么信号更新参数」 | 「MoE 改变了计算图与通信，我的训练系统（T05）和优化配置跟得上吗？」 |
| 「上了 DSA，训练系统是不是就简单了？」 | 架构 × 系统：稀疏注意力压的是长上下文计算，却新增了 indexer 组件并把瓶颈推向 KV Cache 与 kernel | 「注意力省下来的账，转移到系统层哪一项？谁来付？」 |
| 「多模态不就是数据的事吗？」 | 跨层：模态路线既改数据配方（T03），又改骨架（编码器、连接器）、窗口预算与训练阶段 | 「原生还是连接器？改写的是预训练还是后训练？验收证据是什么？」 |

排雷的意义在于：骨架是**改写者**——它改写数据配方、训练系统、推理账单与验收方式，但每一样被改写的东西都有自己的主归属章。本章负责把改写关系画清楚，被改写的细节到对应章节展开。

> **架构智慧：**架构评审吵不起来的时候，通常不是缺数字，而是每方手里只有一本账。先把容量、窗口、模态三本账摊开，让每个数字都注明口径，「A 还是 B」才有机会变成「在哪个约束下 A、在哪个约束下 B」。

## 二、容量账：Dense 与 MoE 是两种成本结构，不是大小之分

### 1. 先建立直觉：全科诊所与分诊医院

**Dense（稠密）模型**像全科诊所：每个 Token 进来，都要看完全部参数——参数有多少，每个 Token 的计算就有多少。参数与计算 strictly 绑定，账最好算：总参数 = 激活参数。

**MoE（Mixture of Experts，混合专家）模型**像分诊医院：一个**路由器（Router）**先给每个 Token 做分诊，把它送到最相关的少数几位**专家（Expert）**那里，其余专家不参与这一次计算。被选中的专家数由 **Top-K 路由**决定。

[Kimi K3 技术报告](https://arxiv.org/abs/2607.24653)披露的配置是现役最大刻度：**2.8T 总参数、104B 激活参数、896 个专家中每 Token 激活 16 个**——每个 Token 有 16 位专家会诊，激活比 104 ÷ 2800 ≈ 3.7%（口径：官方报告披露值）。

MoE 的赌注在于：**容量（知道的东西）与每 Token 计算（动用多少东西）被解耦了**。总参数可以堆到 2.8T 去买知识容量，而每个 Token 只花 104B 的计算。这正是 T02 Chinchilla 边界二（MoE 的分母不能直接套 Dense 配比）的结构性原因。

### 2. 2026 年现役 MoE 配置区间：一张表读出趋势

把证据库里 2026 年现役、有官方口径的 MoE 放在一起（激活比由「激活 ÷ 总参」自算，四舍五入）：

| 模型 | 总参数 | 激活参数 | 激活比 | 口径来源 |
|---|---:|---:|---:|---|
| Kimi K3（2026-07） | 2.8T | 104B | ≈3.7% | [官方技术报告](https://arxiv.org/abs/2607.24653) |
| Qwen3.8-Max（2026-08） | 2.4T | 约 95B | ≈4.0% | [官方博客](https://qwen.ai/blog?id=qwen3.8)；Max 级首次开放权重 |
| Mistral Large 4（2026-10） | 1.05T | 52B | ≈5.0% | [官方开源公告](https://mistral.ai/news/mistral-large-4-oss)；官方仓库名即 1T-A52B（媒体流传的 49B 口径不准确） |
| GLM-5（2026-02） | 744B | 40B | ≈5.4% | [官方技术报告](https://arxiv.org/abs/2602.15763) |
| Ling-3.2-flash | 560B | 25B | ≈4.5% | 任务书锚点，以对应官方文档为准 |
| ERNIE-5.5-Flash-Base | 280B | 14B | ≈5.0% | 任务书锚点，以对应官方文档为准 |
| Inkling 2 Small（2026-11） | 594B | 17B | ≈2.9% | [官方页面](https://thinkingmachines.ai/news/inkling-2-small) |
| （对照）DeepSeek-V3（2024-12） | 671B | 37B | ≈5.5% | 历史锚点 |
| （对照）GLM-4.5（2024） | 355B | 32B | ≈9.0% | 历史锚点；GLM-5 报告称从 355B/32B、23T Token 扩展到 744B/约 40B、28.5T Token |

两个趋势直接从表里读出来：

- **总参数迈入 0.7T–2.8T 量级**：2024 年的代表是 355B–671B，2026 年的开源旗舰普遍翻了一个台阶；
- **激活比压到约 3%–6% 区间**：2024 年 GLM-4.5 还在 9%，2026 年普遍腰斩——**容量涨了，每 Token 计算量几乎没涨**。这就是 MoE 在 2026 年成为旗舰默认形态的经济学原因：它把 T02「推理摊销账」里最贵的那一项（每 Token 成本）按住了。

**它意味着什么**：同样对标一个能力目标，2026 年的做法不是「把 Dense 训到 2T」，而是「总参堆到 2.8T 买容量、激活压到 4% 买推理」——两本账分开记，各买各的。

### 3. 激活比低 ≠ 成本按比例降：三笔被转移的账

如果激活只有 3.7%，成本是不是也降到 3.7%？不是。MoE 省下的是每 Token 的**计算账**，同时新增或加重了三笔别的账：

| 被转移的账 | 机制 | 现役刻度 |
|---|---|---|
| 显存与权重账 | 推理服务必须把**全部**专家装进显存（或可路由的显存池），不管每个 Token 用不用 | K3.1 Pro（与 K3 同底座）的开放权重体积按第三方报道约 5.6TB（[报道口径](https://www.ithome.com/1/022/490.htm)，2026-11），消费级硬件难以本地部署 |
| 负载均衡账 | 请求分布不均 → 热专家排队（长尾延迟）、冷专家占着显存不出力；训练时还要额外加均衡目标防止路由坍缩 | 定性机制；具体均衡策略以各官方报告为准 |
| 通信账 | 专家分布在多卡多机上，Token 要被「寄」到专家所在的卡，产生 all-to-all 通信 | 2026 年的生产做法是 wide expert parallelism 横跨 NVL72 机架级系统（[NVIDIA 官方博客](https://developer.nvidia.com/blog/scaling-large-moe-models-with-wide-expert-parallelism-on-nvl72-rack-scale-systems)口径）；机制在 T05 展开 |

一句话：**MoE 不是「同样的模型打个 3.7 折」，而是「用显存账和通信账换计算账」。** 换得划不划算，取决于你的部署形态——高并发云端 API 通常换得值（每 Token 成本每月都在发生），单机私有化部署可能换亏（5.6TB 的装载门槛直接劝退）。

### 4. 路由参数怎么定：专家粒度、Top-K 与稳定性

「用 MoE」只是开始，配置才是决策：**多少个专家、每个 Token 选几个、粒度多细**。这三件事互相咬合：

| 设计变量 | 一端 | 另一端 | 交换什么 |
|---|---|---|---|
| 专家数量 / 粒度 | 少而大（如 8 个大专家，Mixtral 时代做法，历史锚点） | 多而小（K3 的 896 个，细粒度） | 细粒度组合更灵活、容量利用率高，但路由与通信更碎、系统更复杂 |
| Top-K | 小 K（如 2） | 大 K（如 K3 的 16） | K 越大每 Token 计算越多、越接近 Dense 的稳，K 越小越省但知识覆盖窄 |
| 路由稳定性 | — | — | 训练早期路由抖动会让专家分工反复洗牌，需要均衡目标约束（定性机制，具体做法以各官方报告为准） |

**粒度方向有研究证据**：T02 引用过的[细粒度 MoE Scaling 律](https://arxiv.org/abs/2402.07871)（2024）给出两个方向——最优 Token : 激活参数比随规模上升而下降（实验范围内 6.4B 激活约 44:1，到 64T 总参 / 1T 激活时降到约 8:1）；更高的专家粒度在大算力下更优。2026 年现役旗舰普遍的「数百个专家、低激活比」配置（K3 的 896 选 16）与这个方向一致——但注意这是研究结论加现役观察的拼图，不是任何一家官方披露的「我们按这条律配置」。

**它意味着什么**：路由配置不是从论文里抄一组数字，而是把「容量利用率（粒度）、每 Token 成本（K）、系统复杂度（通信与均衡）」三个旋钮一起拧。配置一旦定死，改它几乎等于重训——这是它必须进 ADR 的原因。

### 5. Dense 未死：什么时候简单结构反而赢

2026 年的旗舰榜单上确实难见 Dense，但「Dense 已淘汰」是误读。**中小规模与微调场景仍常用 Dense**——这是分类学纪律，不是怀旧。

Dense 赢在三个地方：

- **系统简单**：没有路由、没有专家并行、没有负载均衡目标，训练栈和推理栈都轻。对中小团队，「能跑稳」比「单位算力最优」值钱；
- **微调友好**：LoRA / 全参微调的生态在 Dense 上最成熟，行为最好预测（微调场景的写入深度问题在 T06 展开）；
- **部署轻**：总参 = 激活，权重体积直接对应模型规模，量化部署路径清晰。T02 的端侧案例 LFM2.5-350M（28T Token、约 80,000:1 过度训练）就是 Dense 在端侧形态下的胜利——体积上限锁死参数，剩余预算全换 Token。

再用一个教学对照把「赢在哪里」量化（配置为教学示意，方法照搬 T02 的三本账视角；同族对比也可回看 T02 的方案 B/C 裁决）：

| 配置（教学示意） | 30B Dense | 100B Dense | 60B-A6B 小型 MoE |
|---|---:|---:|---:|
| 每 Token 计算（激活口径） | 30B | 100B | 6B，三档最省 |
| 装载显存（总参口径） | 30B，最轻 | 100B | 60B，且需多卡放专家 |
| 微调生态 | 成熟、行为可预测 | 成熟 | 路由与专家的微调有额外功课 |
| 系统复杂度 | 最低 | 低 | 路由 + 专家并行 + 负载均衡 |
| 适用域 | 端侧 / 私有化 / 微调主力 | 低请求量一次性训练 | 高并发云端服务 |

读法：小型 MoE 的每 Token 成本优势真实存在（6B 对 30B），但要为它付通信账、均衡账和系统复杂度——**交换是否划算由部署形态决定，不由结构先进性决定。**

历史锚点：Llama 3 405B（2024）常被当作「Dense 旗舰时代」的收官之作；此后开源旗舰阵营整体转向 MoE。收官不等于消失——正如 Mixtral 8x7B 是「最早开源 MoE」的历史锚点，Dense 与 MoE 是两种成本结构，各自有各自的适用域。

> **判断边界：**「选 MoE 还是 Dense」的正确问法不是「谁更先进」，而是「我的部署形态愿意付显存账和通信账吗」。高并发云端服务、请求量大、集群互联好——MoE 的交换通常划算；单机部署、中小规模、微调为主、团队系统经验有限——Dense 常常是更诚实的答案。

## 三、窗口账：压缩、稀疏、线性是三条路，不是一级级台阶

### 1. 先建立直觉：为什么上下文一长，成本就爆炸

自回归生成的每一步，注意力都要拿「新 Token 的查询」去和**全部历史 Token** 算相关性。为了不重复计算，推理系统把每层每个历史 Token 的键（K）与值（V）缓存下来——这就是 **KV Cache**。

```text
生成第 N 个 Token 时：
    新 Token 的 Query
        ↓ 逐层
    与 KV Cache 里全部历史 Token 的 K/V 做注意力
        ↓
    朴素注意力的计算量随上下文长度平方增长（O(L²) 量级）
    KV Cache 的体积随上下文长度线性增长（O(L) 量级）

推理两阶段：
    Prefill（预填充）：一次性并行处理输入 —— 算力密集，吃长输入
    Decode（解码）：逐 Token 生成 —— 访存密集，吃 KV Cache
```

三条成本曲线叠在一起，长上下文的账就清楚了：

- **计算账**：注意力计算随长度平方涨（朴素口径）——Prefill 变慢；
- **显存账**：KV Cache 随长度线性涨——它和**并发路数**共享同一块显存池，此消彼长；
- **延迟账**：每个生成 Token 都要扫一遍历史——Decode 变慢。

2026 年的注意力结构创新，全部是在这三条曲线上做手术。但手术有三种，经常被混成一种。

### 2. KV Cache 的算术：同一块显存的三方分账

长上下文为什么挤占并发？把显存池的分配算一遍就清楚了。先给口径：每 Token 的 KV Cache 体积 ≈ **2（K 与 V）× 层数 × KV 头数 × 每头维度 × 每参数字节数**。用一组纯教学示意的配置（30B Dense、60 层、GQA 8 个 KV 头、每头 128 维、FP16 即 2 字节；不是任何真实模型）：

```text
每 Token KV ≈ 2 × 60 × 8 × 128 × 2 字节 ≈ 240 KB（教学示意）

单路并发 @ 128K 上下文 ≈ 240KB × 131,072 ≈ 30 GB
单路并发 @ 1M 上下文   ≈ 240KB × 1,048,576 ≈ 240 GB ← 单卡放不下一路

显存池三方分账（同一张卡）：
    权重（总参数口径，全专家常驻）
  + KV Cache × 并发路数（随窗口与并发双线性增长）
  + 激活与运行时开销
    = 显存供给
```

三个结论直接从算术里掉出来：

- **窗口与并发是一根跷跷板**：显存池固定，窗口从 128K 提到 1M（×8），每路 KV Cache 也 ×8，并发预算就 ÷8——这就是「长上下文能力提升后并发可能下降」的机制层答案；
- **压缩 KV 的家族（MQA/GQA/MLA）买回的是并发**：若结构把每 Token KV 压到 1/8，同样显存下并发 ×8（比例示意）——它们压的是显存曲线，不是计算曲线；
- **稀疏家族（DSA 类）压的是访问与计算**：KV 还是那些 KV，但每步只访问 top-k 个 Token 的条目，Decode 的访存与 Prefill 的计算都按 k 封顶——所以 GLM-5.2 省完计算之后，瓶颈才转移到「KV Cache 还装不装得下」（第三方估算 830–950GB 一档）。

这也解释了为什么真实的长上下文服务必然多卡：按第三方估算，GLM-5.2 以 FP8 权重 + FP8 KV Cache 服务长上下文要约 830–950GB 显存——单卡显存（教学示意配置下连一路 1M 都装不下）撑不起这个预算。**每个关键数字都要问一遍口径：这是每 Token 体积、单路总体积，还是整池供给？**三者差着量级。

### 3. 分类学纪律：三个家族，不许写成升级路线

这是本章最容易写错的一张表（分类学纠正依据：2026 年的分类学专文与现役模型配置，[Raschka 注意力变体指南](https://magazine.sebastianraschka.com/p/visual-attention-variants)）：

| 家族 | 机制一句话 | 代表 | 它压哪条曲线 |
|---|---|---|---|
| **压缩 KV 的 dense 注意力** | 仍然看**全部**历史 Token，但把每个 Token 存的 K/V 压小 | MQA / GQA（多查询/分组查询，共享 KV 头）；MLA（低秩压缩，DeepSeek 系列引入并发扬——V3 为历史锚点） | 显存曲线：KV Cache 变小；**计算仍是平方量级** |
| **稀疏注意力（先选再看）** | 先为每个查询挑出 top-k 个相关 Token，注意力只对它们做 | DSA（DeepSeek Sparse Attention，V3.2 于 2025-12 首发生产化）；GLM-5.2 的 IndexShare | 计算与访存都按 k 封顶；k 固定，长度再涨也不爆 |
| **线性 / 亚二次注意力** | 把「看全部历史」改写成固定大小状态的递推更新 | KDA（Kimi Delta Attention，delta-rule 类）；LongCat-Flash 的 MixLinear；gpt-oss 的 half-dense 属混合分支 | 计算近线性、状态恒定；代价是固定状态带来的遗忘与召回权衡 |

**分类学红线**：DSA 是稀疏注意力，MLA 是压缩的 dense 注意力，**两者都不属于线性（亚二次）注意力**；2026 年真正进入万亿级开源权重的混合线性注意力实例，是 Kimi K3 的 KDA（delta-rule 类）与 AttnRes。把「标准注意力 → MLA → DSA → 线性注意力」写成一条升级路线，等于把三条不同的路画成一级级台阶——这是本章指定的错误判断第一名。

三条路的正确画法是并列的取舍：

```text
同一个问题：上下文变长，注意力太贵
    ├── 路线一：KV 存小一点（MLA/GQA）——还是全看，只是看得省
    ├── 路线二：只看相关的那 k 个（DSA/IndexShare）——先选再看
    └── 路线三：不存历史、存状态（KDA/MixLinear）——近线性，但可能忘
生产现实（2026）：「MLA 压缩 + 稀疏 top-k 选择」为主流组合，
                  线性/混合为差异化分支；谁能成为默认，尚无定论
```

### 4. 案例拆解：稀疏注意力的生产化链条

这条链条的每一环都有官方口径，适合整段读一遍。

**第一环：DeepSeek V3.2 首发 DSA（2025-12）。** DSA 的机制可以概括为「Lightning Indexer + top-k 选择」：一个索引器先为每个查询挑出最相关的少量 Token，注意力只对它们做（机制解读见 [DSA 专题](https://www.emergentmind.com/topics/deepseek-sparse-attention-dsa)）。关键细节：DSA 与 MLA **叠加**而非取代——MLA 管「每个 Token 的 K/V 存多小」，DSA 管「这次看哪些 Token」，一个压缩存储、一个裁剪访问，互不替代。这个组合方式本身就是分类学的一课。

**第二环：GLM-5 采用 DSA+MLA（2026-02）。** [GLM-5 技术报告](https://arxiv.org/abs/2602.15763)披露其注意力采用 DSA+MLA 组合（口径：官方报告）。同一家族的结构决策在一代模型间延续并深化，说明稀疏路线已过生产验证。

**第三环：GLM-5.2 引入 IndexShare（2026-06）。** [官方博客](https://z.ai/blog/glm-5.2)披露的这项设计，让**一个 indexer 服务一组层、跨层共享 Token 选择**——不是每层各自选一遍，而是一组层共用一份「该看哪些 Token」的名单。按第三方拆解口径（[拆解文](https://sebastianraschka.com/blog/2026/glm-5-2-indexshare.html)）：每个查询只对 top 约 2048 个 Token 做完整注意力，1M Token 上下文时注意力计算量约减少 2.9 倍（该倍数与 top-k 数值为第三方拆解口径，引用前以官方原文为准）。

第三环最有教学价值的不是省了多少，而是**瓶颈转移**：注意力计算降下来之后，GLM-5.2 的推理瓶颈被推向 KV Cache 容量、长上下文 kernel 与 CPU 侧开销——**注意力省了，系统没省**。这正是「架构决策改写训练系统」的实例，系统侧的解法属于 T05。

**另一条路的同行者：Kimi K3（2026-07）。** K3 没有走 DSA 路线，而是用 **KDA（delta-rule 类线性注意力）与 AttnRes（Attention Residuals）**——把部分注意力层改写成固定状态的递推更新（「新信息进来时按差值更新记忆」），与完整注意力混合使用。这是万亿级开源权重里真正的混合线性实例。纯线性层仍有遗忘问题（NSA / laNSA / NHA 等混合设计多在研究侧），所以「混合」是当下的稳妥形态——线性路线能否从差异化分支变成默认，尚无定论。

> **架构智慧：**两条路线（稀疏选择与混合线性）都在解「长上下文的算术问题」，但手术位置不同：一个裁剪「看多少」，一个改写「怎么记」。评审注意力方案时，第一问永远是「它在压哪条成本曲线，代价转移到了哪里」——而不是「它比上一个结构新多少」。

### 5. 1M 上下文的落地现状：标称 ≠ 有效 ≠ 便宜

2026 年，1M Token 上下文已生产可用（口径：各官方文档与[窗口汇总页](https://codingscape.com/blog/llms-with-largest-context-windows)）：

| 模型 | 标称上下文 | 备注 |
|---|---:|---|
| Gemini 2.5 Pro | 2M | 汇总页口径，以官方文档为准 |
| Claude Opus 4.6 | 1M | 聚合页转述口径，引用前需对 Anthropic 官方页核实 |
| Kimi K3 | 1M | 官方报告口径 |
| DeepSeek | 1M | 输出上限 384K（汇总页口径） |
| GLM-5.2 | 面向长程任务 | 官方博客口径，配 IndexShare |

但「已生产可用」要配三个必须写的口径：

- **标称 ≠ 有效**。窗口是输入与输出**共享**的：标称 1M、输出上限 128K 的模型，实际可用输入约 870K（1M − 128K ≈ 870K）；输出上限越大，可用输入越小。社区普遍认为标称 1M 对多数场景名不副实——有效上下文还要打折于任务的检索与多跳能力（T03 的 fertility 口径是另一重折扣：同样十万字，不同词表切出的 Token 数差一倍以上）。
- **长上下文 ≠ 便宜**。按第三方估计口径，GLM-5.2 以 FP8 权重 + FP8 KV Cache 做长上下文服务，约需 830–950GB 显存（[第三方估算](https://www.mindstudio.ai/blog/glm-5-2-architecture-index-share-sparse-attention)）——单卡放不下，多卡才跑得起来。
- **窗口军备正在降温**。2026-01 的行业判断是窗口数字增长趋缓，重心转向推理时扩展与上下文管理（Compaction / 检索式记忆）——把「更大的窗口」换成「更会用窗口」，长程任务的上下文管理在 T09 展开。

### 6. 长上下文 vs 检索：不是二选一

「上 1M 窗口还要不要 RAG」是报价单 C 与 A 争论的延续。决策变量有四个：

| 变量 | 偏向长上下文 | 偏向检索（RAG） |
|---|---|---|
| 单次材料量 | 几十万 Token 级、必须全息交叉引用（合同比对） | 海量语料、每次只需少量片段 |
| 访问模式 | 反复回看同一批材料 | 一次查询、命中即走 |
| 延迟与成本预算 | Prefill 变慢、KV Cache 变大都能接受 | 首 Token 延迟敏感、按 Token 计费敏感 |
| 正确性口径 | 「模型看过全文」可审计 | 「检索没漏」需要另外证明 |

Agent 长程任务中两者常与 Compaction 组合使用（上下文写满前先压缩），这是 T09 的决策现场。本章只立一条纪律：**窗口大小是架构决策，检索与否是系统决策，两者一起决定「模型实际能看到什么」**——后者又回头改写数据与评测口径。

### 7. 有效上下文怎么测：三类证据的层级

「有效上下文」不是算出来的，是测出来的。评测证据分三层，一层比一层接近真实负载（方法性框架，不引用具体基准分数）：

| 层级 | 测什么 | 局限 |
|---|---|---|
| 单点检索类（大海捞针型） | 在长文档深处埋一个事实，问模型能否找到 | 必要非充分：找到一根针 ≠ 理解全文档 |
| 多跳 / 交叉引用类 | 答案需要把散在文档各处的两三个事实串起来（合同条款互引、财报勾稽） | 更接近文档任务，但仍是人工构造 |
| 长程任务类 | 真实多轮负载下的表现（工具链、状态保持） | 与上下文管理策略（Compaction）混在一起，归因要小心 |

两条口径纪律：**报告窗口能力必须带任务类型与评测设置**（哪一层、什么长度、什么位置分布），跨模型比较才有意义；**针测全对不等于交叉引用全对**——把第一层满分当「有效上下文 = 标称上下文」的证明，是产品承诺缩水的常见起点。

> **判断边界：**标称上下文是厂商口径，有效上下文是产品口径，部署成本是账本口径。向业务方承诺「能读一百万字」之前，三个口径都要过一遍——窗口共享规则、词表 fertility、输出上限、显存预算，任何一处都会让承诺缩水。

## 四、模态账：原生与连接器，以及「它真的在看图吗」

### 1. 两条路线：从零联合训练，还是后来挂上去

多模态能力的骨架决策只有两条主路线：

| 路线 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **原生多模态** | 图像 / 视频 / 音频与文本 Token 从预训练起就交织在一起训练 | 视觉与语言在同一表示空间，早期对齐好，架构统一 | 数据配方、训练阶段、评测全部要为多模态重做（T03 的配方被改写） |
| **连接器 / 适配器** | 冻结或轻量微调的视觉编码器 + 投影层，把视觉特征「翻译」给已有文本模型 | 上车快、能复用成熟文本底座，增量小 | 对齐上限受连接器约束；「是否真的用图」的证据义务更重 |

历史锚点：Flamingo（2022）与 LLaVA 系（2023）是连接器路线的方法起源；此后的演进一边把连接器做深，一边把模态前移进预训练。**现役锚点**：Kimi K3 官方报告称原生多模态；Mistral Large 4 亦为原生多模态（[官方公告](https://mistral.ai/news/mistral-large-4-oss)口径）——旗舰层的默认姿势正在从「挂连接器」转向「原生进预训练」，但连接器路线在存量底座与轻量场景仍是主流做法（适用域判断，非淘汰论）。

### 2. 视觉 Token 预算：模态账怎么挤占窗口账

图像进模型不是「一张图一个输入」，而是先被切成**视觉 Token**：一张图通常对应数百到上千个视觉 Token（量级示意，具体以各模型文档为准）；视频再乘以帧数。于是模态账直接改写窗口账：

```text
窗口预算（例：1M Token）
    ├── 文档输入：几十万 Token（合同/财报）
    ├── 视觉输入：每图数百至上千 Token × 图数
    ├── 输出预留：上限越大，可用输入越小（口径见第 3 节）
    └── Agent 多轮：历史轨迹累积（T09 展开）
        ↓
「多模态长文档智能体」的窗口，比「聊天机器人」的窗口贵一个量级
```

它同时改写训练侧：原生路线的数据配方里要有足够的图文交织语料（回指 T03 的配比方法），训练阶段要多出编码器与文本主干的对齐阶段。模态决策从来不是「加一个输入口」那么便宜。

### 3. 模态账的训练阶段：两条路线改写的不是同一处

路线选择落到训练管线里，是两种不同的改造位置：

```text
原生多模态：
  图文交织语料进预训练（视觉编码器与文本主干早期联合）
      → 模态对齐 / 指令阶段（图文行为定型）
      → 多模态后训练（示范、偏好、RL 与文本同链路，T06–T09）

连接器 / 适配器：
  冻结或轻调的视觉编码器
      → 投影层训练（把视觉特征对到文本嵌入空间）
      → 指令微调（多为文本主干的轻量更新）
```

两个直接推论：

- **原生路线改写的是「预训练本身」**：数据配方必须有足够的图文交织语料（怎么配，回指 T03 的能力矩阵方法），预训练算力账里要计入视觉侧；这就是为什么原生多模态通常出现在「从头训」的旗舰上（K3、Mistral Large 4），而很少出现在存量底座的增量改造上；
- **连接器路线改写的是「后训练」**：预训练不动，增量集中在投影层与微调，便宜快，但对齐上限受连接器约束，且证据义务更重（见下一小节）。

视频与音频同理由：视频通常按「帧 × 每帧视觉 Token」进窗口（预算再乘一个量级），音频按帧或片段编码。现役锚点：K3.1 Pro 官方口径为文本 + 图像 + 视频输入、1M 上下文（[官方博客](https://www.kimi.ai/blog/kimi-k3-1-pro)）——多模态输入形态已经是旗舰默认配置，但「输入支持」与「证据使用」仍是两回事，验收纪律见下。

把两条路线的成本摊成一张清单，模态账的全貌就出来了：

| 成本侧 | 原生多模态 | 连接器路线 |
|---|---|---|
| 数据侧 | 图文交织语料的配比与质量评估（回指 T03 的方法） | 图文对 / 指令数据，量小但要求对齐质量 |
| 训练侧 | 预训练算力计入视觉侧；多出模态对齐阶段 | 投影层与轻量微调，增量小 |
| 推理侧 | 视觉 Token 进窗口、编码器延迟计入首 Token | 同左，但通常可用更小编码器 |
| 验收侧 | 证据义务三件套（见下） | 证据义务更重：对齐上限受连接器约束 |

### 4. 证据义务：模型是否真正使用了图像证据

多模态榜单分数上涨，不构成「模型在看图」的证明——文本先验（题干里已含答案线索）与图像证据（只有看图才能答对）在总分里无法区分。验收多模态能力时，证据义务至少有三条：

- **扰动测试**：遮挡图中关键数字 / 交换两张图 / 替换为无关图，答案应当跟着变。不变，说明模型没在看图；
- **同题有无图对照**：同一道题，有图与无图两个版本的正确率差，才是「图像证据贡献」的粗口径；
- **基准版本与评测口径**：多模态基准更新快，跨模型比较必须对齐基准版本与采样设置（T10 的评测治理展开）。

> **判断边界：**「支持图像输入」是接口口径，「使用图像证据」是能力口径，「两者都有评测证据」才是验收口径。模态账的最后一栏永远留给证据——没有扰动测试的多模态方案，按「文本模型 + 装饰性图片口」处理。

## 五、三笔账互相改写：架构是一张依赖图，不是技术清单

### 1. 把三笔账画成一张图

前四节分别算了三笔账，本节把它们接起来——这才是「联合决策」的本体：

```text
容量账（总参 / 激活）
    ├─ 改写 → 装载与部署（权重体积、量化门槛）
    ├─ 改写 → 通信（专家并行 all-to-all，T05 展开）
    └─ 改写 → 窗口账（专家权重与 KV Cache 抢同一块显存）
窗口账（注意力 / 上下文）
    ├─ 改写 → 并发与延迟（KV Cache × 并发路数 = 显存池）
    ├─ 改写 → 模态账（视觉 Token 挤占窗口预算）
    └─ 改写 → 上下文策略（长窗口 vs 检索 vs Compaction，T09）
模态账（原生 / 连接器）
    ├─ 改写 → 数据配方与训练阶段（T03 的产出被改写）
    ├─ 改写 → 窗口账（视觉 Token 膨胀）
    └─ 改写 → 训练系统（编码器吞吐、图文交织的数据管线，T05）
        ↓
硬件与部署约束（互联、机架、显存供给）反向锁定上面的选择
        ↓
Architecture ADR：把这张依赖图连同取舍理由一起存档
```

### 2. 三个「互相改写」的现役实例

**实例一：MoE 省下计算，却加重了窗口账。** MoE 把每 Token 计算压到 4–6%，但全部专家必须常驻显存——而 KV Cache 也要显存。专家权重与 KV Cache 在同一块卡上此消彼长：总参越大，留给并发或长上下文的显存越少。K3.1 Pro 的 5.6TB 权重（第三方报道口径）是最直白的刻度：容量账的膨胀，直接压缩了窗口账与并发的空间。

**实例二：稀疏注意力省了计算，瓶颈却换了地方。** GLM-5.2 的 IndexShare 把 1M 上下文的注意力计算压下来（约 2.9 倍，第三方拆解口径）之后，瓶颈转移到 KV Cache 容量、长上下文 kernel 与 CPU 侧开销。架构的收益没有消失，而是**被转移到了系统层**——这也是为什么本章的每一个数字最终都要在 T05 的训练与推理系统里复核。

**实例三：模态路线改写上一章刚定好的数据配方。** 选原生多模态的那一刻，T03 的预训练配方就被改写了：图文交织语料成为新的配比变量，其来源、质量评估与去污染都要按 T03 的方法重做一遍；选连接器，改写的位置则移到后训练的指令数据。模态账是三笔账里最会「越界」的一笔——它动的往往是别的章节刚交付的产物。

### 3. 硬件供给进依赖图：混合芯片栈的口径

三笔账之外还有一股反向作用力：**骨架越重，越依赖特定的互联与机架形态，硬件供给反过来约束架构选择。**2026 年最完整的公开案例是 DeepSeek 的「分阶段混合硬件」路线，把证据逐条列表（每条标口径）：

| 事实 | 口径 |
|---|---|
| DeepSeek V4 约 1.6T 参数、预训练数据超 32T Token | HF 模型卡口径 |
| V4 预训练主要仍在 NVIDIA 上，仅部分流程适配华为 Ascend | [MIT Technology Review](https://www.technologyreview.com/2026/04/24/1136422/why-deepseeks-v4-matters) 报道口径 |
| V4-Pro 的全参数后训练由华为牵头联合体用至少 1000 片 Ascend 芯片完成 | SCMP 报道口径，引用前需复核原文 |
| 第三方工作 SLAI T-Rex 在 Ascend NPU SuperPOD 上对 DeepSeek-V4 做端到端全参后训练，达到 34.22% MFU | [arXiv:2607.20145](https://arxiv.org/abs/2607.20145) |

三条读表纪律：

- **写成「完全国产化训练」或「完全去英伟达」都会翻车**——证据支持的只有「分阶段混合」：预训练与后训练用了不同供给策略；
- **「V5 将在华为硬件上预训练」属单源报道**，本章不采用；单一来源的下一代计划，默认不进决策依据；
- **教学意义在依赖图上**：万亿级骨架决定训练必须横跨机架级系统（wide expert parallelism 横跨 NVL72，NVIDIA 官方博客口径），机架与互联的供给能力因此成为架构可行域的一部分——这正是下一章（T05）的开场问题。

### 4. 回到开场：三份报价的联合裁决

现在可以把第 1 节的表格升级成裁决版（裁决 = 暴露前提，不是选出赢家）：

| 报价 | 它成立的前提 | 它没告诉你的 |
|---|---|---|
| A（2.8T-A104B，1M，原生多模态） | 你真的需要旗舰级能力上限，且部署在 TB 级权重装得起的集群上 | 每 Token 计算是三份中最贵（104B）；5.6TB 级权重的装载与私有化门槛 |
| B（744B-A40B，DSA+MLA） | 长文档是你的主负载，且能接受多模态路线另议 | 注意力省的是计算段，KV Cache 与系统侧开销仍在（瓶颈转移） |
| C（30B Dense + 连接器 + 检索，教学示意） | 材料访问是「查询式」的，检索召回率可证明，多模态需求浅 | 128K + 检索能否撑住「全息交叉引用」类任务；连接器的证据义务要自己补 |

三行读下来，真正的决策变量浮出水面：**任务的材料形态（全息阅读 vs 查询命中）、部署形态（云端集群 vs 私有化单机）、多模态深度（真用图 vs 装饰性接口）**。这三个变量分别来自八层坐标系的第①层（能力目标）与第⑦层（系统约束）——架构决策是在它们之间找可行域，而不是在结构名字里找「最新的」。

### 5. 依赖图的评审读法：四步走

把依赖图变成评审会上可操作的流程，任何骨架提案都按这四步过：

```text
第 1 步  先读输入：任务形态 / 部署形态 / 硬件供给
         —— 不读约束就读结构，是一切错位的起点
    ↓
第 2 步  再读三笔账读数：容量 / 窗口 / 模态
         —— 每个数字标口径（官方披露 / 第三方拆解 / 教学示意）
    ↓
第 3 步  顺着箭头找改写：这个方案改写了谁的账？
         —— MoE 改显存与通信；稀疏注意力改 KV 与 kernel；
            模态改数据配方与窗口预算
    ↓
第 4 步  最后找瓶颈转移：收益去哪了，代价转移到哪一层？
         —— 转移到系统层（T05）、数据层（T03）还是评测层（T10），
            每一处都要有人接住
```

四步走完，一份「我们用某某结构」的提案就变成了一组可检验的陈述：它假设了什么约束、改写了哪几本账、代价由谁承接、用什么实验验证。任何一步答不上来，提案就还没到能拍板的状态——这与引言八层坐标系「在花算力之前先让假设破产」的用法完全一致。

> **架构智慧：**抄旗舰骨架的人抄到的是别人约束的解。K3 的 896 选 16、GLM-5.2 的 IndexShare，都是在「万亿容量 + 长程任务 + 自家集群」这组约束下解出来的；你的约束不同，同一个解就是错的。复用推理（依赖图 + 取舍理由），不复制答案（结构配置）。

## 六、Architecture ADR：把骨架决策写成可复盘的文档

### 1. 为什么架构决策尤其需要 ADR

模型架构决策有一个别的决策没有的毛病：**它在训练开始前定死，在训练结束后才能验证**。词表、专家数、注意力结构、上下文目标，中途更换的成本都是「接近重训」。所以架构决策的文档价值最高——它记录的不是「选了什么」，而是「当时在什么约束下、放弃了什么、打算怎么验证」。

沿用引言的 Training ADR 九段骨架（完整模板在 T11），架构版填法如下：

```markdown
# Architecture ADR：模型骨架决策

1. 能力目标与任务形态——主负载是什么（全息阅读 / 查询命中 / Agent 多轮），
   多模态深度要求，哪些能力不许回退
2. 部署约束——云端高并发 / 低延迟 / 私有化 / 端侧；显存与互联供给；量化路线
3. 容量账——总参数 / 激活参数 / 专家数 / Top-K，双口径各自对应什么成本
4. 窗口账——注意力家族选择（压缩 / 稀疏 / 线性）、标称与有效上下文、
   KV Cache 预算、并发目标
5. 模态账——原生 or 连接器、视觉 Token 预算、数据配方改动（回指 T03）、
   证据义务的验收方式
6. 候选方案与放弃理由——每个候选写清它在三笔账上的读数
7. 系统影响——通信（专家并行）、显存切分、瓶颈转移预判（预告 T05）
8. 验证计划——小规模 proxy 实验、固定预算对照、有效上下文评测、
   多模态扰动测试；预测分级（已验证 / 部分验证 / 纯外推，回指 T02）
9. 退出条件——什么信号出现时重启骨架决策（如：有效上下文长期低于标称的 X%）
```

### 2. 一张速查决策表

把本章的推导压成一页（倾向为方向性指引，最终以三笔账复算为准）：

| 你的约束 | 容量倾向 | 窗口倾向 | 模态倾向 |
|---|---|---|---|
| 云端高并发 API，请求量大 | MoE，激活比 4–6% 区间，激活绝对值压低 | 稀疏 / 压缩组合，窗口按有效口径承诺 | 原生（若多模态是核心能力） |
| 私有化单机 / 中小规模 | Dense，或小型 MoE（以官方文档为准） | 128K–256K + 检索辅助 | 连接器，配证据义务 |
| Agent 长程任务 | 激活中等、总参可大 | 长窗口 + Compaction（T09 展开） | 视觉 Token 预算前置核算 |
| 端侧 / 设备 | 小 Dense + 极端过度训练（T02） | 短窗口，检索外置 | 通常不做或极轻 |
| 微调 / 领域适配为主 | Dense 优先（微调生态成熟） | 继承底座 | 连接器增量最小 |

### 3. 工程产物：Model Architecture ADR 检查清单

**输入项（每项标口径）：**

| 输入项 | 示例值 | 口径来源 |

### 4. 一份填好的示例（节选）

拿开场的场景把前几段填一遍（示例为本文演示，数字口径均回指本章正文；真实 ADR 应替换为自己项目的实测）：

```markdown
# Architecture ADR：中文企业智能体 · 模型骨架决策（示例节选）

3. 容量账
   选定 744B-A40B MoE（激活比 ≈5.4%，官方报告口径）。
   理由：高并发在线服务，每 Token 成本走激活口径（40B 优于 104B 绝对值，
   官方 API 标价 $1.0/$3.2 对 $3/$15 为方向性佐证）；
   放弃 2.8T 方案：装载门槛（第三方报道 5.6TB 量级）与私有化选项冲突。

4. 窗口账
   注意力：DSA+MLA 家族（生产化链条 V3.2→GLM-5，官方口径）。
   上下文：对外承诺「有效输入约 870K」（标称 1M − 输出预留 128K），
   词表 fertility 折扣另测；并发预算按第 3 节 KV Cache 算式复核。

5. 模态账
   路线：连接器（图表理解为浅多模态需求，证据义务可自行验收）；
   验收：扰动测试 + 同题有无图对照，双达标才计入能力目标。

8. 验证计划（证据分级）
   已验证：DSA+MLA 组合（多家生产采用，A1 口径）；
   部分验证：870K 有效上下文（口径推算 + 长文档评测待做）；
   纯外推：无。

9. 退出条件
   长文档评测中有效检索能力持续低于标称的 60%，或并发成本
   连续两季度超预算 → 重启骨架评审（优先复核窗口账与模态深度）。
```

这份 ADR 的纪律与 T02 的预算表相同：**每个数字标注身份（官方披露 / 第三方拆解 / 教学示意），每个取舍写明放弃了什么，每个预测留出回填位置。**评审者要能拿着它复算并挑错——挑不出的 ADR 不是写得完美，是写得不够诚实。

> **架构智慧：**架构决策最贵的失败模式不是选错结构，而是「选了却没人记得为什么」。一年后模型能力回退、要判断是数据问题还是骨架问题时，唯一能救你的是当年那份写清了前提与退出条件的 ADR。

## 七、六种最常见的错误判断

### 错误 1：把激活比例当成成本折扣

「激活只有 3.7%，所以成本低」混淆了比例与绝对值。每 Token 计算量对应激活参数**绝对值**（104B 仍是 40B 的 2.6 倍），激活比只说明相对自家总容量有多省。总参数决定的装载显存更是一分没省——K3.1 Pro（与 K3 同底座）的开放权重体积约 5.6TB（第三方报道口径）。**纠正动作**：报 MoE 成本必须三件套——总参、激活、激活比，缺一不可。

### 错误 2：把 MLA / DSA / 线性注意力写成升级路线

MLA 是压缩的 dense 注意力（还是全看，只是存得小），DSA 是稀疏选择（先选再看），线性注意力（KDA、MixLinear）是固定状态递推（近线性但可能忘）。三者是并列的三条路，且 DSA 与 MLA 在生产中是**叠加**使用。**纠正动作**：评审注意力方案先问「属于哪个家族、压哪条曲线」，再谈优劣。

### 错误 3：把标称上下文当有效上下文承诺

窗口是输入输出共享的：1M 配 128K 输出上限，可用输入约 870K；词表 fertility 再打一折；有效检索与多跳能力还要评测证明。行业判断（2026-01）窗口数字增长已在趋缓。**纠正动作**：对业务方只承诺「有效上下文 = 标称 − 输出预留 − fertility 折扣」，并附评测口径。

### 错误 4：宣布 Dense 已淘汰

2026 年旗舰榜单 Dense 稀少，但中小规模、微调为主、系统简单性优先、端侧形态的场景里 Dense 仍是常理答案（T02 的端侧案例即 Dense）。**纠正动作**：把「Dense vs MoE」写成部署形态的函数（显存账与通信账愿不愿意付），不写成时代先后。

### 错误 5：多模态只验收接口，不验收证据

「支持图像输入」不等于「使用图像证据」。没有扰动测试与同题有无图对照，榜单提升可能全部来自文本先验。**纠正动作**：多模态验收三件套——扰动响应、有无图对照、基准版本口径。

### 错误 6：抄旗舰骨架，不抄旗舰约束

K3 的 896 选 16、GLM-5.2 的 IndexShare 都是「万亿容量 + 长程任务 + 大型集群」约束下的解。抄配置不抄约束，等于把别人的答案填到自己的考卷上。**纠正动作**：复用前先走一遍本章第五节的依赖图，确认任务形态、部署形态与硬件供给同构；再核对每个数字的口径（权重开放 ≠ 训练透明 ≠ 可自部署）。

## 本章小结

- **骨架不是选新结构，是三笔账的联合决策**：容量账（总参 / 激活）、窗口账（注意力 / 上下文）、模态账（原生 / 连接器）互相改写，谁也不能单独拍板。
- **容量账：MoE 是成本结构的交换，不是打折。**2026 年现役 MoE 落在 0.7T–2.8T 总参、约 3%–6% 激活比；激活压的是每 Token 计算，总参决定的装载显存、负载均衡与专家通信一点没省。
- **窗口账：三个家族，三条路。**MLA 压缩 KV（仍全看）、DSA 稀疏选择（先选再看，V3.2 首发、GLM-5/5.2 跟进并加 IndexShare）、KDA 等混合线性（近线性但可能忘）——叠加与并列是常态，升级路线是误读。
- **1M 上下文已生产可用，但标称 ≠ 有效 ≠ 便宜**：输出预留先扣（1M 配 128K 输出约剩 870K）、fertility 再折、长上下文服务要按多卡显存预算（第三方估算 830–950GB 一档）。
- **模态账：原生与连接器各有适用域，验收看证据义务**——扰动测试、有无图对照、基准口径，三样齐了才叫「用了图」。
- **架构是一张依赖图**：容量挤窗口、稀疏注意力把瓶颈转移给系统、模态改写数据配方、硬件供给反向锁定骨架（DeepSeek 的分阶段混合芯片栈为证）。
- **Dense 未死**：中小规模、微调、端侧、系统简单性优先的场景，Dense 仍是诚实答案。
- **工程产物是 Architecture ADR**：九段骨架 + 三笔账读数 + 依赖图 + 验证计划与退出条件；每个数字标口径，每个取舍写明放弃了什么。

> **下一章的问题：**架构方案确定后,必须回答:如何把模型切分到 GPU 上,并让计算、通信、显存和故障恢复都能工作?

## 基础术语速查

| 术语 | 初学者可以先怎样理解 |
|---|---|
| 总参数 / 激活参数 | 装了多少东西 / 每个 Token 实际动了多少；前者对应显存与权重体积，后者对应每 Token 计算量 |
| MoE（混合专家） | 分诊医院：路由器把每个 Token 送给少数相关专家，其余专家不参与这次计算 |
| Top-K 路由 | 每个 Token 选中 K 个专家的规则；如 K3 的 896 个专家每 Token 选 16 个 |
| 负载均衡 | 让各位专家的活儿差不多多的机制；失衡会出现热专家排队、冷专家占显存 |
| KV Cache | 推理时缓存的历史 Token 键值，让模型不必每步重算历史；随上下文与并发线性增长 |
| Prefill / Decode | 推理两阶段：一次性并行处理输入（算力密集）/ 逐 Token 生成（访存密集） |
| MQA / GQA | 多查询 / 分组查询注意力：多个查询头共享 KV，把缓存压小（dense 家族） |
| MLA | 低秩压缩的 dense 注意力：仍看全部 Token，但每个 Token 存的 KV 更小（DeepSeek 系列起源） |
| 稀疏注意力（DSA 类） | 先为每个查询挑出 top-k 个相关 Token 再做注意力，「先选再看」；与 MLA 叠加使用 |
| 线性 / 混合线性注意力 | 用固定大小状态的递推代替「看全部历史」，计算近线性但有遗忘权衡（K3 的 KDA 为现役实例） |
| 原生多模态 / 连接器 | 图文从头联合预训练 / 视觉编码器挂到已有文本模型上；两条路线各有账 |
| 标称上下文 vs 有效上下文 | 厂商窗口数字 / 扣掉输出预留与 fertility 折扣后真正可用于输入的口径 |
