回车之后的那几秒

你在 pi 里按下回车，屏幕底部跳出 working 状态条。那几秒里，你那一行字被几个角色接力传了一遍——没有一个角色是模型自己。

把 pi 想成一场会议。模型是坐在桌前的主管，它不会自己离开座位去翻文件，只会说「小李，帮我把这段读出来」。你（pi）就是助理：照办，把结果摊回桌面，主管接着说下一句，直到他说「就到这里」。

🪑

主管：模型

坐在桌前不动。它能读文件、能改代码的那双手，是别人递给它的——它只会下指令。

🧑‍💻

助理：pi

把主管的每句话变成真的动作：读文件、跑命令、改代码，然后把结果摊回桌面。

💡
这套节奏叫代理循环

你说我做、我做完你再说——工程上叫代理循环 agent loop。模型不是「回答一次」，它可能连着问好几轮；它停手的标志，是某一轮回复里不再出现工具请求。

卡住了，先看哪一层

pi 不回话有三种长相，对应三层完全不同的代码。按症状定位，比重开会话重试快得多。

🖥️
界面层（packages/tui）：没反应

按键没进来、状态条不刷新、窗口不动、Ctrl+C 也没用。看的是 tui 的输入框和渲染。

🔁
代理循环层（packages/agent）：界面在动，文字不出来

working 一直转，或者转了两圈就停在那儿。看的是 agent-loop：请求发出去了吗、回复回来了吗、toolCall 判定对不对。

🔌
请求层（packages/ai）：明确报错

鉴权失败、模型名不存在、接口不通、限流。看的是 models.ts 里的 provider、密钥和请求参数。

为什么改一句 prompt 会牵连一大片：因为每一轮请求都把整段对话重新发一遍。模型每轮看到的都是"前面的全部 + 你这次这句"，所以多写一句话，可能让工具行为和权限检查一起变。上下文窗口 context window满了，老对话就进不去了。

所以下次 pi 不听话，别急着重开会话。先问两句：界面动了吗？动了就去 agent 层看这一轮到底发生了什么；模型那一轮说了什么、有没有 toolCall？这两问通常能把"卡住了"缩小到一个文件、一个函数。

一栋只能往下送电的楼

你在 pi 里敲下 /model，屏幕上列出一长串模型名：claude-…、gpt-…、gemini-…。这些名字没有一个是 pi 自己造的——它们来自这栋楼最底层的电缆井。

pi 不是一个程序，是一栋楼。楼里住着四层，每层只干一件事，而且只有一条规矩：楼上的可以往下拉线，楼下的永远不知道楼上住着谁。

🛠️
顶楼 · 总控室（packages/coding-agent）

把电接到模型、把模型的回话接到屏幕，顺便装上 read / bash / edit 这些工具和会话档案。它就是 pi 这个命令行程序本身。

🖥️
墙上 · 显示屏（packages/tui）

画框、收按键、渲染 Markdown。它压根不知道什么是大模型——它是一个通用终端界面库。

🔁
三楼 · 机房（packages/agent）

循环继电器：模型说「我要调工具」，由谁执行、结果怎么再喂回去，全在这一层。

🔌
地下 · 电缆井与总闸（packages/ai）

各家模型厂商的接口、密钥、请求格式都在这里。井里先通，电才能往上送。

颜色还是上一模块那套：朱红＝终端层（你、显示屏）、青＝coding-agent、紫＝agent 机房、金＝ai 电缆井、绿＝模型服务。

⚠️
最常见的误解：tui 依赖 ai

不依赖。翻 packages/tui/package.json，它一个 @earendil-works/* 包都没引，是这栋楼里最干净的叶子。所以 tui 不认识 AI，ai 也不认识 pi——把整栋楼拆了，显示屏照样能单独拿去用。

💡
「这段逻辑该写在哪」的三问

离用户的手最近（按键、渲染）→ 放 tui；离模型的嘴最近（请求格式、密钥、厂商协议）→ 放 ai；离屏幕最近（把工具、会话、扩展组装成 pi）→ 放 coding-agent；管的是「模型说了什么、工具怎么跑、结果怎么回喂」→ 放 agent。拿不准的时候问这四句，比翻目录快得多。

先定位层，再动手

同一句报错，落在不同层，修法完全不同。读完判罚单，下一步是判断它出自哪一层。点标签切换。

终端界面层（tui）

你看到的那层：画字、收按键，把你敲的话变成一条消息发给代理循环。

典型症状：输入框没反应、界面不刷新、进度条卡住不动——这些都跟模型无关，先怀疑这一层。

去哪儿看：packages/tui

代理循环层（agent-loop）

跑对话的那台机器：什么时候调工具、什么时候收尾、失败怎么写回上下文、上下文怎么被压缩。

典型症状：模型反复重试同一个工具、压缩发生得莫名其妙、你插的便条迟迟不进上下文——看 packages/agent/src/agent-loop.ts。

模型服务层（provider）

把请求发出去的那段电缆：换格式、附上密钥、处理限流和超时。

典型症状：认证失败、限流、连接被拒、响应被截断——先看这一层和你的密钥配置，别急着怀疑模型。

工具层（tool）

真正动手的那只手：读文件、跑命令、改代码。它抛出的错会被包成 toolResult，递回给模型。

典型症状：路径不存在、命令退出码非零、写入被拒——去看那条 toolResult 里写的具体原因，那才是判罚单正文。

四层里，错误几乎总能落到一层。先读判罚单上的字，再决定去 tui、agent-loop、provider 还是 tool 里找。

收尾：三步调试法

用户报「pi 反复重试同一条命令」。你先看对话记录（transcript）里的哪一条消息？看到什么就能断定是工具失败，而不是模型没听懂？

模型回复到一半被截断（stopReason === "length"），工具参数只写了一半。代码为什么选「失败」而不是「照着执行」？你怎么验证它确实没执行？

用户要禁止 agent 删文件。从哪个接缝下手？如果只靠在提示词里写一句「请不要删文件」，风险在哪？

所以，调试 pi 的顺序永远是三步：先读那张判罚单（错误文本写在哪儿），再判断它出自哪一层（tui / agent-loop / provider / tool），最后才决定是改代码、加一层扩展，还是改提示词。pi 把失败原样喂回模型，是为了让模型自己纠正；你不需要猜，你需要读。
