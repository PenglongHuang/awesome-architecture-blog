关键洞察：每一层都“只做一件事”

鉴权层不关心你问什么；路由层不关心你是谁；记账层不阻塞回答。软件工程里把这叫 关注点分离。看懂这个，你就能在让 AI 改代码时准确说出“这段逻辑应该放在哪一层”。

Scene 1 一个项目，两种用法

LiteLLM 经常让人困惑，是因为它同时是两个产品：一个 Python 库，和一个 AI 网关服务。 它们共用同一套底层代码，但面对的用户完全不同。

🧰 Python SDK

写几行 Python，直接调用 100+ 模型。

  • import litellm
  • 没有多租户、虚拟 Key、预算
  • 适合脚本、原型、单个应用
  • 核心入口：litellm/main.py

🏢 AI Gateway（Proxy）

起一个 HTTP 服务，让整个团队/公司来调用。

  • 监听 :4000
  • 虚拟 Key、限流、预算、路由、管理台
  • 适合团队、平台、对外中转站
  • 核心入口：litellm/proxy/
🔁
它们不是二选一

网关内部就是在调用 SDK：Proxy 先做鉴权/限流/选路，再把请求交给 SDK 去翻译和发 HTTP。所以看懂 SDK 的请求流程，是看懂网关的基础。

补充：这个版本的仓库新增了 gateway/ 目录，它复用原来的 FastAPI 应用，但只保留“LLM 数据面”的路由； 完整的控制面仍然可以通过旧入口 litellm.proxy.proxy_server:app 使用。

打开 litellm/main.py，主角 acompletion 的第一屏就是它的“能力清单”。 你看不到任何厂商特有的参数，全是 OpenAI 风格的通用参数：

大白话

model 是唯一必须给的参数。格式通常是 "厂商/模型名"，比如 "anthropic/claude-sonnet-4"。

03

翻译层：让 100 家厂商说同一种话

OpenAI 格式进，各家方言出；回答回来，再统一成一种格式。

Scene 1 同一个“你好”，三种方言

想象你带了一个万能转换插头去旅行。OpenAI、Anthropic、Gemini 的插座形状不同，但你的电器只认一种插头。 LiteLLM 的翻译层，就是这个转换插头。

O

OpenAI 方言

对话放在 messages 里，每条有 role 和 content。这是 LiteLLM 的“普通话”。

A

Anthropic 方言

系统提示单独放 system；消息内容用 content block 数组；工具调用有自己的一套字段。

G

Gemini 方言

对话叫 contents，每条消息里是 parts；角色名和工具格式也不一样。

如果每个应用都自己写三套适配代码，维护成本会爆炸。LiteLLM 把这些差异收进 Provider 目录下的 transformation.py，对外只暴露一套 OpenAI 接口。

Scene 2 一次翻译的往返

1
统一入口收到 OpenAI 格式

messages、temperature、tools……全是标准 OpenAI 参数。

2
识别 provider

从模型名前缀（如 anthropic/…）解析出该找哪家翻译器。

3
transform_request()

把 OpenAI 请求翻译成厂商能懂的 JSON：字段改名、结构重排、丢弃不支持的参数。

4
发 HTTP，拿到原始响应

厂商返回自己的格式，可能是流式的一串事件。

5
transform_response()

把厂商响应翻译成统一的 ModelResponse，包括 choices、usage、工具调用。

6
流式处理

如果是 流式，还要把各家的 SSE 事件逐块翻译并转发。

Scene 3 “哪些参数我能用？”写在清单里

每个 provider 的 Config 类都有一个方法，声明自己支持哪些 OpenAI 参数。下面是 Anthropic 的清单：

PYTHON · llms/anthropic/chat/transformation.py 
def get_supported_openai_params(self, model: str):
    params: Final = [
        "stream",
        "stop",
        "temperature",
        "top_p",
        "max_tokens",
        "max_completion_tokens",
        "tools",
        "tool_choice",
        "extra_headers",
        "parallel_tool_calls",
        "response_format",
        "user",
        "web_search_options",
        "speed",
        "context_management",
        "cache_control",
    ]
大白话

这是一张“验收单”。请求里出现清单内的参数，翻译器会认真处理；不在清单里的，可能会被丢弃或报错（取决于 drop_params 设置）。

“stream” 在里面，说明 Anthropic 支持流式；“tools / tool_choice” 在里面，说明支持工具调用。

“cache_control” 在里面，说明支持 提示词缓存。不同厂商的缓存写法不同，翻译器负责转换。

这份清单就是契约。要新增一个 OpenAI 参数支持，第一步就是把它加到这里，并在 map_openai_params 里写转换逻辑。

Aha：翻译层是最容易出 bug 的地方

网络、鉴权、路由出问题通常报错很明确；翻译层的 bug 往往表现为“请求成功了，但模型行为不对”。比如缓存没生效、工具调用参数丢了、流式内容缺了一块。排查时先对比转换前后的 JSON。

虚拟密钥：谁能进来，能花多少钱

不要把真正的厂商 API Key 发给客户。发给他们的，是一张有额度、有权限的“房卡”。

Scene 1 总卡与房卡

酒店前台有一张总卡，能打开所有房间。客人拿到的是房卡：只能开自己的门，而且过了退房时间就失效。

❌ 直接分发厂商 Key

  • 拿到 Key 的人可以为所欲为
  • 无法知道是谁花的钱
  • 一个人泄露，全员换 Key
  • 无法按团队限额

✅ 分发 LiteLLM 虚拟 Key

  • 绑定到某个用户/团队
  • 可设预算、RPM/TPM、模型白名单
  • 随时吊销，不影响其他 Key
  • 每一笔花费都能归属到人

在 LiteLLM 里，虚拟 Key 以 sk- 开头，用法和 OpenAI Key 一样。客户端以为自己在直连 OpenAI，其实请求先到了 LiteLLM。

Scene 2 四层身份：Org → Team → User → Key

🏢
Organization（组织）

最大的租户。适合一个公司或一个事业部，可以有自己的预算和管理员。

👥
Team（团队）

组织下的协作单元。预算、模型权限、回调（如 Langfuse）可以按团队配置。

👤
User（用户）

具体的人。一个用户可以拥有多把 Key，也可以属于多个团队。

🔑
Key（密钥）

真正发到客户端手里的那一串字符。限额可以设在这一层，也可以继承上层。

🧾
为什么要分四层？

因为“谁花了多少钱”必须能按不同粒度回答：公司总共花了多少？研发部花了多少？张三花了多少？这把 Key 花了多少？四层结构就是这个账本的维度。

数据层对应 litellm/models/ 里的实体（如 LiteLLM_VerificationToken、LiteLLM_TeamTable、LiteLLM_UserTable），读写封装在 litellm/repositories/。

Scene 3 门卫怎么验证一张房卡

1
从请求头取出 Key

通常是 Authorization: Bearer sk-…，也支持其他厂商的 Header 写法。

2
对 Key 做哈希

不是拿明文去数据库比对，而是先算 SHA-256，再用哈希值查。

3
先查 Redis 缓存

身份信息缓存起来，避免每个请求都打 Postgres；缓存没命中才回源。

4
组装 UserAPIKeyAuth

把用户、团队、预算、权限、限流配置打包成一个对象，交给后续每一层。

Scene 4 为什么数据库里不存明文 Key

PYTHON · types/proxy/auth/user_api_key_auth.py 
def hash_token(token: str) -> str:
    import hashlib

    # Hash the string using SHA-256
    hashed_token: Final = hashlib.sha256(token.encode()).hexdigest()

    return hashed_token
大白话

把 Key 变成一串固定长度的指纹。SHA-256 是单向的，拿到指纹也推不回原 Key。

数据库只存指纹。所以即使数据库泄露，攻击者也拿不到能直接使用的明文 Key。

验证时比指纹。客户端发来明文 Key，服务器算一次哈希，再和数据库里的指纹比对。

📄 litellm/types/proxy/auth/user_api_key_auth.py : 40
⚠️
两个常见误解

1）虚拟 Key 不是“加密后的厂商 Key”，它是一把独立签发的凭证。
2）哈希不等于加密：加密可以解密，哈希不能。因此明文 Key 通常只在创建时展示一次，丢了只能重新生成。

想继续深入：鉴权主流程在 litellm/proxy/auth/user_api_key_auth.py，预算校验在 litellm/proxy/auth/auth_checks.py，JWT/SSO 在 handle_jwt.py。

05

限流与预算：别让一辆车堵死整条路

RPM 管“多快”，TPM 管“多重”，预算管“总共能花多少”。

Scene 1 匝道信号灯与油箱

高速公路入口有匝道信号灯：每分钟只放固定数量的车上去，否则主路会堵死。同时，每辆车还有油箱：油烧完就必须停下。

限流（Rate Limit）解决“瞬时压力”，预算（Budget）解决“长期消耗”。它们是两套不同的闸门，经常被混为一谈。

🚦

RPM

Requests Per Minute，每分钟请求数。最直观的“频率”上限，适合防止脚本刷爆。

🪙

TPM

Tokens Per Minute，每分钟 Token 数。一次长上下文请求可能顶几百次短请求，只看 RPM 会误判。

🚗

Max Parallel

同时进行的请求数上限。防止一个客户端占满所有连接。

⛽

Budget

一段时间内能花的钱（或 Token）。可以按 Key、用户、团队、组织分别设。

Scene 2 计数器长什么样

限流不是“记住总数”，而是“记住这一分钟的数”。LiteLLM 把计数器放在 Redis 里，Key 的拼法非常直白：谁 + 哪一分钟 + 计什么。

PYTHON · proxy/hooks/parallel_request_limiter.py 
request_count_api_key=(f"{api_key}::{precise_minute}::request_count" if api_key is not None else None),
request_count_api_key_model=(
    f"{api_key}::{_model}::{precise_minute}::request_count"
    if api_key is not None and _model is not None
    else None
),
request_count_user_id=(
    f"{user_api_key_dict.user_id}::{precise_minute}::request_count"
    if user_api_key_dict.user_id is not None
    else None
),
大白话

第一行：每把 Key 每分钟一个计数。比如 sk-abc::19:42::request_count。分钟一变，自动换新计数器。

第二段：Key + 模型 + 分钟。这样可以单独限制“某个 Key 调某个模型”的频率，而不是一刀切。

第三段：用户 + 分钟。同一个人可能有多把 Key，用户级计数能把它们合起来算。

后面还会按 team、end-user 再记一遍。同一个请求可能同时消耗多个维度的配额，任一维度超限都会拒绝。

Scene 3 先占座，再结账

Token 数是请求发出去之前无法精确知道的（模型还没生成回答）。所以 LiteLLM 采用“预扣 + 对账”：

1
预估

根据输入消息估算大概会消耗多少 Token。

2
预扣（reserve）

先从配额里“占座”，防止并发请求把额度同时用超。

3
真实调用

请求发往上游，拿到实际 usage（输入/输出 Token 数）。

4
对账（reconcile）

用真实用量替换预估值，多退少补。失败/断连也要释放占座。

💡
Aha：为什么一定要 Redis？

如果你只跑一个 LiteLLM 实例，内存里记计数器就够了。但生产环境通常是多实例，用户的下一个请求可能落到另一台机器。计数器必须放在共享存储里，否则每台机器都以为“自己没超限”。

预算的“预扣”还能避免并发超支：两个请求同时看到“还剩 $0.01”，都以为能花，最后一起超。占座机制让第二个请求看到的是“已被占掉一部分”的余额。

Scene 4 配置长什么样

在模型部署上可以直接写限流参数；在虚拟 Key / 团队上则配置预算和 RPM/TPM。下面是仓库自带配置里的真实片段：

rpm: 480这个部署每分钟最多 480 次请求（来自 proxy_server_config.yaml 的模型配置）。
timeout: 300单次调用最多等 300 秒。
stream_timeout: 60流式响应允许的空闲/总时长上限，避免连接一直挂着。
max_budget / budget_duration预算金额与重置周期，例如 30 天。可在 settings 或 Key/团队层配置。
🧮
限流的三层视角

请求级（RPM/并发）防止刷接口；Token 级（TPM）防止长上下文拖垮上游；金额级（Budget）防止账单失控。三层都配，才算完整。

路由、重试与降级：永远留一条备用跑道

同一个模型名，可以对应多个部署。Router 决定这次飞哪条航线。

Scene 1 一个名字，多条航线

在订票 App 里，你输入“北京 → 上海”，系统会给你多个航班：直飞、经停、不同航司。你只关心目的地，系统负责挑一个能飞的。

LiteLLM 里，客户端请求的 model="gpt-4o" 是一个模型组（model group）。这个组背后可以挂多个部署（deployment）： OpenAI 官方、Azure 同名模型、甚至另一个区域节点。Router 的工作就是从中选一个。

🎲

加权随机

simple_shuffle.py：按 weight/rpm/tpm 权重随机选，简单、分散压力。

⏱️

最低延迟

lowest_latency.py：优先选最近响应更快的部署。

💰

最低成本

lowest_cost.py：在健康部署里优先选更便宜的。

📊

TPM/RPM 余量

lowest_tpm_rpm.py：看哪个部署这一分钟还有余量，避开快被打满的。

还有 least_busy.py、tag_based_routing.py、以及自适应/复杂度路由等策略，都在 litellm/router_strategy/。

Scene 2 加权随机是怎么算的

“加权随机”不是简单掷骰子。它先看每个部署的权重；如果权重没配，就依次退回用 rpm、tpm 当权重。下面是选择循环：

PYTHON · router_strategy/simple_shuffle.py 
for weights in weight_sets:
    largest = max(weights, default=0.0)
    if largest <= 0:
        continue
    normalized = tuple(weight / largest for weight in weights)
    if sum(normalized) <= 0:
        continue
    selected = random.choices(healthy_deployments, weights=normalized)[0]
    _ROUTER_LOGGER.info("Selected deployment for model %s: %s", model, selected.get("model_info"))
    return selected
大白话

依次尝试几套权重：先看请求里指定的权重，再看部署的 weight，再看 rpm，最后看 tpm。只要有一套有效就用它。

归一化：把权重按最大值缩放成 0~1，方便随机选择。全为 0 就跳过这套。

按权重随机抽一个健康部署。权重越高，被抽中的概率越大，但不是绝对轮流。

如果所有权重都无效，最后会完全随机选一个（函数末尾的兜底）。

📄 litellm/router_strategy/simple_shuffle.py : 55
⚖️
为什么按权重而不是轮询？

因为部署的能力不一样：有的额度大，有的额度小，有的延迟低。权重让你能表达“这个部署承担 70% 流量，那个承担 30%”。

Scene 3 重试 ≠ 降级

🔁 重试（Retry）

同一目标，再试一次。

  • 适合偶发超时、网络抖动、429
  • 通常有次数上限和退避
  • 不改变模型，只增加延迟

🪂 降级（Fallback）

换一个目标。

  • 主模型持续失败时，切到备用模型组
  • 可以按“上下文超长”或“内容策略”触发
  • 模型变了，输出风格和质量可能也变

Router 的 async_function_with_fallbacks 会准备三类降级名单：

PYTHON · router.py 
fallbacks: Final[list | None] = kwargs.get("fallbacks", self.fallbacks)
context_window_fallbacks: list | None = kwargs.get("context_window_fallbacks", self.context_window_fallbacks)
content_policy_fallbacks: list | None = kwargs.get("content_policy_fallbacks", self.content_policy_fallbacks)
大白话

普通降级名单：主模型报错（超时、5xx、供应商故障）时，按顺序尝试备用模型组。

上下文窗口降级：提示词太长、超过主模型窗口时，切到窗口更大的模型。比如长文档分析。

内容策略降级：主模型因安全策略拒绝时，切到策略更宽松的模型（是否合规要你自己判断）。

优先级：请求里传的名单优先于 Router 全局配置。这让你能按业务场景覆盖默认策略。

📄 litellm/router.py : 8427
⚠️
降级的隐藏代价

备用模型可能更贵、更慢、输出风格不同。降级是“可用性优先”的取舍，不是免费的。生产上要监控降级率，并给用户/调用方返回 x-litellm-* 头部，避免“悄悄换了模型”导致难以排查。

Scene 4 一次请求的决策顺序

1
过滤不健康部署

健康检查失败、被冷却（cooldown）的部署先排除。

2
按策略选一个

加权随机 / 最低延迟 / 最低成本……取决于你配置的 routing strategy。

3
调用失败，先重试

在 num_retries 范围内重试当前部署或同组部署。

4
仍失败，走降级

按 fallbacks 名单换模型组，并记录尝试过哪些目标。

5
把决策写进响应头

调用方能看到用了哪个模型、是否降级、成本是多少，便于排障。

成本追踪：每一次调用都有一张计价器

Token 怎么变成钱？账单为什么是异步写的？哪些账 LiteLLM 管，哪些要你自己建？

Scene 1 出租车计价器

出租车不是按“一趟”收费，而是按里程和时间。模型调用也一样：输入 Token 是起步里程，输出 Token 是继续行驶，缓存命中则像“已走过的路打折”。

📥
输入 Token

你发给模型的提示词。通常按“每百万 Token 多少美元”计价。

📤
输出 Token

模型生成的回答。单价通常比输入贵，因为生成更耗算力。

♻️
缓存 Token

命中的提示词缓存，通常有折扣；写入缓存也可能单独计费。

价格表在仓库根目录的 model_prices_and_context_window.json，每个模型一行：上下文窗口、输入价、输出价、缓存价、支持的参数等。

Scene 2 计价公式：没有魔法

PYTHON · cost_calculator.py 
regular_prompt_tokens: Final = max(
    prompt_tokens - cached_tokens - cache_creation_tokens,
    0,
)

input_cost: Final = (
    regular_prompt_tokens * input_cost_per_token
    + cached_tokens * cache_read_input_token_cost
    + cache_creation_tokens * cache_creation_input_token_cost
)
output_cost = completion_tokens * output_cost_per_token
大白话

先算“普通输入”：总输入减去缓存命中和缓存写入的部分。用 max(…, 0) 防止出现负数。

输入成本 = 普通输入 × 输入单价 + 缓存命中 × 缓存读单价 + 缓存写入 × 缓存写单价。三段分别计价。

输出成本 = 输出 Token × 输出单价。有些模型还有图片、音频、推理 Token 等附加项，会再加。

单位是“每 Token 美元”，价格表里通常写“每百万 Token”，代码里会先换算。

💡
Aha：成本计算是“估算 + 定价表”

LiteLLM 不是向厂商查询账单，而是用厂商公开的单价 × 实际 Token 数自己算。所以价格表需要持续更新；厂商调价后，LiteLLM 也要更新 JSON。

Scene 3 账单为什么是异步写的

如果每来一个请求就同步写一次 Postgres，数据库会成为瓶颈，用户也要多等。LiteLLM 的做法是“先返回，再记账”：

1
响应里带上成本

成本先塞进响应的隐藏字段 _hidden_params["response_cost"]，再暴露成响应头 x-litellm-response-cost。

2
触发成功回调

SDK 的 logging 对象调用 async_success_handler()，通知所有已注册的回调（LiteLLM 自己的记账器、Langfuse、Prometheus 等）。

3
先入 Redis 队列

DBSpendUpdateWriter 把“某 Key 增加 $0.0021”放进队列，而不是立刻写库。

4
后台批量落库

APScheduler 每 60 秒跑一次 update_spend，把队列里的增量批量写进 Postgres。把 N 次写合并成 1 次。

🧾
这解释了一个常见现象

你在管理台看到的用量可能延迟几十秒才更新。这不是 bug，而是“异步批量写入”的取舍：牺牲实时性，换取数据库吞吐和请求延迟。

Scene 4 LiteLLM 管到哪，你还要建什么

结合你开头那张“AI 中转站”架构图，这条边界非常重要：

✅ LiteLLM 已经覆盖

  • 每次调用的成本计算与用量日志
  • Key / 用户 / 团队 / 组织级预算
  • 预算预扣与并发防超支
  • 用量看板、花费报表
  • 成本响应头、回调到 Langfuse 等

🧱 通常要你自己建

  • 支付充值（支付宝 / 微信 / Stripe）
  • 发票、退款、对账、税务
  • 与财务系统的账单同步
  • 复杂合同价、阶梯价、分成结算
  • 面向客户的套餐与订阅体系
🧮

LiteLLM 提供的是“用量与成本的计量层”，不是完整的“计费账务系统”。预扣/预算它做了，但支付、退款、发票、对账这些“钱的闭环”，仍然要接你自己的业务系统。
