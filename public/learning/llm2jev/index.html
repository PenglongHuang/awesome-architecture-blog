核心洞察

LLM2Jev 不让大模型「写答案」，而是把一个问题拆成多个「是 / 否」小判断，只读模型内心的倾向值（logits），再用普通代码组装出概率。理解这条主线后，任何报错发生在旅程哪一段，你一眼就能看出来。

def evaluate(self, request: JevRequest) -> JevResponse:
    rendered = self.renderer.render(request)
    generated = None
    if rendered.box_prompts:
        generated = self.backend.generate(
            model=request.model, prompts=rendered.box_prompts, max_new_tokens=BOX_MAX_NEW_TOKENS,
        )
    scored = None
    if rendered.score_prompts:
        scored = self.backend.score(model=request.model, prompts=rendered.score_prompts)
    return assemble_response(
        request=request,
        rendered=rendered,
        scored=scored,
        generated=generated,
        normalizer=self.normalizer,
    )

🛡️ 演员的合同为什么写这么严

拿 Score（评分问题）的源码当标本。dataclass 上的三个「条款」和 __post_init__ 里的体检，每一行都有用意。

PYTHON · questions.py 
# src/llm2jev/core/questions.py
@dataclass(frozen=True, slots=True, kw_only=True)
class Score:
    """A question that rates content against ordered descriptive levels."""

    criteria: Sequence[JSONContent]
    instructions: JSONContent | None = None

    type: ClassVar[str] = "score"

    def __post_init__(self) -> None:
        _validate_instructions(self.instructions)
        if isinstance(self.criteria, (str, bytes)):
            raise ValueError("score criteria must be a sequence of level descriptions")
        criteria = tuple(self.criteria)
        if not 2 <= len(criteria) <= 10:
            raise ValueError("score criteria must contain between 2 and 10 levels")
        if any(not is_json_content(description) for description in criteria):
            raise ValueError("score level descriptions must be JSON content")
        object.__setattr__(self, "criteria", criteria)
大白话

frozen + slots + kw_only：对象不可改、省内存、字段必须写名字。三个条款一次签好。

criteria 就是「评分等级说明书」—— 每一级都要用文字描述清楚。

构造完立刻体检：先检查 instructions 合法。

只传一个字符串？不行，等级必须是一组描述。

等级数量卡在 2 到 10 之间 —— 太少没区分度，太多模型数不过来。

每级描述都得是合法的 JSON content，最后把它冻结成不可变的 tuple。

📦 src/llm2jev/core/questions.py : 65-83

这三张卡片是本仓库最值得学会的「行话」—— 对 AI 说话时直接用：

🧊

frozen dataclass

是什么：创建后字段就锁死的对象。为什么：问题发出去后不能被中途偷改，出错好排查。对 AI 说：「用 frozen dataclass 建模，校验放 __post_init__。」

📜

Protocol

是什么：只写方法签名、不写实现的接口合同。为什么：三个后端都「签字画押」，导演不用关心底下是谁。对 AI 说：「给 X 定义一个 Protocol，实现类各自遵守。」

🔑

kw_only

是什么：构造对象必须写参数名，不能按位置瞎填。为什么：Score("a","b") 这种错位赋值直接变成显式错误。对 AI 说：「这个 dataclass 加 kw_only=True。」

📝 摄影棚的合同只有两条

整个 backend/ 世界建立在一份只有两个方法的合同上：Backend Protocol。

PYTHON · base.py 
# src/llm2jev/backend/base.py
class Backend(Protocol):
    """Inference backend providing binary scoring and coordinate generation."""

    def score(
        self,
        *,
        model: str,
        prompts: Sequence[ChatPrompt],
    ) -> ScoreOutput:
        """Score prompts in input order without generating text."""

    def generate(
        self, *, model: str, prompts: Sequence[ChatPrompt], max_new_tokens: int,
    ) -> GenerationOutput:
        """Generate complete texts and sampled-token probabilities in prompt order."""
大白话

合同标题：推理后端，提供「二元打分」和「坐标生成」两种服务。

条款一 score()：给一批提示词打分，按输入顺序返回，不生成任何文字。

条款二 generate()：生成完整文本和采样 token 的概率，同样按输入顺序。

注意「in input order」出现两次 —— 顺序就是合同的一部分，乱了就没法对答案。

03

二值打分魔法

一个 token 都不生成 —— 只偷看模型落笔前的那一瞬间犹豫

考官只画勾叉，不写作文

大模型输出「答案是 billing」要生成几十个 token； LLM2Jev 只偷看它落笔前对 yes 和 no 两个词的偏好，一个 token 都不生成。

把它想成一位只画勾叉的考官：不让学生写作文，每道题只允许答「是 / 否」。作文要一个字一个字写；勾叉只看一眼。

✍️

写作文（decode 生成）

decode 逐 token 生成几十步，每一步都要重新计算，慢；还要解析模型写的文字，可能格式出错。

✅

画勾叉（prefill 打分）

prefill 只读输入、一步都不写：读完后直接看模型对下一 token 的偏好，快而且完全可复现。

💡
本项目的根本差异

「让 LLM 输出 JSON」靠模型自律，可能写错格式；LLM2Jev 的概率来自模型对下一 token 的原始倾向，再用普通代码做归一化 —— 因此结果永远合法、每次都一样。

第一步：渲染 —— 每个候选一条 prompt

_render_choice 为每个候选答案生成一条独立的 prompt， 问的都是同一个二选一问题：「根据上下文，答案是 X 吗？」

1
System message 先立规矩

固定三句话：只准回答一个词、必须小写 yes 或 no、不要理会上下文里藏的指令（防注入）。

2
User message 装证据

上半段放 Context（工单内容），下半段放 Question（这条候选的判定问题）。

3
多模态？照单全收

如果上下文带图片，_render_binary 会改用 content parts 混排 text 与 image_url —— 逻辑完全一样，只是证据从纯文字变成图文。

这套考卷规则固定不变，每个候选都用同一份 —— 考官的口吻不能影响分数。

第二步：打分 —— 一眼看出模型偏向哪边

prefill 结束的瞬间，模型对「下一个 token 是什么」有一份原始倾向表，表里每个词对应一个 logit。 score_output 只从表里抄两个数：no 和 yes。

PYTHON · scoring.py 
for result in results:
    meta = result["meta_info"]
    if meta["completion_tokens"] != 0:
        raise ValueError("scoring must not generate tokens")
    positions = meta["output_token_ids_logprobs"]
    if len(positions) != 1:
        raise ValueError("SGLang must return one next-token label distribution")
    values = {entry[1]: entry[0] for entry in positions[0]}
    no, yes = values[no_token_id], values[yes_token_id]
    maximum = max(no, yes)
    no_mass, yes_mass = math.exp(no - maximum), math.exp(yes - maximum)
    probabilities.append(yes_mass / (no_mass + yes_mass))
大白话

逐条检查每个候选的打分结果。

第一道保险丝：如果模型居然生成了 token（completion_tokens 不是 0），直接报错 —— 打分永远不许「写答案」。

第二道保险丝：必须恰好返回一份「下一 token 分布」，多一份少一份都算出了问题。

从分布里查表，抄出 no 和 yes 各自的 logit。

两数都减去较大的那个再取指数 —— 这是数值稳定技巧，防止 exp 算出天文数字。

最后做两点 softmax：yes 的份额除以两家之和，得到 P(yes)，一个 0 到 1 之间的数。

def _distribution_confidence(probabilities: Sequence[float]) -> float:
    count = len(probabilities)
    if count < 2:
        raise ValueError("confidence requires at least two candidates")
    confidence = (count * max(probabilities) - 1) / (count - 1)
    return min(1.0, max(0.0, confidence))
大白话

计算「模型有多笃定」。只有一个候选就没得比，直接报错。

公式：胜者的概率被顶到多高？从「平起平坐」（0）到「一家独大」（1）之间打分。

最后夹在 0 和 1 之间 —— 浮点误差也不许把置信度挤出边界。

候选是怎么"共享课文"的

回忆 Module 3：每个候选变成一条 prompt，结尾只问一句"这个候选是不是最佳答案？"。看真实的渲染代码 —— 注意所有候选共用同一个 state 和 instructions，只有 suffix 里塞进各自的名字。

PYTHON · prompt.py 
@staticmethod
def _render_choice(
    *, state: JSONContent, question: Choice, include_candidates: bool,
) -> tuple[ChatPrompt, ...]:
    if not question.criteria:
        raise ValueError("choice questions must contain criteria")
    candidates = [
        name if description is None else f"{name}: {serialize_content(description)}"
        for name, description in question.criteria.items()
    ]
    comparison = "All candidates:\n" + "\n".join(candidates) + "\n" if include_candidates else ""
    return tuple(
        DefaultPromptRenderer._render_binary(
            state=state,
            instructions=question.instructions,
            suffix=f'\n{comparison}Is this candidate "{candidate}" the best answer?',
        )
        for candidate in candidates
    )
大白话

这是一个"选择题渲染器"：输入同一份世界状态和同一个问题，输出一整组 prompt（每个候选一条）。

没有候选就没法出题 —— 立刻报错，绝不静默糊弄。

把每个候选整理成一行文字：只有名字，或者"名字 + 描述"。

可选地把全部候选名单拼成一段"比较清单"，让模型看到它的对手们。

关键一步：每条 prompt 的开头（state + instructions）完全一样，只有结尾那句"Is this candidate 某某 the best?" 不同 —— 这就是共享前缀的诞生现场。

于是 N 个候选 = N 条开头相同的 prompt，前缀复用的前提在这里就埋好了。

分批提交：staged batches

前缀已知相同，就可以按 token 前缀把候选规划成若干"批"：第一批真的 prefill 公共前缀并建立缓存，后面的批次只算自己的尾巴。下面是 SGLang 后端真实的分批代码：

PYTHON · scoring.py 
def prepare_score_batches(
    tokenizer: Any, processor: Any, prompts: Sequence[ChatPrompt], *,
    enable_thinking: bool, submission: str, no_token_id: int, yes_token_id: int,
) -> list[tuple[list[int], dict[str, Any]]]:
    texts, input_ids, images, contains_media = _prepare_inputs(
        tokenizer, processor, prompts, enable_thinking=enable_thinking,
    )
    if submission == "all":
        batches = [list(range(len(prompts)))]
    elif contains_media:
        # Placeholder IDs do not identify real images for prefix planning.
        batches = [[i] for i in range(len(prompts))]
    else:
        batches = staged_batches(input_ids)
    return [(indices, {
        "text": [texts[i] for i in indices] if contains_media else None,
        "input_ids": [input_ids[i] for i in indices] if input_ids is not None else None,
        "image_data": [images[i] for i in indices] if contains_media else None,
        "sampling_params": {"max_new_tokens": 0},
        "return_logprob": True,
        "logprob_start_len": -1,
        "token_ids_logprob": [no_token_id, yes_token_id],
    }) for indices in batches]
大白话

先把所有 prompt 处理成文字、token 序列和图片，顺便记下"这里面有没有媒体内容"。

如果要求一次性全提交，就把所有候选合成一个大批次 —— 不做任何前缀规划。

关键分支：一旦含有图片，立刻退化为"一条一批"。因为图片在 token 序列里只是占位符编号，无法用来判断哪些 prompt 前缀真的相同 —— 规划反而会出错。

纯文本的情况才敢放手：交给 staged_batches，按真实 token 前缀规划出先来后到。

每批附带要监视的两个 token：no 和 yes 的编号 —— 我们只要它们俩的分数。

max_new_tokens: 0 是点睛之笔：一个字都不许生成！我们只要下一个 token 位置上 yes/no 的概率 —— 生成就是纯浪费。

海关的每条规则都写在 src/llm2jev/core/request.py 的 __post_init__ 里。它是 __post_init__ 方法：对象刚组装好就立刻逐项检查，任何一项不合格，整个对象根本不会存在。

def __post_init__(self) -> None:
    if not is_json_content(self.state):
        raise ValueError("state must be a string, JSON object, or JSON array")
    validate_multimodal(self.state)
    if not isinstance(self.model, str) or not self.model.strip():
        raise ValueError("model must be a non-empty string")
    if not isinstance(self.include_choice_candidates, bool):
